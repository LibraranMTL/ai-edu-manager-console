# 学习项目模块完整开发计划

> 基线版本：Windows 0.8.3
>
> 计划状态：已整合现有能力、历史后续计划与 0.8.3 全链路审计结果。
> 核心目标：在保持“项目工作空间 + 项目知识空间”双空间架构的前提下，把学习项目收敛为可靠、可追溯、低操作负担的完整闭环。
>
> 交付进度（2026-07-20）：P0 与 P1 已在 0.8.4-0.8.7 完成；P2-1/P2-2 已在 0.8.8 完成；P2-3 已在 0.8.9 完成。P2-4 模板 V2 的既有范围已完成，后续“模板版本升级预览”保留为非阻塞增强项。

## 一、产品边界与设计原则

学习项目模块采用“双空间、一条知识化管道”：

```text
项目工作空间（人开展项目）
        ↓
资料扫描与研究暂存
        ↓
筛选、治理与正式资产晋升
        ↓
项目原始资料库
        ↓
Agent 消化与 LLM Wiki 知识空间
        ↓
知识审核、个人成长证据确认
        ↓
项目归档与成长模型发布
```

- 项目工作空间按学生、教师的实际工作习惯组织，目录可自定义，也可原地绑定已有文件夹。
- 项目知识空间统一使用 LLM Wiki schema，包括原始资料库、概念库、实体库、摘要库、问答精华库、综合汇总库、项目报告和知识贡献。
- 项目原始资料库是经过筛选的知识来源集合，不是工作空间的完整副本。
- 文件资产、知识资产和成长证据必须保留来源、版本、审核状态和操作记录。
- Agent 只生成建议和回执；高风险归档、发布、路径变更必须经过人工确认和统一任务中心。
- 删除项目默认只移除项目记录，不删除工作空间、知识空间或正式资产。
- 路径迁移遵循“登记接管、原地兼容、按需迁移”，不在接管时批量移动或覆盖文件。

## 二、当前已完成的能力

- 新建学习项目，同时创建或绑定项目工作空间，并生成独立项目知识空间。
- 工作空间文件夹可按模板生成，也可在创建时自定义。
- 项目根目录、工作空间、原始资料库和知识空间可直接打开。
- 项目可编辑、复制、导入导出、重新定位、安全删除和恢复记录。
- 支持研究暂存、重复治理、AI 初筛文件导入、三种保存策略和正式资产晋升。
- 支持人工复制 Agent 消化指令、统一任务中心、消化回执同步和知识覆盖审计。
- 支持概念、实体、摘要、问答和综合知识审核。
- 支持多学生项目、每名学生独立成长证据、知识贡献清单、归档、发布和安全回滚标记。
- 支持跨项目知识关联、项目模板 V2、自动化触发和项目仪表盘。

以上能力构成现行功能基础，但不代表所有链路已经达到数据一致性和低操作负担要求。

## 三、当前主要问题

### 1. 数据一致性风险

- 消化指令生成与批次登记顺序不一致，Agent 可能收到旧批次或占位批次。
- 消化同步允许缺失批次或缺失逐文件回执，可能把未确认文件标为已消化。
- “复用正式资产”实际复制文件，且项目资产 ID 与新生成资产 ID 可能不一致。
- 缺少来源映射的知识记录会默认关联项目全部资产，形成错误溯源。
- 知识审核记录依赖物理路径，重新定位或接管知识库后可能丢失审核身份。
- 发布成长模型的后端入口没有重新执行完整归档闸门，项目状态可能与未完成资料不一致。
- 暂存资料被拒绝后重新接受，状态恢复不完整；部分操作显示请求数量而非实际匹配数量。

### 2. 用户操作负担

- 普通用户需要理解暂存状态、审核状态、治理建议、保存策略、资产晋升、消化批次、知识审核、个人证据和任务审批等内部概念。
- 同一阶段同时出现大量主按钮、批量按钮和高级操作，缺少明确的唯一“下一步”。
- 操作反馈集中在页面底部，用户点击扫描、导入或同步后不容易看到结果。
- 资料入口分散，复用正式资产的位置与工作流顺序不一致。
- 归档任务需要切换任务中心审批，完成后缺少返回原项目和自动刷新的连续体验。

### 3. 扫描与迁移能力不足

- 使用已有项目文件夹创建项目后，不会默认执行首次扫描。
- 大型工作空间扫描同步计算全部文件哈希，可能阻塞界面；达到文件上限时会静默截断。
- AI 评估回执仍以导入文件为主，不符合多数 Agent 直接返回文本的使用方式。
- 编辑项目尚不具备完整的安全工作空间重新绑定与回滚。
- 新建项目尚不能正式接管已有项目知识库。

## 四、P0：可靠性与数据一致性整改

P0 完成前，不继续扩大自动发布、批量接管和机构协作范围。

### P0-1 消化批次与逐文件回执严格化

- 将流程调整为“创建批次并冻结待处理清单 → 生成指令 → 复制指令 → 登记等待回执”。
- Agent 指令必须包含当前 `digestBatchId`、项目 ID 和逐文件 `relativePath + sha1`。
- 回执必须同时匹配项目、批次和至少一条当前提交文件；缺失批次不得完成同步。
- 禁止以整批 `submittedFiles` 代替 Agent 明确返回的 `digestedFiles`。
- 支持部分成功：已确认文件进入 manifest，失败或未回执文件继续待处理。
- 空批次不得创建任务；重复回执保持幂等。

验收标准：旧批次、空回执、错误项目和无逐文件结果均不能改变消化状态；部分回执只更新对应文件。

### P0-2 正式资产复用与引用关系修复

- 将“复用已有正式资产”改为默认建立引用，不复制物理文件。
- 需要独立副本时提供明确的“创建项目副本”动作，并生成版本关系。
- 项目 `assetIds` 只写入成功建立关系的真实资产 ID；失败和跳过项不得写入。
- 对现有项目执行只读一致性审计，识别原资产 ID、新副本 ID、缺失文件和孤立引用。
- 提供可回滚的数据修复脚本，不自动删除重复文件。

验收标准：引用模式不新增物理副本；复制模式能追溯原资产；项目资产索引与资产中心完全一致。

### P0-3 知识来源与稳定身份修复

- 每条知识记录使用稳定 `knowledge_id`，不再仅由物理路径生成身份。
- 来源必须来自 Agent 回执、知识文件 frontmatter 或人工补充；无来源时保持“待补充”，不得默认关联全部项目资产。
- 路径变化只更新位置，不改变知识 ID、审核状态和来源关系。
- 对历史知识记录生成来源健康报告，区分明确来源、推断来源和无来源。

验收标准：移动或重新定位知识文件后审核状态不丢失；任一知识条目不会无依据地关联项目全部资产。

### P0-4 归档、发布与状态闸门统一

- 把暂存收口、消化完成、知识审核、学生证据、冲突检查统一为一个后端闸门服务。
- 生成归档清单、执行归档和发布成长模型都必须调用同一闸门，不能只依赖界面按钮禁用。
- 已发布项目出现新增资料时，自动进入“发布后有变更”状态，不继续显示为完全完成。
- 修复“已完成但仍有待消化”“待处理为 0 但长期消化中”等状态漂移。
- 非法状态输入直接报错，不得默认切换为“进行中”。

验收标准：任何入口都不能绕过闸门；项目状态、暂存数量、消化数量和发布状态保持一致。

### P0-5 暂存审核状态机与事务性

- 定义 `collected → screened → selected → promoted/analyzed` 和 `rejected/discarded → restored` 的明确流转。
- 重新接受已拒绝资料时恢复到可晋升状态。
- “审核并晋升”采用事务：资产登记或来源记录失败时，审核状态不提前提交。
- 返回实际匹配、成功、失败和跳过数量，并列出失败原因。
- 保留每次审核、保存策略和晋升的审计记录。

验收标准：任意失败不会产生半完成状态；恢复、重试和重复执行均可预测且幂等。

## 五、P1：用户流程简化与可见反馈

### P1-1 四步主流程

普通用户主流程收敛为：

```text
1. 添加资料
2. AI 整理建议
3. 确认并消化
4. 完成项目
```

- 每一步只保留一个主按钮，其他操作放入“更多”或高级设置。
- 系统自动根据项目状态推荐下一步，不要求用户理解所有内部状态名。
- 保留专业模式，供教师、管理员查看逐文件状态和策略。

### P1-2 “整理项目资料”向导

- 合并工作空间扫描、研究暂存、初筛、治理、保存策略和晋升入口。
- 默认策略：项目原件和成果保存完整副本；网页和在线论文保存来源记录；普通参考资料默认引用；疑似重复和低可信资料等待确认。
- 用户主要处理冲突、重复、缺失来源和低置信度项目，其余可批量接受。
- 复用正式资产移动到“添加资料”阶段，与工作空间、直接导入、屏幕采集并列。

### P1-3 阶段导航与就地反馈

- 阶段卡显示工作空间文件、暂存候选、正式原始资料、待消化、待审核和待发布的真实数量。
- 扫描、导入、同步和审核结果在按钮所在板块显示，不再只显示在页面底部。
- 操作后自动定位本次新增或失败项目，并提供“查看详情”“重试”“定位文件”。
- 长操作使用进度、取消和完成通知，不阻塞页面。

### P1-4 AI 评估回执改为粘贴优先

- 主操作改为“粘贴 Agent 评估结果”，支持 JSON 和包含 JSON 的 Markdown。
- 写入前展示解析数量、匹配数量、未匹配条目、状态和策略变化预览。
- 保留“从文件导入”作为次级入口。
- 保存原始回执、解析版本、匹配依据和操作者。

### P1-5 风险知识与个人证据最小确认

- 知识审核默认只展示低置信度、缺来源、冲突和新生成内容。
- 高置信度知识可批量确认，但不能自动发布到学生档案。
- 单学生项目自动生成个人证据草稿；多学生项目只要求确认每名学生之间的差异部分。
- 没有具体来源的个人成长证据不得发布。

### P1-6 项目完成向导与任务中心返回链路

- “完成项目”一次运行闸门检查，并按严重程度展示阻塞项。
- 每个阻塞项提供可操作的定位按钮，处理后自动重新检查。
- 高风险写入继续进入统一任务中心；任务批准或完成后自动返回项目、刷新状态并展示结果。
- 归档确认清单默认采用系统建议，用户只需处理冲突项。

验收标准：普通单学生项目可以在四个主步骤内完成；没有风险时无需逐项勾选知识和资产；任何失败都能在当前步骤看到原因。

## 六、P2：扫描、路径与既有知识库接管

### P2-1 异步增量扫描与首次扫描

- 新建项目选择已有工作空间时，默认勾选“创建后立即扫描已有资料”。
- 首次扫描只登记研究暂存候选，不自动晋升、不启动消化。
- 使用目录快照、大小和修改时间先筛选变化，再对新增或变化文件计算哈希。
- 扫描改为异步任务，支持进度、取消、分批提交和明确的文件上限提示。
- 目录包含关系使用可靠的相对路径判断，避免字符串前缀误判。

### P2-2 编辑项目时安全重新绑定工作空间

- 通过目录选择器重新绑定，不允许任意文本路径。
- 检查目录存在性、读写权限、重复绑定、与知识空间重叠、Junction 越界和未完成任务。
- 变更前展示旧路径、新路径和影响范围，并暂停项目自动任务。
- 默认只更新逻辑路径映射，不移动、不复制、不删除文件。
- 保存旧路径、扫描基线和回滚记录；重新绑定后执行增量扫描。

验收标准：失败时索引保持原状；成功后新工作空间可扫描，原知识空间和旧目录不被修改。

### P2-3 新建项目时接管已有项目知识库

- 知识空间来源增加“创建新知识空间”和“接管已有知识库”。
- 接管前只读扫描 `AGENT.md`、LLM Wiki schema、`.pathmap.json`、知识空间身份、来源记录、绝对路径和未完成任务。
- 检查知识库是否被其他项目独占绑定，禁止无意并发写入。
- 保留原文件、原 ID 和目录，生成兼容映射和当前主机路径配置，不覆盖原 `AGENT.md`。
- 项目工作空间仍须单独创建或绑定，不能与知识空间合并。
- 接管前后记录文件数量、大小、路径和必要哈希，并支持取消与回滚。

验收标准：已有知识库可原地接管；跨主机旧路径可映射；重复绑定、Schema 冲突和身份冲突会阻止写入。

### P2-4 项目模板 V2 完善

- 工作空间目录预设、知识加工策略、成长与报告策略继续保持独立。
- 增加“我的工作空间模板”、模板版本、兼容范围和升级预览。
- 模板更新只补建缺失目录或更新策略，不移动、覆盖、删除已有项目资料。
- 项目复制复用模板和策略，但不复制研究资料、资产、审核状态和历史贡献。

## 七、P3：规模化与高级治理

- 多角色权限：学生、教师、家长、项目负责人和管理员。
- 机构批量项目：班级模板、批量绑定学生、批量资料治理和分级审批。
- 智能知识归一：统一概念、实体和能力名称，同时保留原始表达及来源。
- 跨项目证据聚合：同一能力需要多项目证据支撑，避免单项目结论直接升级为长期画像。
- 自动化策略：只在存在实际新增资料时创建任务；全局手动模式继续优先。
- 项目健康仪表盘：状态漂移、来源缺失、过期任务、重复资产、长期未审核和发布后变更。
- 生命周期策略：归档、封存、恢复、发布后修订和知识失效的完整审计。
- 机构级保留策略：暂存资料自动过期、敏感资料权限、审计日志导出和备份恢复演练。

## 八、开发顺序与版本建议

| 批次 | 目标 | 主要任务 | 前置条件 |
| --- | --- | --- | --- |
| A | 数据可信 | P0-1 至 P0-5 | 无 |
| B | 主流程减负 | P1-1 至 P1-3 | 批次 A |
| C | Agent 与完成闭环 | P1-4 至 P1-6 | 批次 A、B |
| D | 扫描与迁移 | P2-1、P2-2 | 批次 A |
| E | 既有知识库接管 | P2-3 | 稳定 knowledge ID、逻辑路径 |
| F | 模板与规模化 | P2-4、P3 | 批次 A 至 E |

建议按后续 Windows 版本逐步交付：

1. `0.8.4`：消化批次、资产引用、知识来源、发布闸门和暂存状态机。
2. `0.8.5`：四步主流程、资料整理向导、就地反馈和真实阶段计数。
3. `0.8.6`：急需插入的固定机器码、双向局域网发现与点击接受连接 V2；学习项目路线在 `0.8.5` 发布后暂停一版。
4. `0.8.7`：恢复学习项目路线，交付粘贴评估回执、风险知识最小审核、完成向导与任务中心返回。
5. `0.8.8`：异步扫描、首次扫描和安全重新绑定。
6. `0.8.9`：已有知识库接管、稳定身份迁移与回滚。
7. `0.8.10` 以后：模板完善、权限、机构批量能力和高级治理；再后续按版本规则进入 `0.9.1`。

版本安排可按实际修复范围合并，但不得在同一版本同时引入 P0 数据迁移和大规模界面重构，以降低回归风险。

## 九、测试与验收矩阵

### 1. 行为测试

- 新建空间、绑定已有工作空间、首次扫描、重复扫描和来源删除。
- 暂存接受、拒绝、恢复、三种保存策略、部分失败和重复执行。
- 消化空批次、部分回执、旧批次、错误批次、重复回执和文件修改后再次消化。
- 知识移动、知识空间重新定位、接管后审核状态和来源保持。
- 单学生、多学生、无学生、证据缺来源和学生证据交叉隔离。
- 归档闸门、任务审批、发布、发布后新增资料和安全回滚。

### 2. 迁移测试

- 0.7.x、0.8.1 至 0.8.3 项目记录升级。
- 跨主机绝对路径失效、逻辑路径重建和恢复备份。
- 历史项目资产 ID、知识审核记录、消化 manifest 和贡献记录修复。
- 迁移前后项目数、文件数、资产数、来源关系和哈希抽检一致。

### 3. 性能测试

- 100、1000、2000 和超过上限文件的扫描。
- 大量图片、深层目录、网络盘、慢速磁盘和不可读文件。
- 扫描、哈希和知识审核期间主界面保持可响应。

### 4. 发布闸门

- 全量自动化测试通过。
- 生产构建通过，无新增未解释的大体积依赖。
- 使用真实项目完成一次从已有工作空间到归档发布的行为级验收。
- 执行备份、升级、失败回滚和恢复演练。
- 更新版本日志、Windows 操作手册、装机检查清单和项目模块说明。

## 十、明确不纳入当前主流程的能力

- 不自动删除工作空间、知识空间或已复制到学生档案的物理文件。
- 不把项目工作空间与项目知识空间合并为一个目录。
- 不允许 Agent 未经审核直接修改学生长期事实或发布成长结论。
- 不重新绑定 Codex CLI 等单一 Agent；继续使用统一任务协议和适配器。
- 不在本轮恢复复杂知识关系图作为项目主界面功能；高级可视化继续交给 Obsidian 等工具。

## 十一、完成定义

学习项目模块达到以下条件后，才可视为闭环真正完成：

1. 普通用户能沿四步主流程完成项目，不必理解全部内部状态。
2. 每份正式资料、知识和成长证据均能追溯到明确来源及处理批次。
3. 任何 Agent、路径、任务或文件失败都不会产生“界面完成、底层未完成”的状态。
4. 已有工作空间和知识库可以安全接管、迁移、回滚并跨主机恢复。
5. 归档和发布在所有入口都执行同一套后端闸门。
6. 自动测试、行为测试、迁移测试和真实项目验收全部通过。
