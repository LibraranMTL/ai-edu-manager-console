# LLM Wiki Engine 与 GBrain 教育场景对比

> 实测日期：2026-07-21  
> 结论适用范围：AI 教育管家当前 Windows 单机/局域网架构  
> 数据边界：十个场景全部使用虚构学生、虚构证据和稳定测试 ID

## 决策摘要

当前不应把正式知识空间从 LLM Wiki Engine 整体迁移到 GBrain。

- 继续以 **LLM Wiki Engine 作为权威数据源和默认运行引擎**：当前治理规则准确性与 GBrain 相同，运行路径更短，文件可直接审计，运维和迁移成本最低。
- 将 **GBrain 保留为可选的影子索引/图谱实验引擎**：原生图关系、时间线、MCP 和未来混合检索能力有明显价值，但需要先补齐长驻 transport、向量检索、学生隔离、备份恢复和范围去重验证。
- 数据策略继续采用“**登记接管、原地兼容、按需迁移**”：不批量移动现有知识文件，不改变业务 ID；只有通过闸门的知识对象才镜像到 GBrain。

## 对比口径

两套引擎使用同一个 `education-synthetic-v1` 数据集和十个治理场景：不可变来源、confirmed 强制证据、candidate 默认隐藏、冲突观察并存、修订历史、实体关系、学生隔离、敏感字段、纠正申诉事件、开放导出与降级读取。

这里的“准确性”是 **检索和治理规则正确性**，不是生成式回答的事实准确率。两套引擎本轮都未调用 LLM；GBrain 未配置 embeddings、reranker 或查询扩展，因此不能据此评价语义召回质量。

## 五维结论

| 维度 | 现有 LLM Wiki Engine | GBrain 0.42.63.0 | 当前判断 |
| --- | --- | --- | --- |
| 准确性 | 十场景 `10/10`；精确词、状态和 `subjectId` 过滤结果完全符合预期 | 十场景 `10/10`；相同规则通过，但 candidate、学生范围和敏感字段主要由适配层约束 | 当前持平；GBrain 的语义检索潜力尚未验证 |
| 可追溯性 | 原始来源不可变；Evidence URI/摘录、Claim 修订、事件 JSONL、Markdown/JSON 导出均可直接检查 | 原生 link、graph、timeline 和 MCP 更适合跨实体追踪；但合同级恢复仍需补充 `snapshot.json` | 图谱浏览 GBrain 更强；离线审计和可搬迁性 LLM Wiki 更简单 |
| 性能 | 十场景合计 `77.543 ms`，中位 `6.976 ms`，进程内直接读写 | 十场景合计 `108,841 ms`，中位 `9,019.5 ms`，当前每次操作启动 CLI | 当前集成路径 LLM Wiki 明显占优；不能把差距归因于 PGLite 内核 |
| 运维 | 无额外运行时和数据库；普通文件即可同步、备份、比对和恢复 | 需要 Bun、GBrain 版本、PGLite、schema migration、独立 `GBRAIN_HOME`、健康检查和备份恢复流程 | LLM Wiki 低；GBrain 中高，但自带 doctor/MCP 等专业能力 |
| 迁移成本 | 已是现行格式；正式数据迁移为零 | 需对象映射、批量导入、范围隔离、去重、计数/路径/hash 核验、回滚和重新索引 | 保持 LLM Wiki 最低；全量切换 GBrain 当前不划算 |

## 准确性

### 已验证

- 两套引擎均阻断同一来源 ID 的内容覆盖，并允许相同内容幂等导入。
- 两套引擎均拒绝无 Evidence 的 confirmed Claim。
- 默认检索均不返回 candidate；显式授权后才返回。
- 两个学生按 `subjectId` 检索没有串档；不带范围的显式跨学生检索能返回两者。
- 冲突结论可以并存，旧修订、纠正事件和监护人申诉不会被静默删除。

### 未验证

- 同义表达、错别字、跨语言和长文档语义召回。
- embeddings、ZeroEntropy reranker、LLM 查询扩展的准确率、延迟、成本与外部数据边界。
- 生成式回答是否只使用已确认知识，以及引用是否完整覆盖回答中的每一项事实。

因此，当前只能说两者在 **结构化教育治理合同** 上持平，不能说 GBrain 已比 LLM Wiki 更“聪明”。

## 可追溯性

LLM Wiki 的优势是透明：每个来源、结论、关系、事件和历史修订都能落为普通 Markdown/JSON/JSONL 文件，业务 ID 不依赖引擎。引擎停止后，资料仍可由只读模式和通用文件工具读取。

GBrain 的优势是关系探索：本轮已验证原生 link、双向图遍历、timeline，以及 stdio MCP 的 102 个工具。它更适合回答“某个项目、学生、证据和结论如何关联”一类多跳问题。

GBrain 仍有两项追溯风险：

1. 原生 Markdown 导出不足以恢复教育合同的全部结构化字段，仍需教育管家适配层补充 JSON 快照。
2. 同一 brain 内只使用 slug namespace 前缀不能证明强隔离；重复内容去重曾返回更早 namespace 的页面。正式环境必须验证 source scope、Profile 策略、缓存失效及权限层。

## 性能

| 指标 | LLM Wiki Engine | GBrain 当前 CLI 路径 |
| --- | ---: | ---: |
| 十场景通过 | 10/10 | 10/10 |
| 场景耗时合计 | 77.543 ms | 108,841 ms |
| 单场景中位数 | 6.976 ms | 9,019.5 ms |
| 单场景最慢 | 15.139 ms | 22,116 ms |

约 `1,404x` 的表面差距只说明当前接入方式不适合高频交互：LLM Wiki 是同进程调用，而 GBrain 评估适配器为每个操作启动一次 Windows CLI。下一轮应使用长驻 MCP/服务连接，分别测量冷启动、热查询、写入、图遍历和导出；在完成前，不应将当前数字宣传为两种存储内核的真实性能差异。

## 运维成本

### LLM Wiki Engine

- 依赖少：Node/Electron 进程和普通文件系统即可。
- 备份简单：知识空间可随现有同步体系复制，并可用文件 diff、计数和 hash 审计。
- 故障面小：没有独立数据库进程、schema migration 或凭据配置。
- 能力上限也较低：当前搜索是内存中的精确子串扫描，没有倒排索引、原生图查询、并发控制和语义召回。

### GBrain

- 新增 Bun、GBrain、PGLite、schema 版本、独立 home、健康检查和恢复演练。
- 当前 doctor 健康分为 `70`（warnings），连接和 schema v124 正常；生产就绪仍需解释并清零关键 warning。
- 独立实例能提高测试和学生范围隔离，但会增加容量、升级、备份和巡检工作。
- MCP、doctor、schema migration 和图谱工具可减少后期自研成本；只有在这些能力被产品真正使用时，额外运维才有回报。

## 迁移成本

以下为基于当前代码和已完成适配器的工程量估算，不是承诺工期：

| 路径 | 数据迁移 | 增量工程量 | 风险 |
| --- | --- | ---: | --- |
| 保持 LLM Wiki 默认 | 0 | 约 1–2 工程日：补备份/恢复与规模性能基线 | 低 |
| LLM Wiki 权威源 + GBrain 影子索引 | 不移动原文件，仅按需镜像 | 约 4–8 工程日：长驻 transport、增量同步、核验、熔断回退 | 中 |
| 全量切换 GBrain | 全量登记、映射、导入、核验与切换 | 约 7–14 工程日，另加真实数据清洗和权限验收 | 高 |

全量切换的主要成本不是“复制 Markdown”，而是证明迁移前后等价：

1. 清点 Profile、KnowledgeSpace、来源、Claim、Evidence、关系、事件和历史修订。
2. 保留稳定业务 ID 和逻辑路径，建立旧路径到 GBrain slug/page 的映射。
3. 先写影子索引，不切换读取；按对象类型核对数量、路径和内容 hash。
4. 对 candidate、敏感字段和跨学生查询做零泄漏验证。
5. 只有核验全部通过才切换索引；失败时删除影子绑定并继续读取原地 LLM Wiki 文件。

## 建议的下一步闸门

GBrain 进入正式可选后端前，至少满足：

- 长驻 transport 的热查询和写入基准达到平板交互要求，且进程重启能自动恢复。
- 使用同一批教育问句完成关键字与向量/混合检索盲测，并单独报告命中率、引用完整率、P95 延迟和外部调用成本。
- 跨学生、candidate、敏感字段和撤销授权测试均为零泄漏。
- 完成一次从备份恢复到空实例的演练，来源、Claim、关系、事件数量及 hash 全部相符。
- 断开或禁用 GBrain 后，应用自动回退到 LLM Wiki，只读和导出能力不受影响。

## 复现

```powershell
node scripts/compare-knowledge-engines.cjs
```

该命令仅用于重现已搁置的历史对比，不属于默认安装、测试或发布流程。脚本读取最近一次隔离 GBrain 实测结果，再在新的忽略目录中运行同一十场景的 LLM Wiki Engine。机器可读结果位于：

- `.gbrain-evaluation/comparisons/latest.json`
- `.gbrain-evaluation/comparisons/<runId>/comparison.json`
