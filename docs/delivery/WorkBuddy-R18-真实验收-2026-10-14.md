# WorkBuddy R18 真实验收记录

日期：2026-10-14。基线：R17；R18 只增加 WorkBuddy 首次后台响应的有界等待修复，并保留 R17 的统一调度、官方登录和桌面交接修复。

## 最终结论

三条 WorkBuddy 路径均已使用合成资料完成真实验收：

1. **后台授权：通过。** 官方 CLI 2.164.0 的本机 password-protected 登录接口完成授权回调；后续包内受控探测返回 `authorized=true`。没有读取、复制或记录登录凭据。
2. **后台直接执行：通过。** R18 包内运行时采用 WorkBuddy-only 策略，受控资格检查通过，实际执行合成资料消化，调度阶段为 `accepted`；宿主提交知识结果，`processedVersion=1`，原始文件内容不变。没有调用备用 Codex。
3. **桌面手工交接：通过。** 生产 `main` 交接函数实际打开 WorkBuddy 5.7.7，完整预填合成任务、回执路径及协议 1.2 执行身份；人工发送后 WorkBuddy 写回“合成验收通过，平均值25”。真实 Worker 与生产消费函数校验任务 ID、执行批次和 Agent，归档回执，并把任务从 `waiting_result` 更新为 `reviewing`。

这些验收不使用真实学生资料，也没有修改真实学生/项目授权。桌面传输测试只验证任务交接、回执身份和入库，不替代逐文件消化的业务证据校验。

## 发现并修复的问题

- R16/R17 的隐藏 `/login` 在 stdout 非 TTY 时被官方 CLI 自动切为 print 模式，实际未进入登录。现改用官方 CLI 的本机登录接口：只绑定 `127.0.0.1`，随机临时端口和 32 字节临时密码，强制 password 认证，并仅允许 `https://www.workbuddy.cn/login`。
- WorkBuddy 完成首次登录后，第一次受控响应实测超过旧的 12 秒探测阈值，导致“已登录仍显示未认证”。R18 将生产探测上限调整为 30 秒；进程停止确认、未知执行禁止备用重派等安全规则不变。
- 桌面交接的包写入、深链生成或进程启动失败会持久化为 `failed`，不会假停留在“等待结果”。
- 结果格式化保留宿主产生的 `handoffState` 与 `requiresUserAction`，但不信任 Agent 自报这些控制状态；有效回执到达后清除待发送状态。

## 交付边界

- 候选包未安装、未上传、未修改正式版本清单。
- 本轮后台执行使用合成教学文本；桌面往返使用合成数列 20、25、30。
- 登录由用户本人在官方页面完成；自动化没有操作认证表单、密码或验证码。
- 后台登录可在本机复用，但学生与项目资料授权仍必须在“Agent 接入与调度中心”分别保存。
- 直接执行成功不扩大 WorkBuddy 工具权限；仍使用无工具、无外部 MCP、无插件/Hook 的受控资格探测，以及宿主验证后提交。

详细机器证据保存在候选目录的 `evidence` 子目录，产物大小、SHA-256、签名状态和验收布尔值见 `artifact-verification.json`。
