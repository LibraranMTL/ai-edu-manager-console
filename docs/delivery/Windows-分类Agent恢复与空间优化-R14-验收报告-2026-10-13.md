# Windows 分类 Agent 恢复与空间优化 R14 验收报告

日期：2026-10-13。Windows 0.21.1 开发候选，标签 `smart-material-agent-recovery-r14-20261013`。R14 取代 R13/R13b/R13c/R13d。

## 用户反馈与根因

- WorkBuddy 重新授权要求选择 CLI 目录或 JSON，原因是旧流程把产品缺失的完整 CLI 转嫁给用户处理。
- 新资料显示 WorkBuddy 未认证而备用未接管，实际检查发现该学生尚未开启备用；已有配置开启备用的学生不应再等到用户刷新后才恢复。
- 84条历史记录被标成 `LEGACY_AGENT_BLOCKED / legacy_unknown`。其中错误文案能够精确证明失败发生在资格阶段、正文尚未发送，R13 将其全部视作未知执行过于保守。
- 用户随后确认新资料手工投递成功，证明受管导入器、目标验证和登记回执链路可用，故障集中在 Agent 资格、恢复和状态迁移。
- 专用中转来源投递后又在来源的“已投递”目录保留副本，同时还可能保留内部快照，造成不必要的多份占用。

以上真实状态仅作只读诊断；开发过程没有修改当前正式用户资料或安装候选包。

## 修复结果

### 普通用户授权与备用恢复

- WorkBuddy 授权改为“自动准备并授权”：应用下载固定的官方 `@tencent-ai/codebuddy-code` 2.164.0 包至应用管理的持久认证目录，验证 npm 官方元数据、SHA-512、包名、版本、入口及压缩路径后启动官方登录。不再要求用户上传 JSON 或选择 CLI 文件夹，不全局安装，不覆盖 WorkBuddy 桌面配置。
- 登录、资格校验和实际分类共用同一持久配置。登录或备用策略变化会使失败缓存失效并唤醒符合条件的技术阻塞任务。
- 应用启动时会恢复已明确开启备用的学生任务；没有授权备用的学生仍保持单主 Agent，避免静默把资料提交给其他服务。
- 真实包内验证使用实际持久认证描述：WorkBuddy 在资格阶段返回认证失败、尚未发送学生正文，Codex 备用资格与分类成功，宿主通过实际任务中心校验并登记；未变化重扫没有新增 Agent 调用。

### 历史记录与手工投递

- 精确命中旧版“后台未取得有效认证”等资格阶段错误的记录，迁移为 `not_sent` 且可恢复；迁移前逐条备份。无法证明发送阶段的其他旧记录仍保持“执行待核对”，不会自动重派。
- 在正式状态的只读副本中，84条旧记录均被安全恢复为可处理状态，未知执行计数从84降为0；该迁移将在运行 R14 时才作用于正式状态。
- 手工投递继续绕开 Agent，但仍执行学生权限、目标、版本、哈希和回执验证。投递后保留 Agent 尝试审计；已投递纠正使用已登记的不可变受管原件，不依赖已经释放的临时快照。

### 单副本存储

- 专用下载/中转来源选择“投递后清理”时，宿主先验证登记回执和内容哈希，再删除中转原件；不再建立来源目录下的“已投递”副本。
- 所有成功投递记录释放内部固定快照；“原件”按钮改为打开已验证的受管登记原件。
- Documents、图库等普通“保留原件”来源仍保留用户原件，不因空间优化而删除。
- 历史重复副本启动时一次性迁移：只清理收件箱快照目录和专用来源的“已投递”目录内、与登记原件 SHA-256 一致的普通文件。路径越界、链接、哈希不一致、回执失效或文件变化均跳过；迁移前保存记录备份。
