# 屏幕采集“消化优先”与双报告闭环修改方案

> 历史方案：后续 P1 实施与验收以《Windows-0.17.9-屏幕采集消化优先与双报告-P1优化实施方案.md》为准；本文件保留此前决策与代码实施记录。
> 方案日期：2026-09-12
> 状态：P1-R1 已完成代码级改造；P1-R2/R3 已形成回执校验与本地投影骨架。2026-09-12 调整 R2 验收口径：不再要求证明模型内部逐图关注过程，改为系统可核验的图片交付/工具读取记录与逐段回执；受控附件接入、局部 OCR 后备和真机验收仍未完成，不可作为正式发布完成声明。
> 范围：Windows 主机端、Windows 学生端的已授权屏幕采集；不改变其他原始资料的 AGENT.md 消化规则。

## 1. 变更结论

采集结束后不再要求预先完成 OCR、候选主题和候选摘要，才允许资料晋升。采集只写不可变的时间、来源、归属、顺序、图片哈希和受管文件引用；结束后用非 OCR 规则选择少量代表性截图，自动晋升为一个受控会话资料包。具备视觉能力的 Agent 在同一次正式消化中，遵循学生或项目现有 AGENT.md 的知识规则，同时返回带证据引用的活动观察。系统再从该回执分别生成：

1. 学习时间线报告：回答“这段时间实际看到了什么、尝试了什么、遇到什么阻碍、如何变化、形成什么产出”，并由活动段逐级组成会话回顾、当日回顾和每周变化概览；每层均可返回原始证据。
2. 按时间统计的学习行为报告：按小时、日期和周汇总**可观察的屏幕活动**，计数和时间归属由程序计算，解释文本可以引用已校验的 Agent 观察。

正常模式下，“采集结束 → 晋升 → 消化 → 两份报告”自动执行，不增设逐次确认。人工“晋升/重试”只保留为诊断与补救入口。若用户主动关闭任务自动化，尊重该选择，界面明确显示待手动消化；不得暗中启动 Agent。

这两份报告是学习过程档案，不自动等同于已发布学情报告，也不把屏幕画面推断为专注程度、能力掌握或正式成绩。现有学情报告只在符合其证据规则时引用已形成的知识资产和活动证据。

## 2. 现状与必须改动的原因

| 当前链路 | 问题 | 本次修改 |
| --- | --- | --- |
| `capture-timeline-worker.cjs` 先对关键帧运行 Windows OCR，再调用 `buildSegments`、`buildMemory` | 主题、分类和摘要主要来自 OCR 文字片段；页面操作与学习变化难以从截断文本恢复 | OCR 从必经前置步骤改为局部、按需回退；消化后的视觉观察成为正式时间线的主要内容 |
| `bundleMarkdown` 列出“可选视觉复核批次”和首段回执示例 | 列出图片不等于图片已交给视觉模型；首段示例容易导致其余段缺结果 | 适配器记录受控图片作为附件成功交付或由受控工具实际打开的事实，不要求不可取得的模型内部逐图注意力证明；回执按全部可处理活动段输出，缺段只标记该段待补齐 |
| 时间线 Worker 与正式消化分别进入不同调度路径 | 互相让出只覆盖部分场景，不能证明全局 OCR/视觉/消化并发满足同一预算 | 建立共享重任务资源许可与队列状态；同一学生的采集资料包不得并行消化 |
| `taskAutomationEnabled()` 和手动执行器仍可阻止自动消化 | “自动晋升”不必然等于“自动出报告” | 自动执行器可用时零点击；仅手动模式/缺授权时给出清楚状态，不谎称已自动完成 |

保留现有采集事件 JSONL、按学生/日期分页、去重、来源安全排除、会话 ID、源哈希、学生/项目隔离、有限关键帧、正式知识回执校验和跨午夜原始时间。旧 P1 缩略图及 OCR 候选结果可供历史兼容查看，但不再作为“有价值的时间线报告”验收依据。

## 3. 新的端到端流程

```text
已授权连续采集
  → 会话结束与远端送达确认（事实层可立即查看）
  → 冻结会话清单：学生/项目、时间、来源、顺序、图片哈希
  → 按时间覆盖、差异和重点标记非 OCR 选帧；最多 20 张/会话
  → 自动晋升一个会话资料包；视觉请求最多 8 张/批
  → 仅在已授权范围内关联 Agent 会话、课程任务及已有知识成果
  → 取得共享后台资源许可与执行器能力
  → 同一次 AGENT.md 正式消化：知识结果 + 逐段视觉及多源观察
  → 校验学生、批次、事件、哈希、知识目标及图片交付/工具读取记录
  → 分别投影知识资产、分层时间线报告、时间统计报告
  → 独立发布已成功部分；失败单元后台恢复
```

会话结束后、正式消化前，UI 只显示“采集事实/待消化”和可展开证据，不用截图序列或 OCR 片段冒充完成的时间线。正常采集使用既有授权范围和学生/项目归属；无法确认归属或授权失效时仅暂停该会话，不阻塞其他会话。

### 3.1 非 OCR 选帧与资料包

- 初分段使用采集时间间隔、已脱敏的来源变化、画面差异、课程边界和重点标记；不读取 OCR 文本，也不在 Electron 主进程解码所有原图。
- 每段优先保留起点、明显变化、重点和终点中的 1～3 张；全会话最多 20 张。长会话须保证跨时间段覆盖，不能只取开头 20 张。
- 一份资料包包含 `studentId`、`projectId`、`captureSessionId`、`bundleId`、`capturePolicyVersion`、`selectionVersion`、采集时间、采样间隔、来源、每张 `eventId/sequence/capturedAt/hashAlgorithm/contentHash`、候选活动边界和受管图片引用。清单与关键图共同构成消化输入；不能只把 Markdown 文件名传给 Agent 后假定它会看图。
- 非关键截图保留在受控候选区，按现有保留策略处理；正式知识引用的关键图和源哈希继续受引用保护。已经晋升的旧会话按原会话 ID 和哈希聚合，不能重复复制、提交或消化。

### 3.2 视觉能力与 OCR 回退

执行前检测当前授权执行器是否支持读取本机受管图片或显式图片附件，并核对其处理位置（本机/外部服务）是否落在用户已经授权的范围内。既有“允许截屏采集”不自动等于“允许把截图交给外部视觉服务”；缺少后一项授权时只使用已获授权的本机能力，若用户选择外部服务再一次性确认范围，不为每个会话重复弹窗。能力探测应使用有效尺寸的内部测试图，不读取学生数据；按执行器版本、模型与处理位置缓存探测结果，能力变化或连续失败时重新探测，不对每张学生截图重复探测。

**放宽的是模型内部的逐图注意力证明，不是输入交付证明。**适配器在发起每个受控子批时，须独立于 Agent 自述记录 `requestId/bundleId/digestBatchId`、处理位置、提交的 `eventId/contentHash`、附件或受控工具读取方式及成功/失败状态。只有附件被接口接受，或受控工具确实打开对应图片，才算“图片已交付”；仅在 Markdown 中列出路径、命令行提示里出现文件名、模型声明 `viewedEventIds`，都不算。该记录只能证明图片进入可供视觉处理的输入，不能证明模型内部关注了每张图，也不能证明模型的解释正确；界面和报告不得写成“已客观核实”。

- 视觉可用：分批读取代表图，结合时间清单理解活动；单次模型输入最多 8 张。一次逻辑消化批次可以包含多个受控子批，所有子批沿用同一个 `bundleId/digestBatchId`。
- **可发布的视觉观察**：同学生/项目、同批次的图片交付记录与冻结哈希匹配；回执逐段引用实际交付的 `eventId`，给出具体观察、可打开的证据及不确定性，校验通过后进入时间线，标为“视觉观察”。如称“两张图之间发生变化”，所引用的前后图都必须已交付或有其他可核验来源。受控工具的逐图打开轨迹可作为更强审计记录，但不作为所有适配器的必备门槛。低置信度、内容空泛或引用不匹配的段仍为候选。
- **未交付或交付失败**：仅有路径、Agent 自述或能力探测通过时，不形成视觉结论；该段自动尝试局部 OCR 或其他已授权来源，其他段照常完成。不存在“模型说看过就算看过”的降级通道。
- **局部 OCR 后备**：对附件交付失败、视觉能力不可用、关键文字难辨或精确题文确有必要的代表图，在独立 Worker 中按需 OCR；复用学生+图片哈希+策略版本缓存，并受同一后台资源预算约束。OCR 文本须附对应 `eventId/hash`，可以补充主题、题文和文字证据，但单靠 OCR 不推断画面操作、学习动机或两帧之间的持续行为；不得退回“全截图 OCR 后才可晋升/消化”。
- 个别图片模糊且 OCR 也无法辨认时保留未知；不要以 OCR 必定能修复视觉失败为前提，也不为补齐一张图重复处理整批。
- 既无可靠视觉也无可用 OCR：保留事实层和已成功的知识部分，相关活动段标记“证据不足/待后台恢复”；不得生成具体学习结论或要求普通用户反复点重试。
- 对现有仅手动执行器，尊重仅手动模式。它无法完成无人值守自动报告，应显示“待执行器处理”而不是“生成失败”。如要提供零点击体验，需要先配置已授权的自动视觉执行器；不能绕过授权换用别的 Agent。

### 3.3 一次消化、三个可独立成功的结果

在学生或项目现有 AGENT.md 规则之后追加**本批受控任务契约**，不覆盖 AGENT.md，也不放宽其来源与知识治理要求。一次逻辑消化返回：

1. 原有逐文件消化回执和常规知识成果；
2. `timelineObservations[]`：逐活动段记录观察到的尝试、阻碍、变化、产出、证据类型及置信度；若要解释“为什么”，必须有明确的会话陈述、任务说明或其他可核验来源，不能从画面变化推断动机；
3. `behaviorLabels[]`：仅对有证据的活动段给出有限类别，例如阅读、练习、订正、写作/创作、编程、Agent 辅助、其他/未知。

Agent **不负责**填写最终统计数字、有效学习时长、注意力或能力分数。图片路径、绝对磁盘路径和私人窗口名称不写入最终报告；报告只引用受管 `eventId/assetId` 或经授权验证的 Agent 会话、课程任务和知识成果 ID。同一批结果内一项知识规则失败不抹掉合法的时间线观察，一项时间线观察失败也不回滚正式知识。

为弥补截图无法说明学习意图和 Agent 具体操作的问题，P1-R2 复用**已有且明确授权**的 Codex、QClaw、WorkBuddy 等 Agent 会话，以及课程任务、作业或知识成果的受控元数据；不因此新增私聊抓取或扩大屏幕采集范围。关联前先按 `studentId/projectId` 校验归属，再按时间范围和来源 ID 形成候选关系；**只有时间相近不足以证明同一学习活动或因果关系**。消化回执可引用系统提供的候选来源 ID，接收端逐项核验。本系统为消化或总结而生成的 Agent 会话必须带内部任务标记，并从多源输入中排除，防止重复采集自身结果形成反馈循环。无法确认的来源保持“未关联”，屏幕活动仍可独立形成事实和候选观察。

## 4. 回执与报告数据契约

建议新增 `edu-manager.capture-digest-observation.v2` 扩展字段，仍使用既有正式消化批次和回执文件。关键形态如下；实际时间由系统根据 `sourceEventIds` 回填，Agent 不可自行改写：

```json
{
  "studentId": "student-...",
  "captureSessionId": "capture-...",
  "bundleId": "capture-bundle-...",
  "digestBatchId": "digest-...",
  "timelineObservations": [
    {
      "sourceEventIds": ["event-1", "event-2"],
      "sourceHashes": {"event-1": "已登记的图片哈希"},
      "viewedEventIds": ["event-1"],
      "activityType": "practice",
      "topic": "二次函数应用题",
      "observedAction": "查看题目并修改解题步骤",
      "attempts": ["调整解题步骤"],
      "obstacle": "未能从当前画面确认具体卡点",
      "observedOutcome": "保存了一版解答",
      "difficultyOrChange": "第二次截图显示步骤已调整；原因无法确认",
      "reason": null,
      "reasonEvidenceRefs": [],
      "evidenceRefs": [{"sourceType": "capture_event", "sourceId": "event-1"}],
      "confidence": 0.76,
      "knowledgeAssetIds": []
    }
  ]
}
```

接收端逐段校验学生、项目、会话、批次、事件是否属于本段、来源哈希、受控图片范围、**系统侧附件交付/受控工具读取记录**或 OCR 来源、其他来源的授权和归属、知识资产 ID。`viewedEventIds` 仍可用于 Agent 指明观察依据，但只是自述，不能替代系统侧记录。受信任的输入记录由适配器写入，不由 Agent 回执填写；接收端从中派生 `visualEvidenceMethod = attachment_delivered | tool_read_confirmed | local_ocr | none` 与本段实际可用的 `eventId` 集合。`attachment_delivered`/`tool_read_confirmed` 且逐段内容与引用校验通过时，可标为“视觉观察”；`local_ocr` 只能支持其识别到的文字及相应有限标签，不得升级成画面操作结论；`none` 或仅有路径/自述时维持候选或未知。旧版 `verifiedImageReadEventIds` 只能承载真实受控工具读取证据，不能用 Agent 声明或附件清单伪造填充；实现时应增加独立的系统交付记录字段，避免改变旧字段语义。

`evidenceRefs` 允许 `capture_event`、`agent_session`、`course_task`、`knowledge_asset` 等受控类型，但后面三类必须在当前学生/项目授权清单内。有独立授权会话/任务证据的观察可按该来源校验，不因截图未交付而声称获得了视觉确认。`reason` 非空时必须在 `reasonEvidenceRefs` 中引用能直接支持原因的授权来源，否则将原因降为“无法确认”，但不隔离其他合法观察。缺失、无效、空泛或低置信度段显示“待补齐/候选观察”，其他段照常入库。已成功处理的段与知识资产以稳定键去重；重复回执不得重复生成报告或知识链接。时间线中的“视觉观察”与按 AGENT.md 形成的正式知识分开治理；放宽输入证明不自动放宽知识发布门槛。

### 4.1 学习时间线报告

默认以活动段而非截图为单位，逐段展示系统确定的起止时间、主题、已观察的尝试、阻碍、变化、产出、证据图、授权 Agent 会话/任务引用、知识资产关系、置信度和处理状态。报告按“活动段 → 会话回顾 → 当日回顾 → 每周变化概览”分层投影：上层只压缩已校验的下层结果，不再为同一证据重复调用 Agent；每条概括均能逐级下钻到活动段和受控证据。未完成但有证据的尝试可以保留，不能只记录最终成果；无归属或无足够证据的内容明确标记“未关联/无法判断”。日、周聚合不得跨学生、跨项目混用。只有已校验消化结果能使用“已形成知识”，其余保留事实层或候选状态。

### 4.2 按时间统计的学习行为报告

统计引擎读取**不可变采集事件和已校验活动标签**，按本机所设时区将跨午夜活动拆入对应日期，再按小时、日、周增量汇总。建议输出：会话数、有效截图数、代表图数、已分类/未知活动段数、按类别和时间桶的活动段数、重点标记数、涉及主题与证据链接、未观察到的时间空隙、来源覆盖情况。重复采集、重试或跨设备补传只按稳定 `eventId` 计一次。

“会话起止跨度”和“采样覆盖窗口”只能作为采集范围；截图无法证明两帧之间持续学习。因此第一版**不输出‘有效学习时长’、‘专注时长’或活动类型的精确分钟数**。如需时间量，单列“可观察活动时间窗估计”及采样间隔、未知空隙和不确定性；按同一会话、同一分类、相邻间隔不超过 `2 × 实际采样间隔` 的证据计算覆盖窗口，超限部分记为未知而非补时。类别占比优先按“已分类活动段数量”表示，不能伪装为学习时间占比。

报告文件和统计快照使用 `studentId + captureSessionId + digestBatchId + reportSchemaVersion`（日/周汇总另加时间桶）作为稳定键。它们是正式消化结果的可重建投影，不能变成第二套知识来源；知识引用和报告版本要能反查原始会话、活动段、事件与哈希。

## 5. 自动化与失败状态

用户端只保留原有“选择学生/项目、授权采集、开始/结束”。当任务自动化开启且授权自动执行器可用时，结束采集自动进入背景链路；可在卡片看到“等待送达 → 已入库待消化 → 视觉处理中 → 知识已生成/时间线待补齐 → 两份报告可查看”等状态，不弹日常确认框。不开自动化或只配置手动执行器时不额外催促用户，清楚说明哪一环等待人工执行。

- 远端网络失败：学生端持久化队列自动重试；主机只有确认完整接收才封存会话。
- 图片交付或识别失败：仅隔离受影响图片/活动段，自动尝试缓存、按需 OCR 或已授权的其他证据；其他图片和知识结果继续，不要求用户手动恢复普通失败。
- 某活动段无可靠观察：事实层可见，时间线该段标记未知；知识消化和统计中的其他段继续。
- 常规知识结果失败：保留有效活动观察，但不能显示已形成正式知识；自动按现有治理规则恢复。
- 时间线报告投影失败：从持久化回执后台重建，无需再次调用 Agent。
- 统计报告投影失败：从事实索引和已校验标签后台重建，不阻断时间线与知识。
- 能力/资源暂不可用：持久化待处理和下一次恢复时间；不要求用户处理普通网络、模型超时或磁盘瞬时错误。
- 归属不明、授权失效、越权或敏感内容：仅暂停受影响会话/证据，提示必要的用户决定，不静默扩大采集范围。

## 6. 运行效率约束

取消前置 OCR 预计降低采集后本机 CPU 占用，但视觉模型会增加图片传输、耗时和成本；“首份有意义报告”的完成时间不保证比当前 OCR 候选摘要更短。必须分别测 UI 响应、排队时长、模型耗时和费用。

- 采集主路径只做当前已需的截图、去重、时间/哈希登记；选帧、预览压缩、敏感内容检查、OCR 回退和大回执解析在 Worker/受控子进程进行。
- 把时间线选帧、视觉消化、普通资料消化、报告生成纳入同一资源预算。采集时视觉/OCR/AI 重任务并发为 0；普通使用最多 1；插电、持续空闲且资源充足时最多 2 个**互不依赖**任务，同一学生消化链始终串行。当前的 `externalHeavyWorkActive` 只能作为部分互斥信号，不能代替统一预算。
- 会话最多 20 张代表图，每次视觉请求最多 8 张；对图片使用受控预览尺寸和字节上限，必要时保留原图作为证据而不直接传模型。系统侧交付记录按子批增量写入，不通过额外逐图模型调用获取内部注意力证明。OCR 仅处理失败或需精确文字的代表图，相同学生、哈希、策略版本的图片仅识别一次，仍遵守采集期间重任务并发为 0 的约束。
- 统计由增量事实和回执本地投影，复杂度随本次会话事件数增长；不扫描全量历史、不新增渲染器轮询。时间线与报表首屏分页、证据图懒加载。
- 模型调用按批次记录图片数、输入/输出量、耗时、失败和缓存命中；达到资源/费用预算时自动延后或部分完成，不中断现有知识、报告和采集。

沿用原 P1 方案第 9.6 节硬门槛：前台操作响应 P95 <150ms、主进程无新增 >200ms 长任务、采集期间重任务并发 0、时间线首屏 P95 <1s、100 张截图最多 20 张代表图。新增“单次视觉请求不超过 8 张”和“统计投影不二次调用 Agent”的自动检查。低配机连续 30 分钟和双机断网恢复仍需真机验收。

## 7. 实施顺序与交付边界

| 阶段 | 代码任务 | 完成判据 |
| --- | --- | --- |
| P1-R0：基线与能力 | 记录真实会话的 OCR 耗时、内容质量、Agent 图片能力、任务调度和模型费用；设计新回执及版本 | 能区分“图片只列在资料包中”“图片已作为附件交付/被受控工具打开”和“模型自称看过”；有可比的 0.17.8/P1 候选基线 |
| P1-R1：消化优先 | 改造 `capture-timeline-worker.cjs`：停止前置 OCR，非 OCR 选帧、冻结清单、自动晋升；主机与学生端沿用原有自动送达 | 停止授权会话后无需额外点击即可形成一个幂等资料包；无视觉 Agent 时也不丢事实或卡住队列 |
| P1-R2：视觉与多源正式消化 | 给自动执行器增补图片能力、受控附件及独立的系统交付记录；AGENT.md 后附本批任务契约；将已有授权 Agent 会话、课程任务和知识成果作为可选证据关联；实现尝试/阻碍/变化/产出字段、原因的证据门槛、局部 OCR 回退、逐段回执校验和共享资源预算 | 不要求模型内部逐图注意力证明，但须验证附件交付或受控工具读取与回执引用；一个逻辑批次产出常规知识和全部可处理段的观察；仅时间相近的来源不自动归因，未授权来源不读取；原因无证据时留空；局部失败不回滚成功段、无重复识别 |
| P1-R3：分层时间线与统计投影 | 新增活动段→会话→日→周的时间线回顾、小时/日/周统计投影、精确证据回链、状态 UI 和按学生分页查询 | 不额外调用 Agent 即可重建两份报告；每层概括能下钻到对应活动段和原始证据，未完成尝试不被丢弃；统计与原始事件可复算、跨午夜正确、不推断专注时长 |
| P1-R4：候选验收 | 单元/集成/性能测试、真实视觉 Agent 质量抽检、两台 Windows 设备长时采集及断网恢复、候选包审计 | 符合本节与旧方案性能门槛后才考虑签名和正式发布；本地合成测试不替代真机验收 |

首次验证采用明确授权的测试学生和一段包含阅读、练习、订正/创作的真实会话。至少检查报告是否出现**具体尝试、阻碍或变化、可打开的证据、适当的未知/不确定标记**；逐级检查会话、日、周回顾能回到原始活动段。另设“图片实际交付但无内部逐图轨迹”“仅列路径或模型自称已看”“交付失败后局部 OCR”“文字过小或 OCR 失败”“错误事件 ID/哈希”“无外部视觉授权”样例：第一种可在逐段校验后形成视觉观察，其余须按证据能力降级，不得伪装视觉确认；核验局部失败不会卡住整批或触发全量 OCR。另设授权 Agent 会话和仅时间相近的无关会话两个样例：前者在身份/项目及来源均吻合时可关联，后者不得硬关联或推断原因。不能再以“形成 N 个活动段”或截图排列正确作为内容质量通过标准。抽检是发布验收，不是每次用户使用时的人工审核。

## 8. 不在本次范围内

不实施后台持续监控全部窗口、私人聊天采集、注意力评分、摄像头/麦克风监控、有效学习时长推断、自动成绩判断、旧历史全量重算或重新消化。除非另行授权，不增加上传第三方云视觉服务的隐式数据路径。
