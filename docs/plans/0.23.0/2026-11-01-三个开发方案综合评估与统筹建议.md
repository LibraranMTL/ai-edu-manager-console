# AI教育管家三个开发方案综合评估与统筹建议

日期：2026 年 11 月 1 日  
评估对象：项目总体报告、学情分析与学习模块、每周知识增长统计图

> **实施基线更新（2026-11-02）**：已授权直接以干净的 Windows `0.22.8` 内部基线启动后续功能开发，不再把正式发布标签作为 Track A/B/C 的开工前置条件。该决定不把 0.22.8 表述为已发布、已签名或已完成安装升级回滚验收；所有长时 Agent 性能、证据矩阵、安装、回滚、跨机恢复和公开更新清单核验，合并为 0.23.0 正式发布前的统一回归门槛。

## 一　执行结论

三份方案的产品方向都成立，且已经比一般开发方案更重视证据、权限、撤回、幂等和恢复。需要完善的不是“再加功能”，而是统一基线、缩小首版、冻结跨模块契约，并把试点与正式发布分开。

| 方案 | 价值 | 当前成熟度 | 主要风险 | 建议顺序 |
|---|---|---|---|---|
| 每周知识增长统计图 | 高、范围小、用户容易感知 | 接近可实施 | “首次登记”无权威账本；名称可能误导为掌握增长 | 1 |
| 学情分析与学习模块 | 最高，形成“证据—判断—行动—反馈”闭环 | 设计完整、工程量被低估 | 多端身份、跨学生权限、自动行动循环、五维被误用为总分 | 2 |
| 项目总体报告 | 高，能把项目资料转成可复核成果 | 证据架构强、整体范围过大 | 全量扫描、Agent 过度判断、个人贡献越权、归档与恢复耦合 | 3（M1 可提前预研） |

推荐交付顺序不是按业务重要性排序，而是按风险递增：先用周图验证单学生范围、截止时刻和安全导出；再用学情一期验证可撤回的证据与自动行动；最后把稳定的证据和授权契约用于项目报告的版本化生成。

## 三　建议冻结的共享契约

| 契约 | 最小含义 | 适用方案 |
|---|---|---|
| `SubjectScope` | 主体类型、主体 ID、可信学生/项目绑定、解析来源 | 三者 |
| `EvidenceRef` | 来源类型/ID、版本、内容哈希、定位、有效状态 | 学情、项目报告 |
| `AsOfCutoff` | 资料截止时刻、产品时区、输入代次 | 三者 |
| `AccessProjection` | 读者身份、用途、授权版本、允许字段 | 三者 |
| `CommitKey` | 可重复调用但只产生一次业务结果的稳定键 | 三者 |
| `Correction/Withdrawal` | 追加式更正/撤回及受影响派生项 | 学情、项目报告；周图使用来源撤回 |
| `PolicyVersion` | 统计口径、阈值或分析规则版本 | 三者 |

共享的是字段语义、错误码和测试夹具，不建议一开始就建立一个覆盖三种业务的大型通用数据库。周图、学情状态和项目报告分别保留自己的状态机、表和迁移；等两处以上出现稳定重复后再抽公共实现。

## 四　统筹后的实施路线

### Gate 0　冻结内部开发底座与夹具

1. 选定目标候选，建立干净实施工作树。
2. 记录分支、提交、工作树指纹、`package.json` 版本、数据库 schema、`app.asar`/安装包指纹、验收状态。
3. 建立两名虚构学生、一个多人项目、授权差异、撤回、迟到回执、未知执行结果和大数据量夹具。
4. 先跑现有基线测试；既有失败与新功能失败分开记录。长时性能门禁可在各 Track 集成后统一执行，且必须在正式发布前完成。

### Track A　每周知识库新增图

1. 冻结“首次登记”语义，建立可恢复的首次登记投影/账本。
2. 使用同一 `asOf`、时区、学生范围和授权版本读取资产总量与周新增。
3. 完成一张图、预览与落盘同字节、迟到响应废弃、真机手机查看。
4. 明确这不是掌握度或能力增长指标。

### Track B　学情一期 1A/1B

1. 1A：证据、目标、问题、周反馈、状态总览、更正撤回和权限投影；不依赖自动派发也能完整使用。
2. 1B：达到规则后自动创建一个可追溯行动，绑定现有任务或卡片；反馈返回同一问题。
3. 先验证单学生和多学生隔离，再开放教师/家长摘要；无可信身份绑定时不开放独立在线查看。
4. 五维不合成总分，不用于诊断、排名或纪律判断。

### Track C　项目报告 M1/M2/M3

1. M1：项目阶段摘要、逐条依据、补资料入口和只读页面；证据不足时只显示事实和待验证。
2. M2：自动/手动生成、稳定 Claim 键、版本差异、权限变化即时裁剪。
3. M3：结项快照、导出、跨机恢复和归档回执对账。
4. 项目结论不能自动写成学生知识掌握；个人贡献必须经过既有贡献确认。

## 五　统一放行门槛

以下任一项失败，暂停相应自动路径，不以“多数用例通过”放行：

1. 跨学生、跨项目或跨角色泄露正文、标题、计数、缓存、日志、导出或待传数据。
2. 页面浏览触发资料写入、贡献草稿、学习状态变更或自动任务。
3. 同一业务键产生重复任务、重复卡片、重复报告版本或重复结项快照。
4. 执行结果未知时重新派发，或迟到旧结果覆盖新代次。
5. 把知识库新增写成掌握增长，把完成行动写成知识掌握，把团队成果写成个人贡献。
6. 撤回后仍在摘要、历史、差异、原文入口、导出或云同步中泄露失效内容。
7. 新功能使原有大型项目、资产中心或任务中心超过目标候选的性能门禁。

## 七　2026-11-01 新增配套任务

四项新增要求已形成独立的《Windows 基础体验与项目新建补充开发方案》，并纳入三方案共同底座：

1. **P0 修复知识资产统计更新链。** 当前资产库健康且汇总一致，但最后一次已观察的持久化更新停在 2026-11-01 08:55；前端又缺少统一的资产变更订阅。先用受控文件区分后端漏写与页面旧快照，再用提交后事件、统计代次和幂等对账修复。每周知识增长图在该门槛通过前不得进入正式验收。
2. **首页改为五个明确入口。** 设置“本周行动建议、每日固定动作、项目进展、推荐选题、推荐比赛”。前两项共享既有周行动报告，“每日固定动作”定位到报告章节，不复制任务数据；所有入口只导航，不因浏览启动 Agent 或生成内容。
3. **启动版本检查判定为部分完成。** 现有手动检查、版本比较和 Windows 下载链接可复用，但尚缺每次启动自动检查、新版弹窗、正式/候选通道隔离、链接校验和行为测试。补齐后仍只提供受信下载链接，不静默安装。
4. **新增“作品集项目”模板。** 模板 ID 建议为 `portfolio`，文件夹严格为“参考资料、过程文档、最终成果”。前后端模板定义必须一致，只补缺失目录，不迁移或覆盖既有项目文件。
5. **P0 修复项目列表 IPC 载荷超限。** 已确认不是项目或学生关联丢失：14 个项目、23 条学生关联、3,152 条资产关联和 49,637 条暂存资料仍完整，数据库 `quick_check = ok`。根因是列表接口把完整项目 `payload_json` 带入响应，全部项目序列化为 2,098,181 bytes，超过 2 MiB 上限 1,029 bytes 后被整体拒绝，前端遂把加载失败显示为“0 个项目”。修复采用严格轻量列表投影、按 ID 详情读取、保留 IPC 上限和明确超限错误状态；不得通过提高上限、重建数据库或静默清空列表处理。

详细证据、任务拆分与验收见同目录：`2026-11-01-Windows基础体验与项目新建补充开发方案.md`。

## 八　最终建议

1. 立即采用修订后的三份方案作为设计输入，完成 Gate 0 的干净内部基线与夹具后即可开工；不直接在当前脏工作树叠加。
2. 首个可交付功能选择每周知识库新增图；它能用最小范围验证三份方案共同依赖的学生范围、截止时刻、授权变化和安全导出。
3. 学情模块坚持自动发布和自动下一步，但用 1A/1B 两道门控制风险；五维永不合成总分。
4. 项目报告坚持逐条证据和不可变版本，但把 M1 明确命名为阶段摘要，避免一张草图被包装成完整总体结论。
5. 三个模块共享契约和测试夹具，不共享未经验证的大型通用框架；每个模块都可独立关闭、迁移和回退。
6. 将知识资产统计更新修复设为 Track A 的前置门；首页、启动更新提醒和作品集模板按补充方案独立验收，不能以界面已出现替代数据对账或安装包验证。
