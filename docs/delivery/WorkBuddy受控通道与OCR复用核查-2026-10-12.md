## 1. 已完成的兼容修复

- 本机 WorkBuddy 5.7.7 自带 CLI 的实际参数是隐藏的 `--no-plugin-management`，不是此前使用的 `--no-plugin-manager`。在安装包只读源码中确认其作用是禁止插件生命周期管理，并不等于禁用所有插件加载。
- `electron/workbuddy-runtime.cjs` 新增共同受控调用构造器；授权探测和实际分类／消化调用统一复用，避免探测与正式任务权限不一致。
- 保留 `dontAsk`、空工具列表、空 MCP 配置及 strict 模式、空临时工作目录、单轮上限、无会话持久化、仅 local 设置、`disableAllHooks=true`。调用方不能通过额外目录、工具或 permissionMode 覆盖这些要求。
- 同时禁用插件安装／加载通道、内置市场、热重载、自动记忆、系统提示文件、内置子智能体、后台任务及 cron；移除继承的内联插件／会话技能目录、Node 预加载和旧会话身份，明确关闭 `CODEBUDDY_IS_SANDBOX` 权限旁路。仅变更子进程环境，不改用户环境或桌面配置。
- 授权探测超时后先请求停止并等待真实 close；未确认停止则报告 executionUnknown，而不是假定 kill 请求已经停止进程。
- 认证错误改为“后台通道未取得有效认证”，不再误称“桌面登录失效”。桌面进程或 IPC 发现文件存在不能当成后台认证成功。

## 4. OCR／AI 理解是否重复：当前实现的准确结论

| 环节 | 当前实现 | 是否重复 |
|---|---|---|
| 文档正文提取／图片 OCR | 分类复用项目提取器代码，但使用 `smart-inbox/scope-cache/<学生范围>/extraction-cache`；项目消化使用项目登记库下的 `extraction-cache`，缓存 key 还包含 projectId | **会跨阶段重复**：首次分类与首次项目消化可能各提取一次；不是已经“一次 OCR、全程复用” |
| 分类内部缓存 | 按学生或来源范围、内容 SHA-256、扩展名、提取器版本缓存；建议还核对项目上下文／规则摘要 | 同范围不变文件不重复发现后分析；相同内容可命中已有提取／建议缓存 |
| 消化内部缓存 | 按项目、内容哈希、格式、提取器版本、OCR 语言及实现环境校验缓存；批次预提取后将同一文本传给 Agent | 同项目、同版本／参数可复用，批次选择与实际执行不会各 OCR 一次；安全哈希／固定版本校验仍会执行 |
| AI 分类 | 最多使用 200 KiB 提取正文，结合授权学生和候选项目决定位置；固定目标或精确规则命中时可跳过 Agent | 未命中规则时会有一次轻量路由理解 |
| AI 消化 | 读取固定来源全文及项目规则，生成知识产物和证据来源，随后由宿主校验提交；批次正文最多 4 MiB | 通常是另一轮模型调用，和分类有部分重复阅读，但目的／合同不同，不能拿分类意见当作消化成果 |

因此，当前“复用现有提取器”指复用实现，不代表分类和消化已经共享提取结果。图片、扫描 PDF 的额外 OCR 是可优化的真实开销；普通 TXT／Office／文本 PDF 主要是重复解析，并非都在运行 OCR。分类与消化 AI 还会分别产生调用时间和额度开销，命中路由规则时可免去分类 AI。

代码核对位置：`smart-inbox-host.cjs:70` 创建收件箱独立提取范围；`smart-inbox.cjs:215` 为路由缓存与 200 KiB 上限，`:305` 为先规则后 Agent；`project-material-extract.cjs:125` 为项目隔离缓存 key；`project-material-task.cjs:167` 将预提取文本传给消化执行器。

### 后续优化建议（本次只核查，未实施）

优先建立受控的“提取结果交接”，而不是合并两种 AI 任务：投递登记成功且学生授权、内容哈希、格式、提取器版本、OCR 参数均一致时，把完整、带来源和警告的提取结果交给目标项目缓存；消化仍校验真实文件版本，参数变化或结果不完整时重新提取。不能将分类已截断的 200 KiB 文本伪装成消化全文，也不能建立跨学生无授权的全局缓存。规则命中继续跳过分类模型。
