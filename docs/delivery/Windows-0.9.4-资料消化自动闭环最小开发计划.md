# Windows 0.9.4 资料消化自动闭环最小开发计划

> 计划日期：2026-07-22  
> 开发基线：Windows 主机版 0.9.3、Android 平板终端 0.5.8  
> 计划性质：0.9.4 候选范围，先完成最小可用闭环，再进入成长模型、学情报告和档案原生访问开发  
> 核心原则：零新增外部依赖、普通用户一次操作、后台严格校验、失败可恢复、保留人工兜底  

## 一、版本目标

本版本只解决一个问题：

> 教师或家长把资料放入学生或学习项目后，只需点击一次“开始处理”，系统即可自动创建消化批次、调用现有 Agent、等待结果、校验回执、更新知识资产和处理状态；普通用户不再需要进入任务中心、复制指令、标记已提交或手动同步结果。

完成后的最短路径：

~~~text
资料进入原始资料区
        ↓
用户点击一次“开始处理”
        ↓
系统冻结待处理文件清单并选择可用 Agent
        ↓
Agent 自动消化并写入知识文件/结构化回执
        ↓
系统自动校验来源、批次、文件哈希和产物
        ↓
自动更新为“已完成”或“部分完成”
        ↓
用户查看新增知识；失败时只需点击“重试未完成项”
~~~

本版本不追求无人值守的定时消化。自动化从用户明确点击开始，避免资料刚导入就触发不可预期的处理，同时把日常操作控制在一次确认以内。

## 二、最小开发范围

### 2.1 纳入范围

1. **学生资料消化**
   - 处理学生原始资料区中尚未完成消化的文件。
   - 继续生成或更新现有 LLM Wiki 中的摘要、概念、实体、问答、综合分析、索引、日志和消化状态。
   - 为学生资料补齐与项目资料一致的批次清单、逐文件哈希和严格回执。

2. **学习项目资料消化**
   - 复用现有项目消化批次、文件哈希、严格回执和知识写入规则。
   - 把当前“复制命令—粘贴—标记提交—手工同步”改为统一的一键闭环。

3. **现有 Agent 执行通道**
   - 复用 OpenClaw 直接执行。
   - 复用 Codex 直接执行。
   - 复用 QClaw 任务收件箱。
   - 保留 ManualAdapter 作为无可用 Agent 时的降级方式。

4. **自动状态回写**
   - 自动识别直接执行结果、QClaw 收件箱结果和人工导入结果。
   - 自动完成结果校验、知识状态更新、部分完成记录和剩余项重试。
   - 应用重启后能够继续恢复未完成批次。

5. **低负担界面**
   - 学生资料页和学习项目页各提供一个主操作入口。
   - 普通用户只看到“待处理、处理中、部分完成、已完成、需要帮助”五类状态。
   - 任务 ID、执行批次、文件哈希、JSON 回执和内部审批状态只保留在诊断详情中。

### 2.2 明确不纳入范围

- 不更换现有 LLM Wiki Engine，不安装或接入 GBrain。
- 不新增技能包、数据库、Docker、Python、MCP 服务或其他常驻依赖。
- 不开发身份角色、细粒度权限、敏感信息设置和面向普通用户的审计页面。
- 不开发学生行动反馈；仍由教师或家长管理学生提交，并作为普通资料进入系统。
- 不自动更新成长模型、正式学情报告或正式教育档案。
- 不自动发布成长证据或教育结论。
- 不扩展多 Agent 智能路由；只使用现有简单优先级和降级规则。
- 不改 Android 平板端，Android 版本继续保持 0.5.8。
- 不要求旧知识库迁移目录或重写已有文件。

## 三、现有基础与关键缺口

### 3.1 可直接复用的现有能力

- 统一任务协议 v1.2、TaskEnvelope、TaskResult 和任务状态机。
- OpenClawAdapter、CodexAdapter、QClaw 收件箱和 ManualAdapter。
- 执行器不可用时自动降级到人工模式。
- 项目资料批次冻结、相对路径、SHA-1、严格回执、部分完成和 manifest 更新。
- 学生资料的提交状态、消化状态、日志、索引和结果同步。
- 任务结果身份校验、允许读写路径校验、产物路径校验和执行历史。

### 3.2 必须补齐的缺口

| 缺口 | 当前影响 | 0.9.4 处理方式 |
| --- | --- | --- |
| 学生资料缺少严格逐文件批次回执 | 可能通过日志或文件时间推断整批完成 | 建立学生 DigestBatch，并按 materialId、relativePath、sha1 逐项确认 |
| 消化入口与任务执行分离 | 用户需要复制、粘贴、标记和同步 | 增加统一 startDigestWorkflow，一次操作走完整链路 |
| QClaw/异步结果需要人工同步 | 结果已生成但页面仍显示处理中 | 后台监听或轮询，并向当前页面发送状态事件 |
| 所有成功任务都暴露人工审核 | 低风险知识消化增加无价值确认 | 消化任务机器校验通过后后台自动验收 |
| 部分失败后的重试不够直观 | 用户容易重复处理整个批次 | 只为未完成文件建立后续执行批次 |
| 应用重启后的执行恢复不统一 | 中途退出可能需要人工排查 | 启动时 reconcile 未终结的消化批次 |

## 四、目标交互

### 4.1 有可用原生 Agent

1. 页面显示“有 N 项资料待处理”。
2. 用户点击“开始处理”。
3. 系统自动选择当前已配置且健康的执行器。
4. 页面原地进入“处理中”，用户可以离开页面或关闭窗口。
5. Agent 返回结果后，系统在后台校验并应用。
6. 页面自动显示：
   - “已完成：N 项”，或
   - “已完成：X 项，剩余 Y 项需要重试”。
7. 用户点击“查看新增知识”即可进入现有知识目录或结果页面。

正常路径不出现以下操作：

- 复制消化指令。
- 打开任务中心。
- 标记“已提交”。
- 点击“同步结果”。
- 审核 JSON。
- 确认低风险知识写入。

### 4.2 没有可用原生 Agent

系统仍先建立同一份标准消化批次，然后进入人工降级卡片：

1. 自动复制完整指令，用户只需在 Agent 中粘贴一次。
2. 页面保留一个“粘贴 Agent 返回结果”区域。
3. 用户粘贴文本或 JSON 后，系统转换为统一 TaskResult，并执行同样的严格校验与状态回写。
4. 用户不需要手工修改文件状态，也不需要进入任务中心。

人工模式目标不是零操作，而是保持“一次复制、一次粘贴、无技术配置”。

### 4.3 异常路径

- Agent 暂时离线：显示“等待 Agent”，后台自动重试连接，不反复弹窗。
- Agent 执行失败：显示简短原因和“重试未完成项”。
- 回执不完整：已确认文件仍记为完成，只重试未确认文件。
- 回执身份或哈希错误：不应用结果，显示“结果无法匹配本批资料”，详细信息进入诊断记录。
- 输出文件缺失：不标记完成。
- 用户关闭应用：重新打开后自动继续检查原执行，不重复建立批次。

## 五、统一消化批次协议

### 5.1 DigestBatch v1

新增内部标准对象 DigestBatch，用于统一学生和项目资料消化。建议持久化结构如下：

~~~json
{
  "schema": "edu-manager.digest-batch.v1",
  "batchId": "digest-...",
  "scope": {
    "type": "student",
    "id": "student-id",
    "name": "学生名称"
  },
  "createdAt": "ISO-8601",
  "files": [
    {
      "materialId": "stable-material-id",
      "relativePath": "原始资料/文件名.pdf",
      "sha1": "...",
      "size": 12345
    }
  ],
  "output": {
    "knowledgeRoot": "...",
    "receiptPath": "..."
  },
  "status": "prepared",
  "idempotencyKey": "scope-id + sorted file hashes"
}
~~~

约束：

- 批次建立后，文件列表和哈希不可原地修改。
- 新增或被修改的文件进入新批次。
- 空批次不得提交给 Agent。
- 同一 scope 和同一组文件哈希不得创建并行重复任务。
- 路径使用相对于知识库根目录的逻辑路径保存；当前主机绝对路径只在执行时解析。

### 5.2 TaskEnvelope 扩展

不升级现有任务协议主版本，只增加向后兼容的可选字段：

- digestBatchId
- manifestPath
- scope
- completionPolicy
- requiredArtifacts

学生和项目消化任务设置：

~~~text
completionPolicy = auto_after_validation
~~~

其他高风险或正式发布类任务仍保持 manual_review。现有状态机不删除 reviewing，而是在机器校验通过后由系统内部立即完成：

~~~text
waiting_result → reviewing → succeeded
~~~

reviewing 是后台技术状态，不向普通用户要求确认。

### 5.3 DigestResult v1

Agent 返回结果经适配器归一化后至少包含：

~~~json
{
  "protocolVersion": "1.2",
  "taskId": "...",
  "executionId": "...",
  "digestBatchId": "...",
  "status": "completed",
  "processed": [
    {
      "materialId": "...",
      "relativePath": "...",
      "sha1": "...",
      "artifacts": ["学情分析汇总/摘要/...md"]
    }
  ],
  "failed": [],
  "artifacts": [
    {
      "path": "...",
      "type": "summary",
      "sourceMaterialIds": ["..."]
    }
  ]
}
~~~

项目现有 digestedFiles 回执继续兼容，由结果归一化层转换为 processed。旧学生知识库仍可使用现有 digest-state、log 和 index 作为兼容性提示，但新批次不得仅凭文件修改时间推断全部完成。

## 六、状态模型

### 6.1 内部状态

~~~text
prepared
  → submitted
  → queued / running / waiting_result
  → validating
  → completed / partial / failed / timed_out / cancelled
~~~

内部任务状态继续使用统一任务协议现有状态机；DigestBatch 状态只负责表达资料处理业务进度。

### 6.2 普通用户状态映射

| 用户看到的状态 | 对应内部状态 | 用户主要操作 |
| --- | --- | --- |
| 待处理 | 无批次、prepared | 开始处理 |
| 处理中 | submitted、queued、running、waiting_result、validating | 无需操作 |
| 部分完成 | partial | 重试未完成项、查看已完成结果 |
| 已完成 | completed | 查看新增知识 |
| 需要帮助 | failed、timed_out 或结果无法匹配 | 重试；展开帮助信息 |

“审批、权限、执行批次、幂等键、哈希、回执校验”等术语不出现在普通视图。

## 七、功能设计

### F1. 统一批次创建

- 扫描当前 scope 中所有待处理资料。
- 读取稳定 materialId；旧记录缺失时补建，不更改原文件。
- 计算相对路径、大小和 SHA-1。
- 排除已经由相同哈希成功消化的资料。
- 检查是否存在相同幂等键的未终结批次。
- 原子写入批次 manifest 和任务账本后再提交 Agent。

### F2. 学生资料严格回执

- 为学生消化建立独立 receiptPath。
- 消化指令必须要求 Agent 原样返回 studentId、digestBatchId、materialId、relativePath 和 sha1。
- 每个文件只有在身份、路径、哈希和必要产物均通过校验后才可改为 processed。
- 对旧版 Agent 的非结构化输出允许进入人工降级解析，但不能根据模糊文本一次性确认全部文件。

### F3. 项目资料兼容接入

- 复用 registerProjectDigestBatch 和现有严格回执逻辑。
- 不改变已有项目目录和 digestManifest。
- 将项目提交、结果同步和重试统一接入 DigestOrchestrator。
- 保留旧项目回执解析，避免已存在的执行结果失效。

### F4. 执行器选择与提交

最小路由规则：

1. 用户或系统当前已固定的执行器。
2. 健康且支持该任务的直接执行适配器。
3. QClaw 收件箱。
4. ManualAdapter。

本版本不基于成本、质量、模型能力做智能推荐，也不新增 Agent 设置步骤。

### F5. 自动监听结果

- 直接执行：复用子进程完成回调，立即进入结果校验。
- QClaw 收件箱：在主进程使用已有低频轮询机制检查状态和结果；应用在前台时建议 3—5 秒，后台时适当降频。
- 人工模式：粘贴或导入后立即归一化和校验。
- 所有通道最终只能调用同一个 applyDigestResult，避免三套回写逻辑。
- 通过 IPC 向学生页或项目页发送 digest-status-changed 事件，页面自动刷新。

### F6. 自动验收与应用

按以下顺序执行，任一步失败都不得提前标记资料完成：

1. 校验 protocolVersion、taskId、executionId 和当前任务状态。
2. 校验 scope id、digestBatchId。
3. 校验 processed 中每个文件的 materialId、relativePath 和 sha1。
4. 校验产物位于允许的知识库目录内。
5. 校验必须产物存在、可读且不是空文件。
6. 更新 digest manifest、资料状态和知识日志。
7. 记录成功、失败和未返回项。
8. 通过原子写入提交最终状态。

消化结果属于可逆的知识加工产物，因此机器校验通过后自动验收；正式成长证据、正式学情报告和档案发布仍不在本版本自动验收范围。

### F7. 部分完成与重试

- processed 项立即记为完成。
- failed、缺失或校验不通过的项保留为未完成。
- “重试未完成项”创建新 executionId；必要时创建仅包含剩余文件的新 DigestBatch。
- 不重复处理已经确认完成且哈希未变化的文件。
- 同一结果重复到达时保持幂等，不重复写日志、不重复计数。

### F8. 崩溃恢复与超时

- 应用启动时读取所有未终结的消化任务和批次。
- 若执行器仍能查询原 executionId，则恢复轮询。
- 若结果文件已经存在，则直接进入校验，不重复提交。
- 若 Agent 状态未知但尚未超时，显示“正在恢复”。
- 超时后进入“需要帮助”，用户可重试；旧执行结果随后到达时必须通过 executionId 和批次身份校验，避免污染新任务。
- 取消只停止继续等待，不删除原始资料和已验证产物。

### F9. 普通界面与高级诊断

学生资料页和项目资料步骤统一使用 DigestStatusCard，包含：

- 待处理数量。
- 当前简明状态。
- 最近完成时间。
- 一个主按钮。
- 完成后“查看新增知识”。
- 异常时一行可理解的原因。

高级诊断折叠区保留：

- 实际执行器。
- taskId、executionId、batchId。
- 各文件校验结果。
- 回执路径、日志路径。
- 复制原始指令、导出任务包、手工导入结果。

任务中心继续保留完整记录，但不作为日常主流程入口。

## 九、分阶段开发计划

### D0：协议冻结与测试基线

目标：先固定行为合同，防止边开发边改变完成判定。

- [ ] 记录学生和项目现有消化数据样本、回执样本和失败样本。
- [ ] 确认 DigestBatch v1、DigestResult v1 和 completionPolicy 字段。
- [ ] 建立新旧回执兼容矩阵。
- [ ] 为当前 0.9.3 学生和项目消化行为增加回归测试。
- [ ] 确认 0.9.4 不改变成长模型、学情报告、档案和 Android 数据。

交付物：

- 协议 fixture。
- 回归测试基线。
- 兼容性清单。

阶段验收：

- 新协议能够表示学生和项目两类批次。
- 旧项目回执和已提交中的旧学生任务均有明确处理策略。

### D1：统一批次与严格结果校验

目标：先做到“系统能准确知道哪些文件真的完成”。

- [ ] 实现 digest-batch.cjs。
- [ ] 将项目现有批次结构适配到 DigestBatch。
- [ ] 为学生资料建立严格 manifest 和独立 receipt。
- [ ] 实现 digest-result.cjs 及旧回执归一化。
- [ ] 实现逐文件身份、哈希、路径和产物校验。
- [ ] 实现 partial 结果和剩余文件计算。
- [ ] 实现幂等重复结果处理。

阶段验收：

- 一批 5 个文件中只返回 3 个合法结果时，只能有 3 个文件被标记完成。
- 错误 batchId、错误哈希、越界产物和空产物均不能被接受。

### D2：后台自动执行闭环

目标：让所有现有适配器共用同一条业务链。

## 十、测试矩阵

### 10.1 正常流程

| 范围 | 场景 | 预期 |
| --- | --- | --- |
| 学生 | 单文件、直接执行 | 一次点击后自动完成 |
| 学生 | 多文件、QClaw 收件箱 | 自动等待并逐项完成 |
| 项目 | 单文件、直接执行 | 更新项目 manifest 与知识结果 |
| 项目 | 多文件、人工模式 | 导入一次结果后统一校验 |
| 学生/项目 | 无新增或修改文件 | 不建立空批次，提示暂无待处理资料 |

### 10.2 数据准确性

- 同名不同内容文件。
- 文件提交后原文件被修改。
- 已完成文件再次扫描。
- 相同内容重复结果。
- 旧批次结果迟到。
- 回执缺少一个文件。
- 回执多出不属于批次的文件。
- relativePath 正确但 sha1 错误。
- Agent 写了产物但没有合法回执。
- 回执合法但产物不存在、为空或越出允许目录。

### 10.3 故障与恢复

- Agent 不可用，自动降级 ManualAdapter。
- 直接执行进程失败。
- QClaw 长时间无结果。
- 应用在 running、waiting_result、validating 阶段分别退出。
- 操作系统重启后恢复。
- 网络短暂中断。
- 用户连续双击“开始处理”。
- 用户在重试后收到旧 executionId 的结果。
- 批次 manifest 或回执文件含 BOM、非标准换行或可修复 JSON。

### 10.4 回归

- 原有任务中心仍可读取并展示任务。
- 原有项目严格回执继续有效。
- 旧学生 digest-state、index 和 log 可以读取。
- 学生和项目原始资料不被移动或删除。
- 成长模型、报告和档案不会被消化完成事件自动改写。
- Android 0.5.8 的接口和连接流程不变。

## 十一、量化验收标准

### 11.1 用户体验

- 有可用 Agent 时，普通用户从“待处理”到发起处理最多一次点击。
- 完成后无需点击“同步结果”。
- 普通页面不展示 taskId、executionId、batchId、SHA-1 或原始 JSON。
- 无可用 Agent 时，人工降级不超过一次复制和一次粘贴。
- 部分失败只提供一个主要动作：“重试未完成项”。

### 11.2 准确性

- 只有批次、路径、哈希和产物全部通过校验的文件才可标记完成。
- 部分成功时，成功项与失败项统计必须与回执逐项一致。
- 重复提交、重复回执和应用重启不得产生重复完成记录。
- 旧批次结果不得写入新批次。
- 任何校验失败都不得修改原始资料。

### 11.3 性能

- 100 个本地文件的待处理扫描和批次建立目标不超过 3 秒，不含大文件哈希的首次读取时间。
- Agent 返回结果后，前台状态刷新目标不超过 5 秒。
- QClaw 轮询不阻塞页面，不持续高频读取磁盘。
- 应用启动恢复不阻塞首屏；恢复检查应在后台进行。

### 11.4 可恢复性

- 应用在任意非终结状态退出后，重新启动可以恢复查询或安全重试。
- 失败和超时批次保留诊断信息。
- 人工模式始终可用。
- 原始资料、既有知识库目录和旧任务账本不因升级被删除或强制迁移。

### 11.5 交付

- 新增模块具备单元测试。
- 学生与项目各至少完成一条端到端自动闭环测试。
- 0.9.3 覆盖升级测试通过。
- 0.9.4.exe、版本说明和构建校验记录齐全。

## 十二、风险控制与回滚

| 风险 | 控制措施 |
| --- | --- |
| Agent 声称完成但未正确写入 | 逐文件哈希和产物存在性校验，不信任自然语言摘要 |
| 新自动验收影响高风险任务 | completionPolicy 只对 student_digest 和 project_digest 启用 |
| 学生旧任务缺少严格回执 | 兼容读取但不对新批次使用宽泛完成推断 |
| QClaw 轮询影响性能 | 前台低频轮询、后台降频、终结任务停止轮询 |
| 重复提交造成重复知识 | 幂等键、单活动批次和重复结果去重 |
| main.cjs 改动过大 | 新逻辑放入三个独立模块，main.cjs 只保留编排入口和 IPC |
| 0.9.3 数据升级失败 | 不做强制目录迁移；新 manifest 旁路增加；保留旧读取路径 |

回滚策略：

1. 0.9.4 新增的批次文件和任务记录不替换原始资料。
2. 若自动链路出现问题，可通过功能开关退回 ManualAdapter 和原有高级入口。
3. 已完成结果依据文件哈希保留，不因回滚重复处理。
4. 安装包升级前继续执行现有用户数据备份流程。

3. 学生与项目端到端测试未通过，不升级版本号和生成 0.9.4.exe。

## 十四、完成定义

只有同时满足以下条件，才认为“资料消化自动闭环 v1”完成：

- 学生资料和项目资料均接入统一 DigestBatch。
- 正常自动执行路径只需一次点击。
- QClaw 异步结果能够自动回写。
- 学生资料不再依赖宽泛时间戳或日志文本推断整批完成。
- 部分成功、失败重试、重复结果和应用重启均经过验证。
- 普通用户不需要理解任务协议、回执、哈希、审批或 Agent 路由。
- 无外部依赖环境仍可使用 ManualAdapter 完成同一闭环。
- 不触发成长模型、正式报告和教育档案的自动发布。
- 0.9.4 安装包通过 0.9.3 覆盖升级验证。

达到上述完成定义后，下一阶段才进入“消化结果 → 成长模型候选 → 学情报告/教育档案定期更新”，并继续沿用本版本建立的批次、来源和可恢复执行基础。
