# Windows 资料归属纠正与自动投递 R15 验收报告

日期：2026-10-13。Windows 0.21.1 开发候选，标签 `smart-material-correction-r15-20261013`，在 R14 工作区基础上增量修复；保留其他模块成果。未安装到正式环境，未上传或推送，未修改真实学生资料或认证文件。

## 修复结论

### 学生纠正与重新智能分类

- 原确认学生接口将已确认学生视为不可改变的授权边界；原手动投递也拒绝与之不一致的学生。R15 增加显式 `reassign_student` 操作，确认目标学生权限、资料版本及来源状态后才变更单项归属，不改变整个来源的绑定。
- “待处理”和“已投递”均提供“更正学生并重新智能分类”。清除旧学生的建议、执行状态及相关精确规则的自动资格，记录更正历史；按新学生重新校验提取／分析，不复用旧学生的上下文、语义建议或资料提取缓存。Provider登录及分类资格的复用不改变学生资料隔离。
- 已投递资料从已验证的受管原件重新生成受控快照，不依赖已释放的下载原件。新目标成功后才处理旧关联；已有引用或独立来源的旧资料继续保留并记明原因。不会为了单副本目标删除被引用的历史。
- 手动跨学生纠正须明确选择新学生，前端标出“更正学生并按此位置投递”；宿主重新验证目标及版本。未知执行、投递中、分析中仍不能绕过核对；暂停来源不能自动重分析。
- 同一学生已人工锁定的资料，只有用户明确要求重新智能分类才解除该项锁定；后台 Agent 不能擅自覆盖人工决定。

### 新旧入口统一和空间控制

- 旧下载入口、旧分享入口的生产 IPC 已切到统一收件箱适配层，复用固定快照、学生确认、投递回执、纠正、幂等与清理链路。实际主进程 IPC 测试验证不再调用旧独立导入器。
- 旧下载入口展示统一记录；中转原件已清理的已投递项显示登记历史，不要求再提供丢失的来源文件。需纠正时可使用统一收件箱。
- 专用中转来源在回执、目标文件与 SHA-256 校验后释放中转原件及内部快照，不再建立“已投递”副本。分享接收对象及本版本记录的 `received` 中转副本同样在校验后释放；旧分享账本继续保留。录音投递后仍可从受管原件转写。
- Documents、图库等普通“保留原件”来源仍保留用户原件。“单副本”指可释放的中转副本，不承诺删除普通来源原件或被引用的历史副本。没有可信关联记录的旧 `received` 文件不批量猜测删除。
- 本轮无全盘清理、全量历史重导入或旧独立账本强制合并。R14 的受控历史重复清理和备份机制保留；新旧入口今后的投递共用统一记录。

### 切换学生不重复登录

- 界面从主、备受控分类的已保存状态计算有效执行器，不再因为 WorkBuddy 主通道失败而隐藏已可用的 Codex 备用。
- 同一 Provider、程序、认证配置及分类合同的有效资格供已经授权使用该执行器的学生复用；资格过期显示自动准备，不等同于重新登录。
- “继续待办”使用有效执行器和已有登录，授权恢复可唤醒其他已经允许此 Provider 的学生。仍保留学生级备用资料处理同意，不能把一个学生的授权自动扩大到其他学生。
- 本轮真实验证仍发现 WorkBuddy 后台未认证。已验证的是“WorkBuddy 发送正文前认证失败 → Codex 备用分类成功”，不是 WorkBuddy 直接分类成功。需要使用 WorkBuddy 时仍须官方授权一次；不得用开发测试配置冒充产品授权。

### 图片／公式限制与可信阈值

- 已知图片、公式等提取范围提示改为非阻断提示；只要可读正文足以判断分类，可推荐并按可信条件自动投递。消化阶段继续保留完整性标记，分类成功不代表公式或图片已完整理解。
- 空文本、正文截断、未知提取错误、敏感或冲突仍不自动投递；纯图片无足够文字不按文件名猜测。
- 来源设置新增自动投递可信阈值，默认 **0.95**，可在 **0.95–1.00** 调整。没有明确项目编号时也可依据正文语义，但须有足量的原文证据、合法项目、同学生范围、候选差距至少 **0.20**，且来源已开启自动投递。明确来源目标与用户确认的精确规则仍沿用原授权规则。
- 分数不代表实测准确率，不自动推断学生。所有自动投递均可从“已投递”纠正。低分／证据不足仍集中确认，不进行无限重试。
- 分类提取缓存合同升级至 v3；已有同学生、同版本的完整宿主提取缓存仍可复用，不因范围提示而再次 OCR。跨学生纠正必须重建范围校验，不复用旧学生分析上下文。

### 性能：开发机合成采样，非目标机验收

环境：Windows、i5-12400F／12逻辑处理器、63.8GiB RAM、Node v24.13.0。

- 10,000个不变文件：三次扫描约432–463ms，提取、全文件内容哈希、Agent调用和投递均0；新增10份仅提取／分析10份。
- 收件箱并发查询P95约1.79ms，事件循环最大延迟77.53ms；加载及扫描RSS增量52.49MiB。见 `incremental-performance.json`。
- 10,000条任务、约80.7MB账本：Worker冷加载378.58ms，热查询P95 0.73ms，返回最大9,161字节。见 `task-read-performance.json`。
- 10,000条任务并发耐久写：查询P95 192.34ms，耐久写P95 264.02ms；50次进度更新P95 2.00ms且未重写主账本。见 `task-write-performance.json`。
- 上述不是窗口交互P95，也不是“相对关闭功能劣化≤20%”证明；不把外部Agent资源算作零。本轮未重跑四小时混合运行、四核/8GB/SSD目标机、200份标注质量或5名代表用户效率验收。
