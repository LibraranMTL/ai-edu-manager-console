# 智能资料归集 R5：扫描批次登记修复

日期：2026-10-12（北京时间）。版本：Windows 0.21.1，候选标识 `smart-inbox-r5-20261012`。本次修复扫描后的批次登记缺陷，不是正式发布或完整产品验收通过声明。

## 1. 问题与修复

用户报告目录文件无法发现，来源卡提示“资料批次未能登记”。只读核查表明：当时目录中的 5 份 DOCX 已有发现记录，均为 pending、分析次数为 0。故障发生在发现之后、内容分析之前。

根因是 Windows 主程序 `beginBatch` 新建 pending 任务后直接请求 running；真实任务协议禁止该流转。此前归集引擎测试和包内验证未接入此主程序回调，因此没有覆盖这个集成缺口。

本次改动：

- 保留原资源准入与授权检查。批次取得资源名额后，按 pending → approved → running 登记，留下 `intake_admitted` 审计事件；落盘确认成功后才登记运行句柄、返回引擎处理资料。
- 不修改全局任务状态规则；pending → running 仍被拒绝。approved 是本批内部处理准入，不是批准某份资料的目标、跨学生访问或外部 Agent 调用。
- 登记失败保留具体原因。已有待办成功恢复批次后清除来源的旧错误提示，不要求重新发现或重新导入文件。
- 不清空、篡改或自动接管旧失败尝试留下的 pending 任务。新批次继续处理原发现记录，历史审计保留。
- 不修改真实来源配置、学生绑定、现有资料正文或原件，不启动真实资料扫描，不新增 Agent 授权。

新增接入测试具体覆盖：

1. 手动、定时批次各自完成 approved → running → reviewing → succeeded，状态和审计均真实落盘。
2. 批次失败写入 failed，释放运行登记，不报告成功；重复结束不重复追加审计。
3. 持久化等待期间不返回可执行批次；注入磁盘保存失败后不登记运行句柄。
4. 共享来源发现后转人工确认，不提取正文、不调用 Agent；已绑定可信目标正常投递，原件保留。
5. 不变文件重扫不重复提取、投递或创建任务。
6. 资源忙时不创建批次；登记失败后重用已有发现记录，成功恢复后清除旧错误，保留旧 pending 历史。

包内验证另覆盖同学生、同版本完整提取结果交接给消化阶段，无第二次提取；改投时撤销未引用关联、保留已引用资料和固定版本，重复回执幂等。

这些是生产函数与包内模块的隔离集成测试，不是假装启动完整业务桌面进行界面验收；许可、资源与测试目标使用合成测试环境。没有在用户生产目录上试投递，也没有在本轮调用真实 WorkBuddy。

## 4. 用户需要操作的最小清单

1. 在任务中心确认没有运行中的消化、投递或结果待核对任务后，正常退出旧候选，再运行文件名含 `smart-inbox-r5-20261012` 的新候选。不要同时打开两份主机，不要删除用户数据或任务账本。
2. 打开“资料收件箱 → 来源管理 → 下载文件”，点击一次“立即扫描”。应不再出现“资料批次未能登记”；已有发现记录继续处理，不需要移动原文件或重建来源。
3. 当前下载来源未绑定学生，预期资料进入待处理供人工确认，不会自动发给 Agent。为这些历史待办明确选择学生和项目后批量投递。只有确认今后整个目录均属于同一学生时，才在来源设置中绑定该学生；绑定不会自动改写既有待办的学生归属。
4. 核对目标资料和原件／归档位置，再扫描一次确认没有重复登记。旧下载中转来源仍沿用原有“投递后归档”设置；不要把它与新通用来源默认保留原件混淆。

本缺陷不需要重新登录 WorkBuddy，不需要修改安全设置。若仍失败，只提供时间、资料数量和错误提示，不发送学生正文或凭据。
