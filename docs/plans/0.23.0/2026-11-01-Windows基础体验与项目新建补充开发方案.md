## 二　任务 A：诊断并修复知识资产统计更新链

### 2.1 已观察事实、推断与待验证项

**已观察事实**

- 运行库 `asset-index.sqlite3` 的 `quick_check` 为 `ok`，schema 版本为 4；资产记录数和汇总总数均为 14,732，没有发现数据库损坏或汇总总数漂移。
- 最近一次已观察的资产重建于 2026-11-01 08:55 完成；该时刻之后资产库没有新的持久化时间变化。主机的项目状态等其他数据在之后仍有更新，说明应用并非整体停止工作。
- `src/AssetCenterPanel.tsx` 的统计来自 `assetIndex`；`src/main.tsx` 的 `refreshAssets()` 主要在进入资产页、筛选变化、手动刷新和少数显式导入动作时调用。
- 项目页也读取 `assetIndex.total`，但项目页本身不保证先刷新资产快照。因此用户可能在资产库正常时看到旧值或零值。

**高可信设计缺陷**

当前没有一个由主进程提交结果驱动的统一 `asset-index:changed` 通知，也没有供首页、项目页和资产页共同消费的带代次统计快照。统计是否更新取决于用户访问了哪个页面和哪条操作路径，属于刷新链设计缺陷。

**尚未证实**

现有证据不能证明 08:55 之后存在一份已经成功接纳、却未写入资产库的真实资料。不能在没有受控复现前把问题单一归因于扫描器、数据库或统计缓存。

### 2.2 先复现，再修复

- [ ] 建立一个虚构学生和测试项目，分别通过资料上传、项目采纳、目录扫描、快照恢复、删除/撤回五条路径操作唯一命名的测试文件。
- [ ] 每一步记录：上游业务回执 ID、源路径、内容哈希、资产库代次、统计快照代次、数据库资产行、页面显示值和时间。读取页面不得触发重建。
- [ ] 若上游有成功回执而资产行缺失，定位该路径“业务提交成功—资产 upsert—事务提交—事件广播”的第一个断点；若资产行存在而页面不变，定位为快照/通知问题。
- [ ] 对空库 `replaceAll`、空快照恢复和批量删除补失败用例，确保批量删除后即使没有后续 upsert 也会清除汇总缓存。

### 2.3 修复设计

1. 在资产主进程提供只读 `getAssetStatisticsSnapshot(scope)`，返回 `generation`、`asOf`、学生范围、资产总数、待处理数、重复组数、最后变更/重建时间和健康状态。一次响应只对应一个提交后的代次。
2. 所有成功改变资产或引用的事务——上传、导入、项目采纳、扫描、恢复、删除、撤回和引用变更——提交后统一发出 `asset-index:changed { generation, reason, scope }`。事件不能在事务提交前发送。
3. 渲染层只订阅一次，按代次去重并短时防抖；首页、项目页和资产页读取同一统计服务。首次打开这些页面及窗口重新获得焦点时可做一次轻量校验，但不轮询、不自动全量重建。
4. 项目页不得继续把“曾经访问资产页后留下的 `assetIndex.total`”当实时统计。所有卡片显示“截至 HH:mm”及健康/待处理提示，旧响应不能覆盖新代次。
5. 对“上游成功回执存在、资产记录缺失”的历史项提供显式、幂等的对账与回补操作；先预览差异，再回补，不在启动时静默全量重建。
6. 记录可诊断但不泄露隐私的指标：最后成功代次、待处理数量、失败路径和失败原因码；不把学生姓名、文件正文或完整本机路径写入遥测。

### 2.4 验收

- 五条写入/撤回路径提交后，数据库和三个页面在同一代次收敛；切换页面不需要手动“刷新资产”。
- 重复事件、乱序响应和快速批量导入不会重复计数或形成刷新风暴。
- 空恢复、批量清空、进程在提交前后退出、WAL 恢复和数据库只读失败均有明确结果。
- 10,000 项以上样本中，打开页面不触发全量扫描；资产中心既有筛选、搜索和重建功能通过回归。
- 若受控复现最终未发现后端漏写，问题结论明确记录为“展示快照陈旧”，不扩大为资产丢失事故。

## 四　任务 C：每次启动自动检查版本更新

### 4.1 状态判断

功能只完成了一部分。当前 `electron/main.cjs`、`electron/preload.cjs` 和 `src/main.tsx` 已支持手动读取更新清单、比较版本并打开 Windows 下载地址；设置页已有手动检查入口。代码中未发现应用每次启动后自动调用检查，也未发现 Windows 新版启动弹窗、每会话去重和网络异常行为测试。

### 4.2 开发方案

- [ ] 主窗口完成首屏和基础数据启动后，延迟 3–10 秒执行一次非阻塞检查；每次进程启动最多自动检查一次，不能阻塞或拖慢主窗口。
- [ ] 正式通道只提示 `stable` 且 `windowsVersionCode` 大于当前版本的版本。候选、预候选和未发布构建不能作为正式升级推送。
- [ ] 更新清单校验 HTTPS、允许的下载域、版本名/版本码、平台、发布状态和下载 URL；配置连接和读取超时、响应大小上限、JSON 结构校验。若清单提供 SHA-256/签名，弹窗展示并供下载后校验链使用。
- [ ] 新版弹窗显示当前版本、最新版本、发布时间、精简更新说明和“下载新版”“稍后提醒”。下载按钮只打开经过校验的链接；首版不自动下载、不静默安装。
- [ ] 同一会话、同一版本只弹一次；手动检查仍可再次显示结果。网络失败、超时或清单异常时自动检查保持安静并写入可诊断状态，设置页手动检查则显示明确错误。
- [ ] 下载链接无效或不受信时禁用下载按钮，不能退回任意外链。无新版本时不弹窗。

验收用例至少覆盖：旧版/同版/新版，正式版与候选版隔离，离线、超时、非 2xx、畸形 JSON、超大响应、不受信 URL、同会话重复回调、版本码回退、手动复查，以及安装包升级后当前版本正确变化。只有目标安装包真机验证通过，才能称“启动自动更新提醒已完成”。

## 六　任务 E：修复项目列表 IPC 载荷超限与“0 个项目”假空状态

### 6.1 已定位事实与边界

- 本项不是项目、学生关联、资产关联或暂存资料丢失事故。运行库数据库 `quick_check = ok`；已核验 14 个项目、23 条学生关联、3,152 条项目资产关联和 49,637 条暂存资料仍存在。
- `electron/main.cjs` 的 `listProjectsPage()` 当前对列表行调用 `normalizeProject(stored, { includeStaging: false, metadataOnly: true })`。该名称容易误导：返回对象仍保留完整项目元数据，其中可能含接近 1 MiB 的 `payload_json` 内容；仅清空 `stagingItems` 和扫描快照不足以形成真正列表投影。
- 现场“全部项目”响应序列化后为 2,098,181 bytes，比 `boundedProjectIpcJson()` 的 2 MiB 上限多 1,029 bytes。主进程按现有保护返回 `project_ipc_payload_too_large`，未传输任何项目项。
- `src/main.tsx` 的 `refreshProjects()` 在 `ok !== true` 时仅设置通用 `projectMessage` 并提前返回；初始 `projects` 数组仍为空，页面因此把读取失败误呈现为“0 个项目”。

**固定原则**：保留 2 MiB IPC 防线，不提高上限、不删除保护、不重建或改写数据库、不以静默分页掩盖完整 payload 被返回的问题。列表接口只返回轻量投影；完整字段只由按项目 ID 的详情接口在用户进入或选择该项目后读取。

### 6.2 接口与数据投影

1. 在 `electron/main.cjs` 为 `listProjectsPage()` 增加唯一的 `projectListProjection(stored, stagingSummary)`，不得复用会输出完整 `payload_json` 内容的 `normalizeProject()` 作为列表结果。投影仅允许：`id`、`name`、`type`、`status`、`studentIds`、`studentNames`、`workspaceTemplateId`、`workspaceTemplateName`、`workspaceMode`、`createdAt`、`updatedAt`、归档/结项/发布时间，以及可由现有索引计算的统计摘要。
2. 统计摘要只能包含数字或短状态：原始资料数量、暂存总数/待处理数/已接纳数、知识处理状态、风险数量及短原因码。不得包含项目描述、目标、交付物、路径、`assetIds` 全量数组、`studentEvidence`、自动化细节、扫描快照、暂存项、原始材料正文或任意未知扩展字段。
3. `bridge:getProjectDetail(projectId)` 继续作为完整项目读取入口；详情返回前按当前项目范围和授权校验。列表项与详情对象使用不同的 TypeScript 类型（如 `ProjectListProjection` 与 `LearningProject`），避免后续 UI 又把详情字段回填进列表缓存。
4. `boundedProjectIpcJson()` 继续保护所有项目 IPC 响应。被拒绝时只返回稳定错误码、`limitBytes` 和实际字节数等非敏感诊断，不记录学生姓名、项目标题、路径、正文或 `payload_json`。列表投影通过后，不能删除该错误分支。

### 6.3 渲染层状态与交互

- [ ] 在 `src/main.tsx` 中将“成功加载空列表”与“列表加载失败”分为不同状态。`project_ipc_payload_too_large` 必须显示“项目列表载荷过大，列表未加载；请更新到修复版本或联系支持”，而不是项目数 `0`。
- [ ] 失败时不执行 `setProjects([])`、不重置已选项目、不把失败响应的 `total` 当项目总数；如页面已有上次成功列表，可保留并标记为“非最新”，同时显示本次错误。
- [ ] 真正的空结果仅在 `ok === true` 且 `total === 0` 时显示“暂无项目”。无权限、解析失败、超限和详情加载失败分别使用可区分错误码与文案。
- [ ] 选择项目后再调用 `getProjectDetail(projectId)`；详情失败不回退为“项目不存在”，保留列表选择并显示详情读取错误。浏览列表、打开详情和显示错误均不得触发项目扫描、资料消化、Agent、报告生成或数据库写入。

### 6.4 测试先行与验收

- [ ] 新增 `tests/project-list-ipc-projection.test.cjs`：使用合成的 14 项目、23 条学生关联、3,152 条资产关联、49,637 条暂存资料夹具，并在一个项目中放入接近 1 MiB 的扩展元数据。断言列表响应在 2 MiB 以下、`items.length` 与总数正确、学生关联和统计摘要保留，且响应 JSON 不出现被禁止的完整字段或该大元数据片段。
- [ ] 对同一夹具调用 `getProjectDetail(projectId)`，断言详情仍可返回该项目的完整元数据；未选择的项目完整 payload 不得进入列表响应。按学生范围筛选时，只返回有对应关联的轻量项目项。
- [ ] 为 `boundedProjectIpcJson()` 保留超限单元测试：人为构造超过 2 MiB 的非列表响应，断言仍返回 `project_ipc_payload_too_large`，且错误体不泄露项目内容。
- [ ] 新增或扩展渲染层测试：初始加载超限、已有成功列表后超限、真实空列表、详情超限/失败、乱序响应。断言超限时页面不显示“0 个项目”，不清空最后一次成功数据，不调用任何写接口。
- [ ] 在当前运行库只读复核修复前后的项目数、学生关联数、资产关联数和暂存资料数完全不变；用同一 14 项目现场规模验证“全部项目”、单学生筛选、搜索、项目详情和项目进展入口。
