# P0 学习时间线性能验收报告

日期：2026-09-10

范围：Windows 主机端学习时间线 P0 与 Windows 学生端逐图采集时间上传。

## 结论

本轮合成压力测试通过，未发现新时间线功能会造成明显持续卡顿的代码级证据。时间线默认不运行 OCR 或大模型任务，不轮询完整采集历史，不向前端发送完整截图数组；缩略图仅在采集结束后低优先级生成，并在进入视口附近时按需读取。

这份结论属于本机代码级和合成数据验收，不替代正式 EXE 在两台真实 Windows 设备上的长时采集验收。

## 测试场景

- 同一学生、同一天写入 5000 条不可变截图事件；
- 每条事件同时模拟会话明细追加、轻量会话元数据和摘要索引更新；
- 对 5000 条历史连续执行 60 次分页查询；
- 每次只向渲染端返回 30 条；
- 检查首屏载荷、堆内存增量、P50、P95、P99 和最大单次写入时间；
- 检查前端不存在 5 秒完整状态轮询，并使用增量事件、卡片记忆化、视口懒加载和 `content-visibility`。

执行命令：

```powershell
node scripts/benchmark-capture-timeline.cjs
```

采集策略最低保存间隔为 5 秒，按 P95 6.05ms 计算，新增索引处理约占最低保存周期的 0.12%，不会形成持续占用。旧会话补齐已由逐事件落盘改为按日期批量追加，5000 条从秒级风险降到本次测试的 27.56ms。

## 防卡顿措施

1. 总索引只保存会话摘要，截图明细单独使用 JSONL 追加写；
2. 采集变化只发送轻量 `capture_delta`，不发送完整历史；
3. 取消时间线页面每 5 秒读取完整采集状态；
4. 时间线固定 30 条分页，不把 1000/5000 张截图一次性送入 React；
5. 缩略图在采集停止后每 150ms 最多处理一张，采集重新开始时自动让路；
6. 缩略图进入视口前不通过 IPC 读取；
7. 时间线卡片使用 `memo`，非紧急分页结果使用 React transition；
8. 长列表卡片使用 `content-visibility: auto` 跳过屏幕外布局和绘制；
9. 日期级索引避免查询时扫描所有学生、所有日期；
10. P0 不执行 OCR、大模型摘要、知识状态推断或指导建议生成。

## 正式发布前仍需完成

在正式 EXE 上进行不少于 60 分钟的双机真机验收，记录：

- 开启采集前、采集中和打开时间线后的 CPU、内存及界面交互延迟；
- 1000 张以上真实截图的首屏打开、切换筛选和加载更多耗时；
- 主机正在采集时打开时间线，采集间隔是否稳定；
- Windows 学生端上传过程中主机界面是否可正常切换学生和页面；
- 缩略图后台生成时是否出现持续 CPU 峰值；
- 休眠、重启、网络中断恢复后时间线是否完整且无重复事件。

只有真机指标也通过，才能把“无明显卡顿”升级为正式安装包验收结论。
