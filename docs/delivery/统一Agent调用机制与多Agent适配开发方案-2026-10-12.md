# 统一 Agent 调用机制与多 Agent 适配开发方案

日期：2026-10-12。性质：开发方案，**不代表本方案已实现或各 Agent 已通过真实执行验收**。

## 一、目标与现状

让资料智能分类、项目资料消化及后续研究和普通任务共用一套调用合同，同时沿用教育管家现有任务中心的账本、调度、权限、资源准入、回执和恢复机制。用户继续选择已配置的 Agent；增加执行器不要求重新建立学生档案、配置第二套模型或逐文件授权。

当前任务中心已通过 `getAgentExecutionAdapters()` 统一登记执行器，并通过 `routeTask()` 选择执行器；实际调用仍分别采用 CLI、桌面交接、本机 Gateway 或任务包。智能分类的 Codex／WorkBuddy 分支位于 `smart-inbox-agent.cjs`，受控项目消化另有专用执行路径。因此本方案统一**业务调用合同、任务级资格和结果语义**，各厂商适配器使用其正式支持的传输方式。

本方案只覆盖“教育管家调用外部 Agent”的出站链路。现有“外部 Agent 通过教育管家 MCP 查询授权资料”的入站链路继续使用原有学生范围授权和宿主校验；两条链路的方向、凭据和权限分别管理。

## 二、总体架构

```text
资料收件箱／项目资料消化／研究及其他业务
                  │
       教育管家统一任务中心（唯一任务账本）
       调度、授权、资源、状态、重试、审计
                  │
       AgentInvocationService（进程内合同）
       任务级资格、固定输入、调用、结果归一化
                  │
      ┌───────────┼───────────┐
 CodexProvider  WorkBuddyProvider  其他 Provider
      │             │               │
 官方 MCP／SDK／CLI  官方 SDK／A2A／CLI  官方 MCP／SDK／CLI／人工交接
```

1. **任务中心拥有状态。** `TaskEnvelope`、`executionId`、幂等键、事件、回执和恢复状态仍由现有任务中心保存。适配器只返回外部运行引用与事件，不另建任务账本、定时器或重试队列。
2. **进程内调用合同是权威入口。** 业务模块通过同一服务调用 `classify`、`digest` 等任务档；分类与消化的业务校验、正式文件操作和知识提交仍由宿主完成。
3. **MCP 是一种可选出站传输。** 对提供 Agent MCP Server 的厂商，由教育管家的适配器作为 MCP 客户端连接；其他厂商可使用 SDK、A2A、CLI 或桌面交接。若以后需要供本机其他受信任组件调用的 MCP 外观，它只转发到同一服务与任务中心，不保存第二套状态。
4. **能力与资格按“执行器 × 任务档”登记。** 安装、MCP 握手、CLI 登录、合成任务通过和真实业务验收分别记录。某 Agent 能执行普通任务，不自动获得学生资料分类或消化资格。

## 三、任务档与第一版范围

| 任务档 | 输入与输出 | 必需限制 | 第一版 |
| --- | --- | --- | --- |
| `classification_readonly.v1` | 宿主提供固定版本正文及允许的学生／项目／分类 ID；返回候选 ID、逐字正文证据、分数和敏感／冲突标志 | 无工具、无下游 MCP、无任意路径；宿主验证证据和自动投递条件 | 接入 |
| `digest_host_mediated.v1` | 宿主提供固定版本的完整提取结果和项目规则；返回候选知识产物及来源引用 | Agent 不直接写知识目录；宿主校验来源、暂存及提交 | 接入 |
| `research_web.v1` | 明确授权的研究问题与范围；返回带来源的研究草稿 | 单独允许联网，结果经人工或宿主规则审核 | 后续迁移 |
| `general_task.v1` | 现有受约束任务包与声明权限；返回标准回执 | 沿用现有任务权限和人工交接路径 | 后续迁移 |

第一版只调整 Windows 主机内的调用层，先迁移 Codex 与现有 WorkBuddy 受控路径。TRAE／Qoder 保留现有任务中心适配和桌面交接，按同一 Provider 合同预留扩展；取得安装版真实验收后再开放对应的自动任务档。Android 和远程网络 MCP 不在第一版范围。

分类阶段继续复用宿主文档提取与 OCR。满足相同学生、资料版本、格式、提取器及 OCR 参数条件时，完整提取结果交接给项目消化；分类所用的截断预览不能充当消化全文。不同 Agent 不重复读取原件或各自运行 OCR。分类判断投递位置、消化生成知识产物，仍是两种独立的 AI 任务。

## 四、统一调用合同

Provider 的最小接口：

```text
describeCapabilities()             # 声明传输和支持的任务档
qualify(profile, runtimeFingerprint) # 按任务档运行合成资格检测
invoke(request, abortSignal)        # 发起一次固定输入执行
getStatus(externalRunRef)            # 仅在厂商支持时查询
cancel(externalRunRef)               # 返回已停止／停止未知／不支持
```

`invoke` 请求沿用现有任务身份，至少包含 `taskId`、`executionId`、`idempotencyKey`、`providerId`、`profile`、学生／项目授权范围、输入快照哈希、输出 Schema 版本、权限档及截止时间。正文是资料数据，不能改变任务指令、授权范围或输出合同。请求中不得传入任意 `cwd`、工具列表或由 Agent 自行选择的学生 ID。

标准结果至少包含 Provider ID 与版本指纹、外部运行引用、完成状态、符合 Schema 的输出、来源证据、工具活动摘要、失败类别和停止确认状态。外部返回“进程退出 0”或“模型自报成功”均不代替宿主结果校验。资料版本、学生／项目绑定、证据、路径和自动投递阈值由宿主复核；检查失败保留待处理和原件。

错误类别统一为认证不足、能力不支持、权限拒绝、敏感资料需人工处理、输出无效、资源繁忙、超时、已确认停止、结果未知及宿主提交失败。只有已确认未执行或已确认停止的请求才能按现有策略安全重试；结果未知先核对原执行编号和回执。人工确认／纠正继续锁定结果，Agent 不覆盖。

| OpenClaw／QClaw及其他 | 现有 Gateway／CLI／任务包；支持能力成熟后接专用 Provider | 逐个任务档验收，保留原有手工回写和宿主验证，不按产品名称批量授予自动资格。 |

## 六、安全、调度与资源约束

- 分类档使用固定文本输入、空临时工作目录和最小能力集合。不能证明无工具／无下游 MCP 时不投递学生资料到该执行器；“只读沙箱”本身不足以证明没有网络或其他工具。
- 每个 Provider、每个任务档分别保存资格结果；资格绑定程序路径与内容哈希、适配器版本、限制参数、输出 Schema 及认证范围。变化时失效并以合成资料复检，不在列表刷新时探测。
- 复用现有重任务资源准入、单执行器在途限制、手动优先、熔断、暂停和恢复。无待执行任务时不启动 Agent；MCP stdio 子进程随任务或受控会话生命周期管理，不新增按来源常驻服务。
- 仅宿主执行文件复制／移动、项目关联撤销和知识提交。已被引用资料按现有受控纠正规则保留；适配器返回的路径或文件操作建议不直接执行。
- 外部 Agent 的模型调用资源单独统计。日志仅记录批次摘要、耗时、结果类别和必要版本信息，不收集学生正文作为遥测。
- 已有教育管家入站 MCP 的学生授权、工具过滤和宿主权限检查不因出站调用服务改变；新出站凭据不写入提示词或任务包。

## 七、开发顺序

1. **P0：固定基线。** 为现有任务中心的 Codex CLI、WorkBuddy后台／桌面、TRAE／Qoder CLI与桌面交接记录行为测试；明确当前任务状态、回执、取消和未知执行语义。保存现有候选验收边界，不迁移历史任务。
2. **P1：内部合同。** 新建调用服务和任务档 Schema，把现有适配器包装为 Provider；任务中心仍是唯一派发入口。先接入分类，再接受控项目消化，旧调用路径保留为可回滚开关。
3. **P2：Codex参考链路。** 使用合成资料比较现有 CLI 与官方 MCP Server 的安全限制、结构化输出、启动耗时、取消与恢复；只在同等或更强约束且真实调用通过时切换传输。
4. **P3：扩展执行器。** WorkBuddy先处理输出格式稳定性并复验后台资格；TraeCode CLI 验证 MCP Server 与非交互模式，Qoder CLI 验证 SDK／无头模式。每个执行器逐任务档开放；桌面交接保持原状。
5. **P4：其他业务与可选 MCP 外观。** 研究及普通任务复用相同身份和结果合同；如有内部跨进程调用需求，再提供本机 stdio MCP 外观。外观只调用任务中心，不维护状态或独立重试。
6. **P5：综合验收。** 通过回归、真实厂商执行、目标设备资源和业务质量门槛后生成独立候选包；没有通过的 Provider／任务档保持关闭，不因其他执行器通过而自动开放。

## 八、验收标准

| 维度 | 通过标准 |
| --- | --- |
| 任务兼容 | 既有任务 ID、执行批次、状态、回执和人工交接语义不变；升级后历史任务可查，不重复派发。 |
| 任务级资格 | 每个 Provider × 任务档保存安装／认证／限制能力／合成执行／真实执行状态；版本或权限变化使资格失效。 |
| 分类隔离 | 跨学生、伪造候选 ID、正文提示注入、敏感资料、工具诱导均被宿主拒绝或转人工；跨学生自动投递为 0。 |
| 结果与恢复 | 重复请求和重复回执不重复登记；错误结果不采用；取消先撤销接收，停止未知不自动重派。 |
| OCR与效率 | 相同授权范围及完整版本条件下，分类到消化的提取结果交接继续有效；不同 Provider 不额外触发 OCR。无任务时无 Agent 调用。 |
| 厂商链路 | 每个宣称支持自动任务档的安装版，完成登录、合成样本、真实调用、拒绝路径、取消／超时和版本变化验证；自动测试不代替真实厂商执行。 |
| 回归与性能 | 资料收件、分享、会话采集、分类、消化、任务中心、课程卡片回归通过；四核／8GB／SSD目标机评估交互 P95、进程树内存及四小时混合运行。 |
| 业务质量 | 智能分类仍按既定独立 200 份标注集及至少 5 名代表用户效率目标验收，不用适配器契约测试替代质量测试。 |

## 十、2026-10-13 自动化收口补充方案

本节把“可以调用 Agent”收紧为“资料能够连续自动完成，同时不把安全确认变成技术阻塞”。实现顺序固定如下：

1. **P0 执行可用性。** 资格按 `Provider × 任务档 × 程序哈希` 持久化；有效期内重启不重复要求人工检测，程序、输出合同或有效期变化仍自动失效。分类和消化资格相互独立，不能以普通对话或另一任务档替代。
2. **P0 学生资料受控消化。** 现有学生批次继续使用原资料登记与逐文件结算，但 Codex／WorkBuddy 自动执行改为宿主固定原件版本、统一提取、无工具结构化返回、宿主校验提交。Agent 不再直接写学生知识目录。手动执行器和历史任务保留兼容路径。
3. **P1 阻塞原因治理。** 认证、资格、资源等待、来源异常、敏感资料、未知执行分别给出机器可读原因；仅资源忙、资格复检等已确认未执行的状态允许自动恢复。敏感、多学生冲突和未知结果保持人工处理。
4. **P1 任务存储降载。** 普通心跳写入独立追加日志，按任务 ID 与执行批次重放；业务状态变化仍使用 Worker 独占的原子完整快照。完整快照成功后清理已吸收的进度日志，崩溃重放不得复活已完成任务。
5. **P2 质量和目标机验收。** 继续执行 200 份独立标注集、至少 5 名代表用户、四核／8GB／SSD 和四小时混合运行；开发机合成测试不能替代上述业务验收。

收口后的用户指标为：自动投递准确率不低于 98%、跨学生自动投递为 0、总体自动完成率目标不低于 60%、已绑定重复来源目标不低于 80%。在达到业务样本量前只报告实际分子／分母，不用推算值代替验收。无变化的一万文件扫描必须保持正文读取、OCR 和 Agent 调用均为 0；一万任务运行时普通心跳不得重写完整任务账本。

### 本轮已实施

- 新增持久资格记录及有效期／程序哈希校验；WorkBuddy 分类和消化继续使用不同任务档。
- 学生资料自动消化接入受控固定输入链路：复用原批次和路径预检，知识候选由宿主写入，原件变化时拒绝结算。
- 新增阻塞原因分类，区分自动等待与必须人工处理。
- 新增 `progress.jsonl` 轻量进度日志；心跳不再触发任务账本全量改写。

### 仍需真实用户或目标机完成

- 真实学生资料的知识质量、分类标注集、代表用户节省时间和目标机四小时运行仍属于候选验收，不因代码测试通过而记为完成。
- WorkBuddy 独立开发授权不进入候选包；每台目标机仍需完成官方后台 CLI 授权。授权有效后，资格复检和后续自动任务不再要求逐份确认。

## 十一、充分性评估与停止条件

本补充方案对当前问题是“必要且已覆盖主要已知技术根因”，但不是“无需业务验收即可保证全部自动化”。资格持久化解决重复检测，受控学生消化解决支持执行器只能人工交接，提取交接解决重复 OCR，阻塞分流减少可自动恢复任务被人工接管，进度日志解决万条任务下最高频的全账本心跳写入。这些机制组合后，资料发现、分类、投递、整理和消化具备连续自动执行的基础。

仍然保留的人工处理不是技术退化：学生不明确、多个有效项目、敏感资料、内容不可读、原件变化、未知执行结果和已引用资料改投都属于需要业务判断或安全确认的情形。系统不得为了提高自动完成率而放宽这些门槛。相反，登录已有效、任务档资格已通过、只是资源繁忙或等待下一批次时，不应再显示成“请人工处理”。

候选能否转为正式版本，以以下停止条件判断：跨学生自动投递必须为 0；自动投递准确率未达到 98% 时关闭可信自动投递但保留建议；目标机交互 P95 或四小时资源稳定性未通过时不得以开发机合成结果替代；Provider 任一任务档真实调用未通过时只关闭该 Provider 的该任务档，不影响手工投递和其他已通过执行器。

本轮执行和证据见 [Windows 智能资料自动化 R11 候选验收](Windows-智能资料自动化-R11-候选验收-2026-10-13.md)，需要用户参与的部分见 [R11 用户验收清单](Windows-智能资料自动化-R11-用户验收清单-2026-10-13.md)。

## 十二、分类故障恢复与备用切换 R13

分类已增加学生级显式备用授权、主备各一次的受控路由、正文发送前持久化执行阶段及同认证环境的持久资格。仅在尚未发送正文时切换；本地进程停止不能证明远端未接收，因此发送后的超时与断线先核对回执。分类资格不授权消化或卡片任务。列表只读取状态，认证与资格检测由恢复操作或实际任务触发。

旧认证失败记录迁移保留备份，无发送阶段证据时不自动恢复。相关实现、包内验证与性能未完成门槛见 [R13验收报告](Windows-分类Agent恢复与备用切换-R13-验收报告-2026-10-13.md)。

## 十三、分类恢复与单副本存储 R14

R13 的真实使用反馈证明两个判断需要修正。第一，桌面已登录不等于后台 CLI 已授权，但产品不能把官方 CLI 目录或 JSON 文件交给普通用户选择；R14 由应用在私有持久目录下载固定版本的官方包，核对 npm 元数据、SHA-512、包名、版本、入口及压缩路径，再启动官方登录。第二，旧记录只有在确实无法判断是否已发送正文时才进入“执行待核对”；历史错误文案若能精确证明失败发生在资格阶段，则迁移为 `not_sent`、可恢复，并在迁移前备份。

备用仍由学生级显式授权控制。WorkBuddy 在正文发送前认证失败时，Codex 最多接替一次；正文可能已发送、敏感拒绝、越权或范围冲突不切换。候选包使用真实持久认证描述和实际任务中心完成了“WorkBuddy 资格失败 -> Codex 资格与分类成功 -> 宿主校验投递”的合成资料验证。

资料存储改为单受管原件：专用下载/中转来源在投递回执和内容哈希再次验证后删除中转原件，不再复制到来源下的“已投递”目录；内部固定快照也在完成后释放。“保留原件”的 Documents、图库等普通来源不删除用户原件。历史“已投递”副本仅在受控目录、登记回执有效且 SHA-256 一致时清理，任何异常都跳过。

实施与证据见 [R14验收报告](Windows-分类Agent恢复与空间优化-R14-验收报告-2026-10-13.md)，用户操作见 [R14用户验收清单](Windows-分类Agent恢复与空间优化-R14-用户验收清单-2026-10-13.md)。

## 十四、学生纠正、共享登录与分类阈值 R15

明确区分“Provider登录”和“学生资料处理授权”：同认证环境、程序、隔离参数与分类合同的有效资格可供已经授权的学生共用；备用许可仍逐学生一次确认。有效备用纳入整体状态，不能只显示主执行器认证失败。真实候选验证已覆盖第二名合成学生只新增分类调用、不新增登录或资格检测。

错选学生通过显式、版本绑定、可审计的单项纠正处理，不把旧学生上下文带给新学生。已投递纠正使用经校验的受管原件，新目标成功后才撤销允许撤销的旧关联，被引用历史保留。新旧下载／分享投递入口共用该服务及单副本清理回执，普通来源原件仍保留。

依据本轮用户确认，分类不再要求图片／公式已完整识别；在正文足以支持路由时，允许证据约束的语义自动分类。来源阈值默认0.95、可提高至1.00，候选差距至少0.20，并校验原文证据、学生／项目权限、版本和冲突。空文本、截断、异常、敏感和未知执行仍阻断自动投递。该修订仅作用于分类路由，不降低消化知识完整性要求，分数也不代表实测准确率。

实现、性能采样与未完成门槛见 [R15验收报告](Windows-资料归属纠正与自动投递-R15-验收报告-2026-10-13.md)，需要用户操作的项目见 [R15用户验收清单](Windows-资料归属纠正与自动投递-R15-用户验收清单-2026-10-13.md)。
