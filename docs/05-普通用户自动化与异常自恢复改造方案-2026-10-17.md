> 2026-10-18 授权恢复补记：R40 已持久保存 Codex、WorkBuddy 的授权描述及 WorkBuddy 独立登录目录，但任务合同有效期、页面按钮、授权版本递增和启动异步检查仍会制造“每次启动都要重新授权”的假象。下一 Windows 候选必须把“一次授权、后续自动复用；仅凭据明确失效时重新授权”作为 P0-A，不得把合同复核、CLI/模型版本变化或启动检查中的短暂状态当成账号退出。

## 一、结论

问题不是单纯“按钮太技术化”，而是许多系统可以继续处理的异常，被转换成了用户待办；另一些没有下一步自动动作的任务，却长期显示执行中或待处理。

改造目标：**系统先识别原因，在既有授权和预算内自动修复、核对、重试或切换；只有确实需要人的选择，或者适用的自动恢复措施已经用尽，才请用户接手。**

优先顺序：修复错误识别和队列状态 → 建立统一的有界恢复机制 → 接通资料、报告、项目、卡片和跨端流程 → 简化用户界面。不能仅改提示语、隐藏积压任务或扩大重试次数。

“自动补全”指补全可从可信记录确定的配置、元数据和合法输出结构，不是补造学生事实、能力证据或不存在的原始资料。涉及学生归属不明、首次授权、付费扩容、不可逆操作等真正需要用户决定的事情，不应先做无意义的自动尝试。

### 2.3 已确认的主要问题

#### F01：21 条空历史资料任务未被现有治理规则识别

这 21 条记录均为 `smart_material_intake`、pending、count=0、attempt=0，没有 executionId 或结果。来源同时包含顶层 `sourceId="system"` 和 `input.sourceId="legacy-download"`。

`electron/task-governance-policy.cjs` 的 `isLegacySmartInboxOrphan` 使用：

```js
String(task.sourceId || task.input?.sourceId || '') === 'legacy-download'
```

顶层 `system` 遮住了实际旧来源。对真实账本只读调用该谓词，命中 **0 条**；在内存副本中使用 input 来源再运行，命中 **21 条**。这是可复现的规则漏判，不是用户不会操作。

此外，`electron/main.cjs:25638` 的治理迁移在 version=1 时直接返回。真实账本已经记为 version=1、归档 0 条。因此只修谓词仍不足以修复既有积压，必须提供新版本、幂等、可回滚的重新核对。

实施要求：再验证这些任务没有实际关联资料、子任务、回执及正在运行的执行后，自动归档并记录原因，不删除资料、不伪造成功。不能把“count=0”单独作为清理所有任务的依据。

#### F02：4 条空项目待办与将来计划任务被混入“需要处理”

9 条 pending 项目任务中，4 条 count=0，说明为“当前没有待消化的项目资料”；另外 5 条有资料，其中一条计划时间为 2026-10-18 10:11:55（北京时间）。

当前空项目治理仅处理 queued，不包括这些 pending。`electron/task-read-model.cjs:8` 又将 pending/draft/approved 默认映射到 actionable，不先区分空闲、未到计划时间和正在自动恢复。

实施要求：项目无资料时回到“监测新资料”，未来计划显示预计启动时间，真正有执行条件且到期的任务进入调度。必须核对各项目自己的自动化配置，不能因全局开启而擅自开启所有项目。

#### F03：4 条心跳丢失记录的状态与文案不一致

涉及维护检查、学习画像、2 条内部研究任务。4 条均记录 `HEARTBEAT_LOST`，提示已请求停止但结果未确认；其中只有 2 条具有 `recoveryState=unknown`，另 2 条该字段为空。

当前展示规则依赖 recoveryState，因此同类未决任务会被分成不同的“执行中/需要处理”，还可能在展示层占用执行名额。实际底层资源是否仍被占用，不能仅凭这份账本断定。

实施要求：以 executionId、执行器查询、退出事件、回执、输出校验为依据自动核对；补齐统一恢复状态和持久化记录。先核对再决定是否重跑，不能只改成 failed，也不能将“没有心跳”当成“没有执行”。内部研究任务同样纳入恢复协议。

#### F04：3 条失败没有进入可继续处理的恢复流程

- 2 条报告被校验器拦截：把“观察项”写成正式能力结论。拦截正确，后续体验错误；`electron/task-resolution.cjs:16` 直接要求用户让原 Agent 修订。
- 1 条维护检查记录 `EXIT_0`，但未检测到合格新产物。进程退出成功不等于业务成功。
- 三条均未保存自动重试计划。

实施要求：报告将错误位置、证据 ID、来源版本和允许的表述反馈给生成器，进行有限修订，再交原校验器验证；不能放宽证据规则。缺少产物先核对输出目录、协议、回执和本批次文件，再决定重建，不能只重复整任务。

#### F05：至少一条“Agent 阻塞”实际是主机状态转换错误

任务 `task-project_digest-e0d6660077b4` 的错误为“不允许从 blocked 直接流转到 running”，却被包装为 `AGENT_ROUTE_BLOCKED`。

`electron/task-protocol.cjs` 要求合法状态转换；应修复调用方的恢复入口、前置校验及版本条件，不应要求普通用户更换 Agent，也不能开放任意状态跳转。

另外两条 blocked 记录虽 autoRetry=true，但没有 nextRetryAt；不能把这个布尔值当成自动恢复已安排。另有一条学生资料任务等待选择手工交接目标，需要核查为何未走合格自动通道。

#### F06：5 条任务停在人工交接，不能靠“等后台”完成

5 条 waiting_result 均为 manual 模式。某些记录曾出现自动工具候选，不能据此认定候选当时具备权限与能力。

实施要求：先核对是否已发送、是否已领取、是否有结果。若可靠证明未发送，且当前授权与资格允许，自动迁移到合格通道；若可能已发送，进入自动查结果流程。不可直接将这 5 条统一重新派发。

#### F07：部分失败会被推迟到下个完整周期

`electron/main.cjs:16114` 的项目周期扫描，无论本轮扫描/执行是否成功，都会更新下次运行时间，默认间隔 1440 分钟。

这意味着在缺少独立恢复计划时，一次可恢复启动失败可能等到下个日周期。应拆开“下次例行扫描”和“本次故障恢复”；恢复不能推迟或重置日常计划。

#### F08：旧路径修复存在误报和正文误改风险

此前对包晓闻知识库的只读核查发现：剩余 2 条“旧路径”是合法 `edu://` 被识别成 `u://`，不是两条真实失效主机路径；此前修复还影响了 AGENT.md 的 7 行正文，已有备份可对照恢复。

关联入口为 `electron/main.cjs:5994` 附近的路径提取及后续修复逻辑。路径模式把 URI 后缀当成盘符路径，并可能把反引号后的正文一起纳入替换。

实施要求：优先停止此类不安全替换；依据备份逐段恢复误改，保留修复后新增的合法内容；区分文件路径、URI、历史日志和说明文字。不能整体覆盖当前文档，也不能为消除告警创建空知识库冒充原资料。

#### F09：R40 持久化授权存在“重复授权”假象

R40 的 Codex、WorkBuddy 授权描述和 WorkBuddy 独立登录目录已经持久保存，跨重启并未自然丢失。问题在恢复状态和界面语义：任务合同验证约 30 分钟后进入 `qualification_required`；页面无论是否已经登录都显示“连接／授权”和“验证连接”；普通验证会先使授权失效并递增授权版本，从而连带使已保存的合同验证失效；启动时能力刷新异步触发，页面可能在检查完成前先显示待验证或待认证。

正确状态与动作必须分开：

| 状态 | 重启后应有行为 |
| --- | --- |
| 官方登录仍有效 | 先恢复持久化授权，后台健康检查；不打开登录页 |
| 任务合同验证过期 | 下一次相关任务前使用合成数据自动复核；不要求登录 |
| CLI／模型版本变化 | 只使受影响任务合同失效并重新验证；不使账号授权失效 |
| Token 过期、撤销或账号退出 | 收到明确 `AUTHENTICATION_REQUIRED` 后才提示重新授权 |
| LLM API 配置未变化 | 继续复用本机加密密钥；不把启动检查当成重新配置 |

实施要求：普通“验证连接”不得改变授权版本；只有更换账号、授权目录或明确撤销/重新授权时更新。任务不得在启动检查窗口内被误判为未授权；需要执行时先等待或自动完成健康检查和合同复核。

| Android 独立管理端 | 有独立任务策略与未知结果保护；中断/阻塞易归为 needs_user | 与主机共享恢复原因语义；先查网关请求与回执，避免要求用户填写技术核对说明 | `TaskCenterPolicy.kt`、`UnknownOutcomeRecovery.kt`、`StudentDigestOrchestrator.kt` |
| 云模型网关 | 有学生级授权、幂等键和 unknown 记录；不能据此假定所有供应商可查结果 | 补齐能力声明、请求状态查询与客户端对账；不支持查结果时如实保留未决状态 | `model-gateway-runtime.cjs`、`model-gateway-pilot.cjs` |
| 维护与诊断 | 有检查、日志和产物校验；用户被要求理解技术输出 | 自动收集脱敏诊断，展示“问题/影响/下一步”；日志默认折叠，不自动外发敏感档案 | `task-resolution.cjs`、`main.tsx` 维护入口 |

## 四、统一自动恢复流程

每次异常首先分类，不是机械地依次重试所有方案。

1. **确认现场**：固定学生、任务、输入版本、授权、业务键、执行批次及已发生副作用。
2. **判断是否结果未明**：若可能已发送或写入，先自动核对状态与回执，禁止并行重派。
3. **选择最小修复**：只修失败阶段；补确定元数据、修输出格式、续传、刷新已授权连接、等待资源等。
4. **按条件重试或切换**：仅在可证明安全、授权允许、候选具备该任务能力时执行，并受共享预算限制。
5. **重新验收**：检查身份、输入版本、证据、产物和实际写入结果，成功后才能关闭任务。
6. **安排下一步或请求帮助**：每个非终态必须有持久化 nextWakeAt/事件等待条件，或者明确、最小的用户动作；不能无期限挂一个“处理中”。

已知失败与未知结果采用不同路径：未知结果的自动化首先是“自动查明”，不是“自动再做一次”。若外部工具完全无法查询，不能假装所有自动核对均已成功；应给出已查项目、无法核实之处和风险明确的接手选项。

### 4.1 按原因处理

| 原因 | 自动处理顺序 | 何时需要用户 |
| --- | --- | --- |
| 唯一、可验证的新路径 | 验证目录身份与文件 → 备份配置 → 精确更新 → 复检 | 多候选、身份不一致或目录权限不足 |
| 同步未完成、文件暂不可读 | 查已有同步/可读状态 → 等待文件稳定 → 重试当前读取 | 长时间无进展或源文件确实缺失；不造空文件 |
| 缺少应用自有缓存/索引 | 在授权根内重建可派生文件 → 校验 | 原始资料缺失或无法确定所属学生 |
| 网络短断、429、服务繁忙 | 遵循 Retry-After、退避和事件唤醒 → 同一业务键重试 | 预算/期限耗尽，且没有可用已授权备选 |
| 本机资源不足 | 排队、降低批量、复用已完成步骤、释放已确认退出资源 | 持续资源不足，用户必须释放空间或更改策略 |
| 输出 JSON/结构不合规 | 确定性解析修复 → 带校验错误定点修订 → 原校验器复验 | 有限修订仍失败；不能降低验证标准 |
| 观察项写成能力定论 | 使用原证据修订为观察表述 → 验证证据关联及版本 | 需要补充事实/判断，而非用户修改 JSON |
| 单个文件损坏/格式不支持 | 安全解析器备选 → 跳过单项继续其他项 → 单项恢复 | 需要原件；明确展示部分完成，不标全成功 |
| 工具已失效/不支持该任务 | 在未发送证明下切换已授权、合格工具 | 没有合格工具或新增工具需要授权 |
| 任务合同验证过期、CLI/模型版本变化 | 保留账号授权 → 使用合成数据后台复核受影响合同 → 恢复原任务 | 自动复核仍返回明确认证失效或合同不兼容 |
| 启动健康检查尚未完成 | 先恢复持久授权并显示“正在检查” → 等待同一检查或事件唤醒 | 检查超时且自动诊断无法给出有效状态 |
| 令牌过期 | 在已有合法刷新机制内续期 → 恢复原任务；仅 `AUTHENTICATION_REQUIRED` 进入登录流程 | 账号退出、验证码、授权撤回或刷新失败等必须本人处理 |
| 输出在其他合法目录 | 按当前批次/产物清单查找 → 内容与身份校验 → 登记回执 | 无法证明属于本任务，不能拿旧文件充数 |
| 心跳丢失、崩溃、响应丢失 | 查请求、进程、回执和产物 → 接回结果或确认停止 | 现有手段无法核实；不得盲目切工具重做 |
| 账本并发冲突 | 读取新版本 → 合并本操作的必要变更 → 条件提交 | 多次冲突或业务身份变化；不能重跑模型解决存储冲突 |
| 空历史任务/重复记录 | 查关联对象与执行 → 有依据归档或合并视图 → 保留审计 | 关联关系冲突；不直接删除真实任务或资料 |
| 学生/项目归属不明 | 在授权范围内核对明确元数据与既有绑定 | 仍有多个合理候选时，请人选择；不能用另一学生资料推断 |
| 已取消、暂停、授权撤回 | 停止继续派发，接收并隔离必要的晚到结果 | 仅在用户明确恢复后重新评估 |

### 4.2 恢复预算与防止重复

- 每个逻辑任务共享总预算；切换工具、拆批、重启程序不能重置预算。单独记录执行次数、修订次数、切换次数、用时、费用和核对次数。
- 起始建议：保留现有网络恢复最多 3 次和约 1/5 分钟退避基础；草稿定点修订最多 2 次；备用切换最多 2 次。它们均受同一任务的总费用、总执行次数与截止时间约束，不是相互叠加的无限额度。最终值按任务类型和已有授权确定。
- 纯本地可逆修复、状态查询与付费模型调用分开计费/计次；降低批量不是免费无限重试。
- 只读核对可以先密后疏；长期未决采用持久等待和事件唤醒，达到核对期限后解释无法核实的原因，不能忙轮询。
- 稳定业务键建议包含学生、任务类型、目标、输入指纹与版本。executionId 表示单次执行；重新执行不能生成一个新业务身份来绕过重复保护。
- 派发意图先持久化，外部结果与业务验收再持久化；使用现有 Worker 和条件更新，在关键处等待 flush。业务“只生效一次”由幂等写入与回执核对保证，不能承诺网络调用天然只发生一次。
- 自动切换不能扩大数据出境范围、学生范围或付费权限。不同工具资格按“工具 × 任务类型”验证，不以“已安装”代替“可自动执行”。

## 五、普通用户界面

### 5.1 队列中心只突出三类

- **自动处理中**：包括排队、按计划开始、等待网络、自动修订、自动核对。显示实际原因、最近进展和下一次动作；没有恢复计划的任务不能放进来装作正在处理。
- **需要你帮助**：只包含真正需要决定/授权，或适用自动措施已耗尽的任务。自动失败过程留在详情，不为每次尝试弹窗。
- **历史记录**：区分已完成、部分完成、已取消、无需执行、已归档，不能把它们全部算“成功”。

用户可以查看进度、暂停、取消、修改范围；系统不能以减少人工干预为由隐藏控制权。

### 5.2 人工接手卡片

统一显示五项：要完成什么、为何需要你、系统已经尝试什么、你只需做什么、操作后系统会自动继续什么。

例：“有一份资料无法确定属于哪位学生。系统已核对文件信息和项目绑定，但仍有两个候选。请选择学生；选择后将自动继续整理。”

例：“需要重新登录学习助手。已完成的内容已保存。点击‘去登录’，登录成功后系统将核对旧任务并自动继续。”

对不支持查询旧执行的工具，必须说明“尚不能确认是否已完成”，不能将按钮写成无风险的“立即重试”。用户取消后，也不能自动再次提示派发。

### 5.3 文案与入口调整

| 当前技术化表达/操作 | 普通用户表达/操作 |
| --- | --- |
| 修复旧主机路径 | 自动找回资料位置 |
| 自动合同、Profile、资格探测 | 可自动完成的工作、检查是否可用 |
| 标准 JSON CLI、自定义命令 | 普通界面选已支持的工具；自定义接入放高级设置 |
| 粘贴 JSON、messageId、批次编号 | 自动接收结果；“导入结果文件”作为高级备用入口 |
| 请让原 Agent 修订报告 | 正在修订不符合证据要求的表述，完成后自动复核 |
| 采用成功但整理失败，请手动重试 | 分类已保存，系统将在连接恢复后继续整理（必须有真实计划） |
| 请核对原工具及回执 | 正在查找本次处理结果；无法自动核实时再提供具体接手步骤 |
| 点击重试上传，保留本页 | 已保存到待发送列表，恢复连接后继续（必须先持久保存） |

首次设置用一个业务化授权页说明：哪些学生、哪些任务、哪些工具、资料可到哪里、费用上限、哪些操作仍需确认。常规任务复用该范围；新增权限、扩费或跨学生必须重新授权。

Agent 卡片只显示“正在检查、已连接、等待自动复核、需要重新授权”四种普通状态。已连接时隐藏“连接／授权”，将“更换账号／重新授权”放入高级操作；“验证连接”只做只读健康检查和合同复核，不改变授权版本。启动恢复期间不得先显示需要登录再自动变为已连接。

## 六、实施拆分

### P0：先止损并校准现有积压

1. 修复 URI/路径误识别与跨正文替换；对包晓闻的 7 行误改提供逐段恢复预览、备份与复检。
2. 修复旧资料来源识别；新增版本化、幂等治理，核对后归档 21 条候选空历史任务。
3. 核对 4 条空项目任务，将无资料监测与用户待办分离；未来计划不显示催办。
4. 修复 blocked 恢复入口的状态转换，保持协议约束；补齐错误分类，不能继续冒充 Agent 故障。
5. 对 4 条心跳丢失记录建立只读自动对账结果，统一恢复字段；不能直接全量重跑。

验收：误报不再出现，正文未再被破坏；任务数变化能逐项解释；没有重复业务写入；旧任务不是凭 count 或状态被误删。

### P0-A：下一候选包的一次授权复用止损

1. 启动先读取并恢复 Codex、WorkBuddy 和 LLM API 的持久化授权/加密配置，再异步刷新健康状态；同一 provider 只运行一个共享检查。
2. 状态机明确区分 `checking`、`connected`、`qualification_pending`、`reauthorization_required`；只有明确 `AUTHENTICATION_REQUIRED` 才进入最后一种。
3. 已连接时隐藏普通“连接／授权”，在“高级 → 更换账号／重新授权”中保留显式入口。
4. 普通“验证连接”不得调用授权失效逻辑，也不得递增授权版本；只有账号、授权目录或真实凭据发生变化时更新版本。
5. 约 30 分钟合同验证到期，或 CLI/模型版本变化时，由下一次相关任务使用合成数据自动复核；复核前保存原任务且不打开登录页。
6. LLM API 配置指纹未变化时继续使用本机加密密钥；只有配置变更才重验受影响模型能力。
7. 增加退出/重启、合同过期、CLI升级、验证按钮、凭据撤销和启动竞态回归测试；不得重跑结果未知任务作为验证手段。

验收：有效登录跨重启直接恢复；合同过期和 CLI 变化只触发后台复核；普通验证不改变授权版本；明确撤销或账号退出才提示重新授权；自动恢复期间任务不会被误转人工，也不会扩大原学生、任务或数据授权范围。

### P1：把失败恢复变成主机的统一能力

1. 在现有 task store/retry queue/control plane 内增加原因分类、恢复动作、共享预算和下一步计划；不新建独立总队列。
2. 将存储冲突、资源等待、未发送、已发送未决、结构错误、证据错误、网络失败分别处理。
3. 报告定点自动修订；缺产物自动核对；仅失败步骤重试。
4. 引入执行器状态/回执查询能力声明，内部研究、CLI、云请求统一接入；不支持查询的通道明确标注限制。
5. 对 5 条手工交接逐条核对迁移条件；对 4 条 blocked 补具体原因和恢复计划。

验收：每个未结束任务均有自动下一步、合理等待条件或明确用户动作；重启后动作与预算继续有效；同一错误不会重复让用户点击。

### P2：贯通业务流程

1. 项目扫描与故障恢复分离；资料单项失败不阻塞整批，自动分类按授权及证据分级采用。
2. 报告、画像、选题、维护与学习卡片复用统一恢复策略；保持原业务校验和版本保护。
3. 云上传/分享、Windows/Web 会话提交、Android 学生/教师端提交贯通持久队列和回执。
4. Android 独立端与云网关补状态查询和幂等接回；系统授权、共享设备学生隔离不变。

验收：从收到资料到产物可用的整条流程能在断网、失联、部分失败及重启后接续，而非只通过单个函数测试。

### P3：统一用户体验并长期观测

1. 三类队列视图、业务化接手卡片、默认折叠技术日志、按原因合并提醒。
2. 明确批量暂停/取消、纠错、撤销、授权管理；帮助页按实际按钮名称编写。
3. 上线恢复率、人工介入率、重复副作用、最长无进展时间与通知量指标。

建议每阶段独立形成可回滚候选包并进行真实主机验收，再推进下一阶段。工作区已有大量其他未提交变更，实施时需先固定基线、明确修改文件，不应整体覆盖现有文件。这里不承诺未经估算的交付日期。

## 七、对这 58 条未完成任务的处理计划

| 当前集合 | 下一步 | 禁止的捷径 |
| --- | --- | --- |
| 21 条旧资料空任务 | 验证无关联执行/资料后，版本化归档并保存清单 | 直接删除，或改成功 |
| 4 条空项目 pending | 核对项目真实待处理量与绑定，转空闲监测/有依据归档 | 对所有 count=0 一刀切 |
| 其余 15 条 pending | 按授权、计划时间、输入变化、资源条件判定；有工作则自动安排 | 全部当“需要用户确认”，或忽略计划立即执行 |
| 4 条心跳丢失 running | 查执行、回执、输出，补统一未决状态；查明后接回或安全恢复 | 重派所有任务或强行标完成 |
| 另 1 条资料 running | 检查该任务自身的最新进度、子任务和回执，不依据账本时间独断 | 与陈旧失联记录一起清理 |
| 5 条 manual waiting_result | 核对发送/领取/结果；证明未发送且有合格自动工具再迁移 | 直接切工具，造成双重执行 |
| 3 条 failed | 2 条报告定点修订并复验；1 条查产物与协议 | 放宽证据校验，或反复跑整个任务 |
| 4 条 blocked | 修状态入口、核对交接，补齐另两条结构化原因及下一步 | 单改 autoRetry=true |
| 1 条 queued | 校验调度条件与资源等待；符合条件自动启动 | 将正常排队转人工催办 |

这些集合合计 58 条。21+4 是待业务核对的减负候选，不是本次已经清理的结果；也不能承诺“54 条待处理必定减少到某个数字”。真实有工作、未决风险和用户决策必须保留可见。

## 八、验收与观测

### 8.1 必测场景

1. `edu://`、https URL 不被当盘符路径；反引号后的中文说明不被替换。
2. 含空格、中文、UNC 的合法路径正确识别；历史引用与当前配置分离。
3. 恢复误改时保留后来新增内容；中途失败可回滚。
4. 顶层 system 与 input legacy-download 同时存在时正确识别；有执行/结果/关联资料时不自动归档。
5. 既有 version=1 迁移能被新版安全处理；重复启动不会重复归档或丢日志。
6. 空项目进入监测；未来计划不提前执行；关闭自动化的项目不擅自启用。
7. blocked 合法恢复路径成功；未授权仍拒绝。
8. 网络、429、资源忙按对应策略恢复；等待资源不消耗模型重试额度。
9. 工具切换/程序重启不能重置总预算；不合格或未授权工具永远不成为自动备用。
10. Agent 已接受请求但宿主断线：先查结果，不双发；查询不支持时明确未决。
11. 内部研究任务中断同样可核对；不长期伪装执行中。
12. 本地进程退出 0 但无产物：不认成功；旧产物或别的学生产物不被接回。
13. 报告把观察写成能力：自动修订但不能放松验证；两次仍不合格才按预算升级处理。
14. 修订期间用户改输入/编辑结果：旧输出不得覆盖新版本。
15. 一批资料一个坏文件：其余完成，坏文件单独恢复；准确显示部分完成。
16. 并发写账本冲突：只重试合并提交，不重复模型调用；必须验证真实 Worker/flush 链路。
17. 派发前后各断电一次：意图、预算、回执、恢复动作持久，业务结果不重复落地。
18. 手工已发送但未领取确认：不得因无 claimedAt 就推断未发送。
19. 取消/暂停/撤权后收到迟到结果：不重新启动、不越权写入。
20. 云端已收件但客户端丢响应：根据幂等键接回，不重复上传或发布。
21. Android/Web 关闭页面或进程重启：已受理提交可继续；学生切换不改变原任务目标。
22. 主机备份恢复造成版本回退：不能自动重放已执行的跨端命令。
23. 普通用户完成登录后自动接续，不要求输入命令、JSON 或查找 executionId。
24. 用户待办仅在确需决定或恢复耗尽时出现；详情可看到真实尝试和下一步。
25. 多学生并发、跨项目及健康/教育领域数据不得混写、越权切换或共用错误证据。
26. 官方登录仍有效时关闭并重启程序：直接恢复为“正在检查/已连接”，不打开官方登录页，不阻止已授权任务。
27. 任务合同超过有效期：下一次相关任务使用合成数据自动复核，授权版本和账号状态保持不变。
28. CLI 或模型版本变化：只重验受影响合同，其他合同和已保存授权不失效。
29. 连续点击普通“验证连接”：不递增授权版本，不形成合同验证失效循环，并合并并发检查。
30. Token 撤销、账号退出或刷新失败返回 `AUTHENTICATION_REQUIRED`：才显示“需要重新授权”，且不自动重派正在核对结果的任务。
31. LLM API 配置未变化时重启继续使用本机加密密钥；配置指纹变化后只重验受影响能力，不暴露密钥。

测试层级必须包括：纯函数单测 → 状态/账本 Worker 集成 → 可控故障注入 → Windows 真实候选包 → Android 真机与云端联调 → 真实日常任务观察。源码检查、单测、构建成功、安装成功均不能代替最终业务验收。

### 8.2 指标定义

- 自动恢复成功率：可自动恢复异常中，在预算内自动完成且通过业务验收的比例；分原因统计。
- 人工介入率：具有有效工作量的任务中，确实需要用户操作的比例；首次授权、必要业务决策与可避免的技术操作分开统计。
- 无进展时长：从最后有效进展到现在，不以写心跳或刷新 updatedAt 冒充进展。
- 重复副作用、跨学生写入、未授权外发：验收必须为 0。
- 预算与通知：每任务总费用、模型尝试数、提醒数；归档空任务不能被统计成自动成功。
- 可设“常见可恢复故障自动恢复率 ≥95%”为试点目标，必须预先定义故障集合与样本量；这不是当前已实现结果。
