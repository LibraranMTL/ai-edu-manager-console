# AI教育管家屏幕连续采集学习时间线优化方案

> 文档日期：2026-09-12
> 适用范围：Windows 主机端、Windows 学生端的授权屏幕连续采集
> 方案状态：P0 性能底座已实现；0.17.8 真机功能验收未通过；P1 已于 2026-09-12 完成本地候选实现和自动化测试，尚待 Windows 主机端与学生端双机真机验收
> 参考产品：[Meridian](https://meridiona.com/)

> **P1 处理顺序修订（2026-09-12）**：用户反馈现有 OCR 候选时间线信息量不足。后续实施以[《屏幕采集“消化优先”与双报告闭环修改方案》](./屏幕采集消化优先与双报告闭环修改方案.md)为准：取消消化前必须先 OCR 的路径，正式消化后生成时间线与按时间统计报告。下文关于“先 OCR 再晋升”的步骤仅作为旧候选实现记录，不再作为新的交付要求；现有 P1 候选包尚未通过修订后的内容质量验收。

## 1. 执行摘要

在现有“连续屏幕采集 → 去重 → 资料晋升 → 消化 → 知识沉淀”流程中增加 AI Memory 学习时间线，技术上可行。P0 已验证事件索引、分页、缩略图和长列表性能底座，但 0.17.8 真机测试证明：仅把缩略图按时间排列不能构成 AI Memory，也不能作为学习时间线功能完成的验收依据。

推荐新增的不是传统视频回放器或截图图库，而是“学习活动与记忆时间线”：系统应先识别截图内容，再按时间、主题和学习动作将相邻证据组织为少量活动段，形成当日学习摘要、知识状态变化和指导响应。缩略图只作为可展开的证据，不作为默认信息主体。用户可以回到某一天、某个时间段或某次课程，直接理解当时发生了什么、学到了什么、遇到了什么问题，以及后续形成了哪些知识和学情结论。

方案应遵守以下判断：

1. 当前连续采集以定时或内容变化触发的截图为主，不是持续视频文件，因此产品默认呈现应为“活动段 + 记忆摘要 + 知识状态 + 证据链接”，而不是缩略图序列。
2. 截图产生后立即建立不可变事实索引；AI 未完成时可以查看事实层，但界面必须标记“待识别”，不能把事实层称为已完成的 AI Memory。
3. 学习时间线预处理与原始资料库消化共用同一证据链、同一识别缓存；OCR 和视觉识别原则上只运行一次。
4. 时间线预处理生成的是候选解释，不得直接更新正式知识、成长模型或学情报告；正式知识只由资料晋升后的消化流程产生。
5. 正式消化必须通过稳定 ID 和回执反向增强活动段，使每条知识状态和指导响应都能回到具体时间段与截图证据。
6. 时间线不能被设计成无提示的全天候监控工具。
7. 分页、缩略图、虚拟列表、低优先级后台任务和可恢复队列是功能上线的前置条件。
8. 独立处理进程、全系统统一重任务调度、两阶段活动分段、统一内容哈希和增量搜索索引是 P1-A 的强制架构，不是后续可选优化。
9. 单张截图、单个活动段或单项派生任务失败只能隔离对应单元，不能阻断同一会话中的其他有效内容，也不能阻断采集、资料上传、知识同步和学情报告。
10. 瞬时后台失败必须自动退避、降级和恢复，不要求用户通过“审核”“确认”或“继续处理”按钮维持正常流程。
11. 重任务并发由系统根据采集状态、前台响应、供电和资源压力自动调整，普通用户不需要理解或配置线程、队列和性能模式。

综合建议：保留 P0 作为事实层和性能底座，但不再单独作为学习时间线正式功能发布；P1 必须同时完成语义活动段、统一识别缓存、会话资料包、消化回执反向关联、知识状态与指导响应，达到 AI Memory 的最低可用定义后再进行功能验收。暂不实施视频化回放、注意力监控和复杂行为评分。

## 2. 背景与目标

### 2.1 当前业务链路

AI教育管家现有屏幕资料采集流程主要包括：

```text
用户主动开始采集
→ 按固定间隔、内容变化或智能混合策略检测画面
→ 保存有效截图并跳过重复画面
→ 形成采集候选会话
→ 晋升到学生或项目原始资料库
→ 进入资料消化和知识沉淀
→ 为成长模型、学情报告和教育档案提供依据
```

这一链路能够保存和消化资料，但用户目前主要按“采集会话”和文件目录查看，难以快速回答以下问题：

- 某一天的学习过程是怎样展开的？
- 某个问题最早在什么时间出现？
- 哪些截图对应最终生成的知识卡片或学情结论？
- 某次课程中哪些阶段是阅读、练习、修改和产出？
- 报告中的结论能否回到具体过程证据？

### 2.2 优化目标

新增时间线后，应实现：

- 自动按时间组织采集记录，减少用户手工整理；
- 支持按学生、日期、课程、项目和会话回看；
- 将大量相邻截图压缩为少量可理解的学习活动段；
- 让知识资产、成长模型和学情报告能够回到原始过程依据；
- 保持学生边界、授权边界和本地数据治理不变；
- 在低配置 Windows 设备上保持可接受的采集和浏览性能。

### 2.3 非目标

本方案不建设以下功能：

- 无提示、全天候屏幕监控；
- 键盘输入、密码、私聊等敏感内容采集；
- 摄像头表情、情绪、视线或所谓专注度检测；
- 仅凭窗口停留时间判断学生是否掌握知识；
- 将全部截图制作成高帧率视频；
- 自动把 AI 推断直接写成正式学情结论；
- 默认跨设备同步原始截图和敏感窗口标题。

### 2.4 2026-09-11 真机反馈与修订结论

Windows 0.17.8 候选包在真机上能够稳定按时间显示缩略图，但没有进行内容识别、活动归并、学习总结和知识状态关联。因此：

- P0 的性能和事实索引验证保留有效；
- P0 的产品功能验收不通过，0.17.8 不转为正式学习时间线版本；
- P1 不再定义为“给缩略图增加标签”，而是完整的 AI Memory 语义处理闭环；
- 默认界面从截图卡片列表改为活动段和记忆摘要，缩略图退居证据详情；
- P1 必须与原始资料库消化打通，避免两套 AI 重复识别、重复消耗和结论冲突。

### 2.5 2026-09-12 性能评估与修订结论

P1 的主要性能风险不在事实索引，而在 OCR、图像解码、视觉模型、会话摘要、全文搜索与正式消化同时争用 Electron 主进程、CPU、内存和磁盘。仅使用 `setImmediate`、定时器或“低优先级”标记不能构成真正的进程隔离，也不能保证前台不卡顿。

因此，P1 实施前必须满足五项架构约束：

1. OCR、图像处理、视觉识别和大结果解析移出 Electron 主进程，由独立工作进程执行；
2. 时间线识别、资料消化、报告生成和 Agent 后台任务共用一个全系统重任务调度器，不能各自维护互不感知的队列；
3. 先用时间、来源和画面差异做低成本初分段，再只识别关键帧并局部修正边界，禁止全量截图先 OCR 后分段；
4. 统一复用资产层已有内容哈希，禁止为时间线在采集主路径同步重读图片并再次计算 SHA-1/SHA-256；
5. OCR、主题和知识概念搜索使用按变更更新的增量索引，禁止打开页面或启动程序时扫描全部识别 JSON。

这五项约束必须先于候选摘要和知识状态界面开发落地。否则即使功能正确，也不得进入真机发布验收。

此外，P1 的自动化流程必须满足三项运行不变量：

- **局部失败不阻断整体**：处理结果按截图、活动段和知识关联分别提交，校验失败只隔离对应对象；
- **后台失败不要求人工恢复**：可恢复错误自动重试，持续错误自动降级并进入低频恢复队列，人工入口仅用于诊断或提前重试；
- **自动自适应并发**：采集时停止重计算，前台活跃时保持单任务，设备插电且持续空闲、资源充足时可自动提升到两个互不依赖的重任务。

## 3. 参考产品评估

Meridian 的核心价值不是简单截屏，而是自动还原一天的活动，支持回到任意日期、搜索历史和理解时间去向，并强调数据在本机处理、可暂停、可排除应用和可删除。

适合借鉴的能力包括：

- 自动形成每天的活动记录；
- 按日期和时间回到过去；
- 把零散活动组织成有意义的工作段；
- 支持搜索和定位具体依据；
- 将事实记录与后续总结结合；
- 提供暂停、排除和删除等隐私控制。

不宜直接照搬的能力包括：

- 面向职场的任务和项目管理表达；
- 将应用使用时间等同于有效工作时间；
- 面向项目经理的工作进度发布机制；
- 不适用于未成年学生的长期被动行为跟踪。

教育管家中的适配应从“工作日志”转变为“学习活动与证据时间线”。

| 参考能力 | 教育管家适配 |
| --- | --- |
| 自动记录一天做了什么 | 自动记录一次授权学习采集中的活动 |
| 回到任意日期 | 按学生、日期、课程和项目回看 |
| 工作任务与切换 | 阅读、练习、编程、写作、项目产出等活动段 |
| 决策与证明 | 学习问题、关键操作、成果和原始证据 |
| 本地隐私控制 | 本地索引、排除窗口、暂停、删除和保留期限 |
| 工作总结 | 学习摘要、知识沉淀和学情报告依据 |

## 4. 当前系统基础与差距

### 4.1 已具备的数据基础

Windows 主机端的采集会话已保存：

- 学生 ID 和学生姓名；
- 项目 ID 和项目名称；
- 课程 ID、名称、提供方和课程地址；
- 采集来源、来源类型和会话起止时间；
- 截图数量、检测数量、去重数量和重点数量；
- 每张截图的 `capturedAt`、保存原因、变化程度、重点标记和归档状态；
- 原始截图路径、资产 ID、采集会话 ID 和采集项 ID。

这些字段足以建立按时间排序的基础时间线，不需要重新采集历史图片。

现有智能采集策略已经提供：

- 固定间隔；
- 内容变化；
- 智能混合；
- 完全重复画面过滤；
- 最短和最长保存间隔；
- 用户主动重点截取。

这些结果可直接用于时间线上的“普通记录、内容变化、定时保留、手工重点”等标记。

### 4.2 当前产品差距

P0 已补齐截图级浏览、日期索引、分页、缩略图和原始采集时间，但真机反馈确认仍缺少：

- 相邻截图的活动段聚合；
- 关键帧 OCR、视觉识别及按图片哈希复用的识别缓存；
- 当日学习摘要、知识状态变化和指导响应；
- 时间线候选解释与正式知识结论之间的权威边界；
- 会话级资料包，当前晋升仍会把每张截图分别复制进原始资料库并逐条进入待消化队列；
- 正式消化回执与时间段之间的双向来源关系；
- 原始候选、关键证据帧、正式资产和长期语义记忆之间的保留策略；
- AI 失败、资料未晋升和消化未完成时准确、可见的降级状态。

### 4.3 当前性能风险

现有主机端每次保存截图时会执行截图获取、特征计算、PNG 编码、同步文件写入、资产登记、采集会话 JSON 更新和界面通知。

同时存在以下潜在放大因素：

- 采集会话数据以完整 JSON 文件读写；
- 单个会话最多可保存大量截图条目；
- 采集中心状态可能返回多个包含完整截图条目的会话；
- 前端采集页面存在定期刷新；
- 原图如果直接进入时间线，会产生较大的图片解码和内存压力。

因此，时间线不能直接建立在“返回全部会话和全部截图”的现有状态接口上。

## 5. 产品设计

### 5.1 功能名称

普通用户界面建议使用：

- 一级名称：`学习时间线`
- 辅助说明：`按时间回看采集过程、关键页面和知识成果`

不建议使用“行为监控”“学生监控”“屏幕追踪”等表达。

### 5.2 入口设计

在“屏幕资料采集”区域增加视图切换：

```text
[采集会话] [学习时间线]
```

也可以在学生档案中提供只读入口：

```text
学生档案
├─ 资料
├─ 学习时间线
├─ 知识与成长
└─ 学情报告
```

时间线默认进入当前学生的最近一天，不要求用户重新选择归属。

### 5.3 时间线层级

时间线分为三层：

#### 第一层：日期概览

显示：

- 日期；
- 有记录的时间范围；
- 当日学习记忆摘要；
- 主要学习主题与活动段数量；
- 已识别的知识进展、问题和成果；
- 已正式确认的知识状态变化；
- 基于正式知识生成的下一步指导响应；
- 采集会话与关键证据数量；
- 涉及课程和项目；
- 识别、晋升、消化和知识关联状态。

日期概览中的候选观察和正式知识必须分区显示。没有正式消化回执时，可以展示“今天进行了哪些活动”的候选记忆，但不能显示为已经掌握、能力已经提升或正式教学建议。

#### 第二层：活动段

将相邻截图组合成活动段，例如：

```text
19:02—19:18  数学课程：二次函数
阅读课程内容 · 4个关键页面 · 已消化

19:18—19:31  练习与订正
题目与答题页面切换 · 发现1个待关注问题

19:31—19:36  Agent辅助分析
关联1次已授权Agent会话 · 已形成知识卡片
```

活动段是时间线默认列表单位。一个活动段可以引用多张截图，但默认只显示时间范围、主题、摘要、知识状态和处理状态；缩略图不在列表中逐张展开。

#### 第三层：证据详情

点击活动段后显示：

- 关键截图缩略图；
- 精确采集时间；
- 截图来源；
- 保存原因；
- 用户重点标记；
- OCR 文本摘要；
- AI 活动判断和置信度；
- 对应的知识卡片、资料消化结果和学情报告依据；
- 查看原图、打开正式资产、删除临时副本等操作。

### 5.4 筛选与搜索

P0 支持：

- 日期；
- 课程；
- 项目；
- 采集会话；
- 全部、重点、已晋升、待处理；
- 采集来源类型。

P1 支持：

- OCR 文字搜索；
- 活动主题搜索；
- 知识概念搜索；
- “只看形成知识的活动”；
- “只看被报告引用的活动”。

### 5.5 自动化原则

为减少用户操作：

- 用户只负责主动开始和结束授权采集；
- 时间线自动创建，不增加“生成时间线”按钮；
- 缩略图和基础分组由后台自动完成；
- 消化完成后自动补充语义活动段；
- 已有学生、课程和项目归属自动沿用；
- 正常流程不要求逐张审核；
- 单张截图、单个活动段或单项知识关联失败时自动隔离，不暂停其余有效内容；
- 瞬时处理失败自动恢复，不弹出要求用户维持流程的确认框；
- 敏感内容优先自动排除、遮蔽或降级，只有学生归属、授权或安全边界无法自动确定且继续处理会扩大风险时才提示用户；
- 后台性能参数自动选择，不向普通用户增加并发、批次、重试或队列设置；
- 后台状态按会话汇总为非模态信息，不对每个失败单元弹窗；只有 `requiresUserAction=true` 时显示一条可处理通知。

时间线统一使用以下自动状态链，避免用户在时间线和资料消化之间重复操作：

```text
已采集
→ 识别中
→ 已组织为活动段
→ 已进入原始资料库
→ 消化中
→ 已形成知识
→ 已用于知识状态与指导响应
```

资料尚未晋升时，活动段可以显示候选摘要，但必须明确标记“已整理，尚未进入知识库”。只有正式消化完成并通过自动回执校验后，才能显示“已形成知识”。这里的“校验”是系统自动执行的身份、来源和完整性校验，不是人工审核，也不要求用户点击通过。

## 6. 数据模型

### 6.1 采集事件 CaptureEvent v1

每张有效截图对应一个不可变的基础事件：

```json
{
  "schema": "edu-manager.capture-event.v1",
  "eventId": "capture-item-...",
  "sessionId": "capture-...",
  "studentId": "student-...",
  "projectId": "project-...",
  "courseId": "course-...",
  "capturedAt": "2026-09-10T11:20:30.000Z",
  "sourceType": "window",
  "sourceName": "已脱敏的来源名称",
  "trigger": "visual_change",
  "difference": 0.18,
  "highlighted": false,
  "imageRef": "受管文件引用",
  "thumbnailRef": "缩略图引用",
  "archiveStatus": "candidate",
  "privacyState": "normal"
}
```

基础事件中的时间、归属、来源和原始引用不得被 AI 修改。

### 6.2 活动段 TimelineSegment v1

活动段是可重新生成的语义层：

```json
{
  "schema": "edu-manager.timeline-segment.v1",
  "segmentId": "segment-...",
  "studentId": "student-...",
  "sessionId": "capture-...",
  "startedAt": "2026-09-10T11:20:30.000Z",
  "endedAt": "2026-09-10T11:35:10.000Z",
  "category": "practice",
  "topic": "二次函数练习与订正",
  "candidateSummary": "从题目页面切换到作答和订正页面。",
  "formalSummary": "",
  "confidence": 0.78,
  "sourceEventIds": ["capture-item-1", "capture-item-2"],
  "keyEventIds": ["capture-item-2"],
  "recognitionStatus": "completed",
  "archiveStatus": "candidate",
  "digestStatus": "not_submitted",
  "digestBatchId": "",
  "knowledgeState": "candidate_observation",
  "generatedAt": "2026-09-10T12:00:00.000Z",
  "generator": "timeline-digest-v1"
}
```

活动段必须保留来源事件列表和生成信息，允许在算法升级后重新生成。`candidateSummary` 是时间线预处理产生的候选解释；`formalSummary` 只能由已校验的正式消化回执写入，二者不得相互冒充。

### 6.3 识别缓存 RecognitionArtifact v1

OCR 与视觉识别结果按学生和图片内容哈希保存，供时间线与正式资料消化共同复用：

```json
{
  "schema": "edu-manager.timeline-recognition.v1",
  "studentId": "student-...",
  "sourceEventId": "capture-item-2",
  "hashAlgorithm": "sha1",
  "contentHash": "...",
  "recognitionStrategyVersion": "timeline-recognition-v1",
  "ocrText": "题目与作答内容……",
  "pageType": "exercise",
  "visualSummary": "二次函数选择题及手写订正",
  "confidence": 0.86,
  "model": "configured-vision-model",
  "createdAt": "2026-09-10T12:00:00.000Z",
  "lastAccessedAt": "2026-09-10T12:00:00.000Z",
  "referenceCount": 1,
  "retentionState": "referenced"
}
```

同一学生、同一哈希算法、同一内容哈希、同一识别策略版本只处理一次。`contentHash` 直接复用资产层已经持久化的哈希，并用 `hashAlgorithm` 区分算法；旧资产只有 SHA-1 时先作为兼容键，需要升级 SHA-256 时由后台工作进程异步完成，不得在采集主路径再次同步读取原图。缓存属于候选处理产物，不直接成为正式知识；识别失败时记录失败状态和重试时间，不以空文本冒充成功。

### 6.4 会话资料包 SessionMaterialBundle v1

采集资料晋升时，不再把每张相似截图作为独立消化任务，而是生成一个会话级资料包：

```json
{
  "schema": "edu-manager.capture-session-material-bundle.v1",
  "bundleId": "capture-bundle-...",
  "studentId": "student-...",
  "projectId": "project-...",
  "sourceSessionId": "capture-...",
  "sourceEventIds": ["capture-item-1", "capture-item-2"],
  "keyFrames": [
    {
      "eventId": "capture-item-2",
      "assetId": "asset-...",
      "hashAlgorithm": "sha1",
      "contentHash": "...",
      "recognitionRef": "recognition/...json"
    }
  ],
  "segmentIds": ["segment-..."],
  "status": "pending_digest",
  "digestBatchId": "",
  "createdAt": "2026-09-10T12:03:00.000Z"
}
```

原始资料库至少保存资料包清单、可读的会话摘要和需要长期留存的关键证据帧。普通重复截图继续由采集证据区按保留策略管理，不逐张进入 Agent 消化上下文。

### 6.5 知识关联 KnowledgeLink v1

时间线与知识系统之间只保存引用关系：

```json
{
  "schema": "edu-manager.timeline-knowledge-link.v1",
  "linkId": "timeline-link-...",
  "studentId": "student-...",
  "segmentId": "segment-...",
  "digestBatchId": "digest-...",

  "targetId": "asset-...",
  "relation": "source_evidence",
  "createdAt": "2026-09-10T12:05:00.000Z"
}
```

可支持的目标包括：

- 消化结果；
- 知识资产；
- 学习项目成果；
- 成长模型证据；
- 学情报告中的某条引用。

知识关联只能依据通过校验的消化回执创建。时间线候选摘要可以提前显示，但不能在没有 `digestBatchId` 和正式目标 ID 的情况下伪造知识关联。

P0 不引入新的数据库或常驻服务，使用按学生、按日期拆分的受管索引：

这样可以避免每次更新一张截图时重写包含所有历史会话的单一大型 JSON 文件。`search` 只保存可重建的倒排索引或 SQLite FTS 元数据，不保存图片二进制；按学生隔离，并只更新发生变化的活动段。

## 7. 处理流程

### 7.1 采集阶段

采集阶段只执行低成本操作：

1. 获取屏幕或窗口图像；
2. 计算画面变化并去重；
3. 保存符合策略的原始截图；
4. 追加不可变时间事件；
5. 更新会话计数；
6. 通知前端有增量变化。

采集阶段禁止执行：

- OCR 全量识别；
- 大模型摘要；
- 全量历史索引扫描；
- 大量缩略图同步生成；
- 将全部会话重新发送给前端。

### 7.2 采集结束后的后台阶段

```text
采集结束
→ 生成缺失缩略图
→ 第一阶段按时间间隔、来源变化和画面差异进行 O(n) 初分段
→ 每段选择有限关键帧
→ 使用资产 contentHash 查询识别缓存
→ 仅对未命中的关键帧执行 OCR/视觉识别
→ 根据关键帧文字和语义相似度局部修正相邻段边界
→ 生成候选活动主题、摘要和当日记忆
→ 更新活动段、处理状态和当日时间线索引
```

后台任务应：

- 低优先级运行；
- 每批处理有限数量的截图；
- 可暂停、可恢复、可幂等重试；
- 检测到用户交互或采集开始时自动降速；
- 采集结束后等待 30～60 秒稳定窗口；窗口内出现新截图时延后处理，避免同一会话反复启动；
- 单个会话最多选择 20 张关键帧，超过后按活动段重要性和时间覆盖率取样；
- 单张关键帧识别失败时保留事实层并标记“待识别”或“识别失败”，其余关键帧和活动段继续处理；
- 会话摘要失败时仍保存已完成的活动段，后续异步补齐摘要，不回滚已提交结果；
- 任一派生任务失败均不阻断资料晋升、知识同步和学情报告已有数据的读取或更新；
- 不在本阶段直接写入知识资产、成长模型或学情报告。

### 7.3 资料晋升与会话资料包

资料晋升应由“逐张截图复制并逐张消化”改为“会话资料包一次晋升”：

1. 使用 `captureSessionId` 锁定会话和学生归属；
2. 复用已经生成的活动段、OCR 和视觉识别缓存；
3. 选择每个活动段 1～3 张关键证据帧；
4. 在学生或项目原始资料库写入一个资料包清单和一份可读会话摘要；
5. 只将关键证据帧作为正式图片资产长期保留，普通重复截图不逐张进入消化上下文；
6. 用 `sourceEventIds`、`assetId` 和图片哈希记录完整来源链；
7. 整个会话资料包只生成一项 `pending_digest` 记录和一个幂等键。

资料包由采集结束事件自动晋升，进入原始资料库后，时间线状态自动变为“已进入资料库”。正常流程不要求用户逐张确认。关键证据缺失时仅将对应活动段标记为“证据不完整”，并使用其余有效内容继续晋升和消化；敏感内容优先自动排除或遮蔽。只有学生/项目归属无法确定、授权失效或继续处理可能突破安全边界时，才暂停受影响资料包并提示用户，其他资料包继续运行。

### 7.4 正式消化与回执反向增强

正式资料消化只处理会话资料包，不再次识别同一关键帧。Agent 或本地消化引擎应读取：活动段、OCR 文本、关键证据帧、已有知识和当前学生规则，输出带来源 ID 的正式结果。

消化回执至少包含：

- `bundleId`、`sourceSessionId` 和 `digestBatchId`；
- 实际处理的 `segmentIds`、`sourceEventIds` 和关键 `assetIds`；
- 新增或更新的知识资产 ID；
- 知识状态变化及其证据；
- 指导响应及其适用时间范围；
- 无法确认、证据不足或需要继续观察的项目。

回执按活动段和知识关联分别执行学生、批次、来源和内容哈希自动校验。通过的部分立即提交并反向增强时间线，不等待整个会话全部通过：

- `formalSummary` 覆盖展示优先级，但保留候选摘要和生成记录；
- 关键问题链接到对应知识条目；
- 产出链接到学习项目成果；
- 成长模型证据可以回到具体时间段；
- 学情报告引用可以打开对应活动段和关键截图。

校验失败的活动段或知识关联进入隔离区，保留错误原因、原始回执和重试状态；不得回滚同批次已经通过的结果，也不得阻断其他活动段继续形成知识。知识状态与指导响应只能来自通过自动校验的正式消化结果。未晋升、尚未消化或被隔离的时间线活动只能显示“候选观察”，不得更新学生的正式能力判断和学情报告。

### 7.5 幂等、复用与旧数据兼容

- 识别幂等键：`studentId + hashAlgorithm + contentHash + recognitionStrategyVersion`；
- 活动段幂等键：`studentId + sourceSessionId + segmentStrategyVersion + sourceEventIdsHash`；
- 资料包幂等键：`studentId + sourceSessionId + bundleVersion + keyEventIdsHash`；
- 正式消化继续使用现有 `digestBatchId` 和资料哈希校验；
- 重跑时间线只能替换可重建语义层，不修改原始时间、截图或既有正式知识；
- 对已经逐张晋升的旧截图，按 `captureSessionId`、`captureItemId`、`assetId` 和 SHA-1/SHA-256 聚合为兼容会话资料包，不再次复制物理文件；
- 正式消化已完成的旧资料优先复用现有回执和知识产物，不重复提交。

### 7.6 Windows 学生端接入

Windows 学生端当前上传数据已包含采集会话 ID、采集项 ID、课程起止时间等信息。为确保跨设备时间线准确，需要补充：

- 每张截图的明确 `capturedAt`；
- 采集来源的受控分类；
- 可选的已脱敏窗口名称；
- 重点标记；
- 本地去重结果；
- 原始采集顺序号。

主机收到学生端截图后应使用原始采集时间排序，不能使用上传完成时间代替学习发生时间。

### 7.7 非阻塞失败与自动恢复

异常处理采用“最小隔离单元”原则：截图识别错误隔离截图，活动归并错误隔离活动段，知识回链错误隔离知识关联；除归属、授权和安全边界外，不允许把局部错误升级为整个会话、整个学生或全局队列暂停。

任务状态至少区分：

```text
pending → running → completed
                  ↘ partial_completed → retry_scheduled → completed
                  ↘ degraded → recovery_scheduled
                  ↘ blocked_by_identity_or_security
```

- `partial_completed`：部分结果已提交，失败单元继续后台恢复；
- `retry_scheduled`：短期瞬时错误，最多 3 次指数退避重试；
- `degraded`：连续失败后保留事实层或候选结果，不占用前台和高优先级队列；
- `recovery_scheduled`：系统在网络、模型服务或资源恢复后进行低频自动探测和重试；
- `blocked_by_identity_or_security`：仅用于无法自动确认学生归属、授权有效性或安全边界的情况，此时才需要用户处理。

普通处理失败不弹模态对话框。“立即重试”可以作为诊断和提前恢复入口，但绝不能成为流程继续运行的必要步骤。自动恢复必须保存幂等键和已完成单元，禁止重试时重复生成活动段、资料包、知识资产或报告引用。

## 8. API 与模块设计

### 8.1 不应继续扩大的接口

现有 `getCaptureCenterState` 适合显示概览，但不应继续承担完整历史时间线传输。概览接口只应返回：

- 当前活动会话；
- 最近会话摘要；
- 数量和状态；
- 不包含完整截图数组。

### 8.2 建议新增的主进程接口

```text
getCaptureSessionSummaries(filters, cursor, limit)
getCaptureTimeline(studentId, date, cursor, limit)
getCaptureTimelineDates(studentId, month)
getCaptureTimelineSegment(segmentId)
getCaptureTimelineProcessingState(sessionId)
getCaptureThumbnail(eventId)
openCaptureOriginal(eventId)
searchCaptureTimeline(query, filters, cursor, limit)
rebuildTimelineIndex(sessionId)
retryCaptureTimelineProcessing(sessionId)
```

P0 已落地其中的会话摘要、日期索引、分页事实事件、缩略图、打开原图和按学生补齐旧索引接口。P1 查询默认返回活动段和每日记忆，事实事件只在展开证据时分页返回。

P1 内部模块应拆分为可独立测试的纯数据契约：

```text
preSegmentCaptureEvents(sessionId)
selectTimelineKeyFrames(segmentId)
getOrCreateRecognitionArtifact(eventId, contentHash)
refineTimelineSegmentBoundaries(sessionId, recognitionRefs)
buildTimelineMemory(sessionId, recognitionRefs)
buildSessionMaterialBundle(sessionId)
reconcileTimelineDigestReceipt(bundleId, digestBatchId)
```

“重新处理”只作为诊断或提前重试入口；即使用户不点击，系统也必须按照恢复策略继续处理。正常流程由采集结束、资料晋升和消化回执事件自动触发，不增加“生成 AI Memory”按钮。

### 8.3 增量事件

采集变化通知只发送发生变化的字段：

```json
{
  "kind": "capture_delta",
  "activeSession": {
    "id": "capture-...",
    "screenshotCount": 42,
    "deduplicatedCount": 118,
    "lastCapturedAt": "2026-09-10T11:20:30.000Z"
  },
  "session": {
    "id": "capture-...",
    "status": "capturing"
  }
}
```

前端根据增量更新计数，不再每次解析完整历史会话。

### 8.4 独立处理进程与统一重任务调度器

Electron 主进程只负责权限校验、任务编排、轻量状态写入和 IPC 路由，不承担 OCR、原图解码、视觉模型调用、批量哈希升级或大 JSON 结果解析。上述工作应放入 `utilityProcess`、Worker 或受控子进程；进程间只传任务 ID、受管文件引用和小型结果摘要，不传原图 Base64 或大数组。

时间线不能建立自己的孤立后台队列。系统应提供一个全局资源调度器，统一管理：

- 时间线关键帧识别与活动摘要；
- 原始资料消化；
- 学情报告生成；
- Agent 会话记忆整理；
- 历史索引重建。

默认优先级为：连续采集与前台交互 > 用户主动任务 > 关键帧识别 > 会话摘要 > 资料消化 > 历史重建。调度器自动采用三级并发：采集运行或前台延迟超限时为 0；普通前台使用、电池供电或资源一般时为 1；设备插电、持续空闲且 CPU、内存和磁盘延迟均低于阈值时最多为 2，且两个任务必须互不依赖、不能属于同一学生的同一处理链。资源状态恶化时立即逐级回落，无需用户手工切换性能模式。

为避免低优先级任务长期饥饿，排队任务应随等待时间逐步提升调度权重，但不得超过采集和前台交互优先级。队列、已完成单元、尝试次数和下次执行时间必须持久化。单项任务最多进行 3 次快速指数退避重试；连续失败后自动进入低频 `recovery_scheduled`，在依赖或资源恢复后继续探测，不要求人工恢复，也不形成重试风暴。程序启动时只恢复未完成任务，不扫描历史目录。

### 8.5 增量搜索索引

OCR 文本、活动主题和知识概念应写入学生隔离的增量全文索引。实现可选择与现有运行环境兼容的 SQLite FTS 或按学生、日期分片的倒排索引，但必须满足：

- 以稳定的 `segmentId` 为更新和删除单元；
- 只索引新增或内容版本变化的活动段；
- 页面查询直接读取索引，不遍历 `recognition/*.json`；
- 索引损坏可按会话或日期增量重建，不要求全库重建；
- 搜索索引属于可重建派生数据，不保存图片二进制，也不突破学生权限边界。

## 9. 性能优化方案

### 9.1 性能影响结论

合理实现时，基础时间线对空闲状态和采集过程几乎不增加持续负担；主要新增开销发生在用户打开时间线和采集结束后的后台处理阶段。

不合理实现会产生明显卡顿，特别是：

- 一次性加载和解码全部原图；
- 在采集过程中同步 OCR；
- 每次截图都重写完整历史索引；
- 每隔几秒发送全部截图记录；
- 前端一次渲染数百到数千条图片节点。

### 9.2 图片策略

- 时间线只使用缩略图，不直接使用原始 PNG；
- 推荐缩略图采用 WebP 或 JPEG；
- 建议宽度 320～480 像素；
- 单张目标体积约 20～60KB；
- 原图仅在用户点击详情时解码；
- 离开可视区域后释放图片对象；
- 缩略图缺失时按需后台生成，不阻塞首屏。

### 9.3 分页与虚拟列表

- 首屏加载 30～50 条活动或事件；
- 使用游标分页，不使用大偏移量全表扫描；
- 只渲染可视区域附近的时间线节点；
- 日期列表先加载汇总，不预读每天的截图；
- 展开活动段时再读取内部关键帧；
- 搜索结果也必须分页；
- AI 摘要、知识状态和证据详情按路由或展开动作懒加载，不进入应用启动包和时间线概览首屏；
- 首屏只返回活动段摘要，单次展开默认最多解码 6 张证据缩略图，其余继续分页；
- 活动段卡片使用稳定键和记忆化渲染，避免计数、进度等高频状态变化使整条时间线重绘；
- 搜索输入使用延迟值或过渡更新，优先保持输入、滚动和展开交互响应；
- IPC 增量在前端按 ID 归一化合并，不用新建完整数组替换所有活动段；
- 不可见长内容可使用虚拟列表或 `content-visibility`，但不得因此破坏可访问性和滚动定位。

### 9.4 后台任务调度

- 采集运行时：暂停 OCR、AI 摘要和全量索引重建；
- 用户操作活跃时：降低后台并发；
- 程序空闲时：每批处理不超过 8 张关键帧，单个活动段最多选择 1～3 张，单个会话最多 20 张；
- 高 CPU、低电量或磁盘空间不足时：自动暂停；
- 单个学生的时间线识别、资料包生成和正式消化严格串行；
- 时间线、资料消化、报告和 Agent 任务必须进入同一个资源调度器，并发由系统自动在 0、1、2 之间调整；
- 同一会话优先合并为一次受限的 AI 摘要调用；模型单次最多输入 8 张关键帧，最多拆成 2～3 个分块，不按截图逐次调用大模型；
- 新的采集开始、前台交互延迟升高或资源超过阈值时自动让出执行，并在连续稳定的冷却窗口后自动恢复；
- 单项任务最多进行 3 次快速指数退避重试，连续失败后转入不占高优先级资源的低频恢复队列；
- 局部完成结果立即提交，失败单元单独重试，不重新执行整个会话；
- 队列使用等待时间加权，避免报告、消化或低优先级恢复任务长期得不到执行；
- 队列状态持久化，程序重启后只恢复未完成会话，不扫描全部历史；
- 默认自动选择保守资源参数，不增加要求普通用户理解或配置的性能开关。

### 9.5 索引写入

- 采集事件采用追加写入，避免重写整份历史；
- 活动段单独保存，可重新生成；
- 每日汇总采用原子替换；
- OCR、主题和知识概念使用增量全文索引，以 `segmentId` 更新或删除，不在搜索时遍历全部 JSON；
- 图片二进制不写入全文索引，索引文件按学生隔离并按需打开；
- 写入失败时保留旧索引和待重试标记；
- 启动时只恢复未完成任务，不扫描所有历史截图。

### 9.6 建议性能预算

以下为相对 0.17.8 基线的发布硬门槛，必须在同一台普通配置和低配置真机上重复测试；未达标时 P1 不发布：

| 指标 | 目标 |
| --- | --- |
| 未打开时间线时的新增轮询 | 0 |
| 时间线首屏项目数 | 30～50 |
| 时间线首屏打开时间 | P95 小于 1 秒 |
| 程序启动时间增量 | P95 小于 300ms，且无全历史扫描 |
| 同时解码的缩略图 | 不超过 20 张 |
| 单个活动段默认展开证据 | 不超过 6 张，剩余分页 |
| Electron 主进程重计算 | 0；OCR、图像处理、视觉与大结果解析在独立进程 |
| 主线程长任务 | 不得出现超过 200ms 的新增任务 |
| 后台处理期间前台操作响应 | P95 小于 150ms |
| 采集平均 CPU 增量 | 相对 0.17.8 基线不超过 3 个百分点 |
| 采集保存间隔偏差 | 相对配置值不超过 5% |
| 采集期间 OCR/AI 并发 | 0 |
| 单次模型输入关键帧 | 不超过 8 张 |
| 单个会话关键帧 | 不超过 20 张 |
| 单个活动段关键帧 | 1～3 张 |
| 全局 OCR/视觉/AI 长任务 | 自动并发 0～2；采集时为 0，普通使用时为 1，仅插电空闲且资源充足时最多为 2 |
| 相同图片重复 OCR/视觉识别 | 0 次，命中哈希缓存 |
| 同一会话正式消化任务 | 1 个资料包、1 个幂等批次 |
| 100 张截图压缩结果 | 不超过 20 张关键帧 |
| 资料消化输入项数量 | 相比逐张截图方式减少至少 80% |
| 单项失败影响范围 | 仅对应截图、活动段或知识关联；已通过结果保留率 100% |
| 普通后台失败恢复 | 无需用户点击，自动进入快速重试或低频恢复 |
| 并发切换 | 根据采集、前台响应、供电和资源状态自动完成，无用户配置 |
| 前台交互期间后台让出 | 检测到延迟后暂停或降速 |
| 时间线索引失败 | 不影响继续采集和查看原始截图 |

### 9.7 磁盘空间

原始截图是主要空间占用。时间线新增空间主要来自缩略图和索引：

- 360 张缩略图按每张 20～60KB 估算，约增加 7～22MB；
- 时间、标签、摘要和关联索引通常为几百KB到数MB；
- 合理实现后，时间线附加数据预计约为原始截图空间的 3%～10%。

以上为工程估算，不是实测结果。

建议保留策略：

- 未晋升原始候选：默认保留 7～30 天，可配置；
- 已晋升正式资产：沿用档案保留策略；
- 用户标记重点：允许长期保留；
- 缩略图：随对应原始记录删除；
- 识别缓存：设置全局容量上限并按 `lastAccessedAt` 执行 LRU 清理；仍被资料包、正式知识或学情引用的条目依据 `referenceCount` 保留；
- 识别策略升级：新旧缓存按版本并存，超过容量时优先清理无引用的旧策略版本；
- 语义活动段：可以长期保留，但必须保留来源缺失状态；
- 删除原图后，界面明确显示“摘要保留，原始截图已按策略清理”。

## 10. 隐私、安全与教育边界

### 10.1 授权与可见性

- 仅在用户主动开始授权采集后运行；
- 采集期间持续显示悬浮控制条或系统托盘状态；
- 随时提供暂停、继续、重点截取和结束；
- 程序重启后不得静默恢复采集；
- 采集结束后自动进入整理，不延长采集时间。

### 10.2 排除与敏感内容

建议增加：

- 排除指定应用；
- 排除指定窗口标题规则；
- 对密码管理器、系统凭据、安全桌面等默认拒绝采集；
- 对私人聊天、支付和个人账户页面提供默认敏感提示；
- 支持删除单张、单个活动段、单个会话或某一天的临时记录。

窗口名称进入时间线前应脱敏。普通界面不展示完整本地路径、账号、群名或聊天对象。

### 10.3 学生与项目隔离

- 每个采集会话必须明确绑定学生；
- 绑定项目时，主机再次验证项目属于该学生且未封存；
- 时间线查询必须以学生 ID 为后端隔离条件；
- 不能只依赖前端筛选隐藏其他学生数据；
- 跨主机同步默认只发送受治理的知识和摘要，不默认发送原始截图；
- 如确需同步原始截图，应单独授权并记录同步范围。

### 10.4 事实与推断分离

时间线必须区分：

| 类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 记录事实 | 19:20保存一张截图 | 不可被AI修改 |
| 系统计算 | 与上一张画面差异18% | 标记算法版本 |
| AI推断 | 可能正在订正二次函数题目 | 显示置信度和依据 |
| 正式结论 | 已进入成长模型的错误模式 | 必须经过现有证据治理 |

窗口停留时间只能表述为“观察到该窗口处于采集画面”，不能直接表述为“专注学习时间”。

## 11. 分阶段实施计划

### 11.1 P0：基础时间线与性能底座

目标：不新增 AI 调用，基于现有数据提供稳定、轻量的时间浏览。

实施状态（2026-09-11）：P0 代码和性能底座已完成。会话摘要/明细拆分、截图明细 JSONL 追加写、按学生/日期事件索引、30 条分页、日期/会话/原因/归档状态筛选、停止采集后的低优先级缩略图、旧会话按需补齐、打开原图、删除会话同步清理索引，以及学生端逐图 `capturedAt` 上传均已验证。0.17.8 真机反馈确认其默认界面仍是缩略图序列，没有识别、归纳和按时间重组，因此 P0 只视为性能底座，产品功能验收不通过，不单独转正式版。

候选资料清理采用保守策略：P0 不静默按天数删除学生截图；用户明确删除候选会话时，系统自动同步清理该会话的临时原图、会话明细、时间线事件和缩略图。已经晋升的正式资产不随候选会话删除。

开发范围：

1. 将会话摘要与截图详情查询拆分；
2. 建立按学生、日期组织的事件索引；
3. 为每张截图补充或迁移明确采集时间；
4. 建立缩略图生成与缓存机制；
5. 增加分页时间线接口；
6. 增加日期选择、会话筛选和状态筛选；
7. 显示重点截取、保存原因和归档状态；
8. 支持查看原图和打开正式资产；
9. 为旧会话提供按需索引迁移；
10. 增加候选截图保留和清理策略。

预计工作量：约 3～5 个开发日，另需真实设备性能验收时间。

P0 验收标准：

- 已有主机采集会话能够按时间顺序显示；
- 1000 张截图的测试数据不会一次性进入前端；
- 时间线首屏只读取分页数据和缩略图；
- 打开时间线不阻断正在运行的采集；
- 删除会话后索引和缩略图同步处理；
- 原始资料和正式资产不因时间线迁移被覆盖；
- 学生之间不能越权查询；
- 程序重启后时间线仍可正确恢复。

### 11.2 P1：AI Memory 语义时间线与知识闭环

目标：将事实事件自动组织为可理解、可检索的学习过程；时间线默认呈现活动段、每日记忆、知识状态和指导响应，缩略图只作为可展开证据。时间线预处理与原始资料库消化共享识别产物，并由正式消化回执完成知识闭环。

开发范围：

1. 建立全系统统一重任务调度器，统一约束时间线、资料消化、报告生成、Agent 记忆和历史重建；
2. 建立独立工作进程，承载 OCR、图像处理、视觉识别、批量哈希升级和大结果解析；
3. 建立可恢复的会话处理状态机，采集结束并经过稳定窗口后自动排队；
4. 先基于时间间隔、画面变化和来源变化执行 O(n) 初分段，再只用关键帧 OCR 相似度局部修正边界；
5. 每个活动段自动选择 1～3 张关键帧，单会话最多 20 张、单次模型输入最多 8 张；
6. 统一复用资产层 `contentHash`，不得在采集主路径二次同步读取图片计算哈希；
7. 建立学生隔离的 OCR/视觉识别缓存，只处理未命中的关键帧，并设置版本、引用计数和容量清理策略；
8. 生成候选活动主题、候选摘要、当日学习记忆并标记 AI 置信度；
9. 将默认界面改为日期概览和活动段，AI 区域懒加载，缩略图在证据详情中按需分页展开；
10. 把采集晋升改为一个会话资料包和一个待消化任务，不再逐张截图提交消化；
11. 只把关键证据帧作为正式图片资产长期保留，普通重复截图沿用候选保留策略；
12. 正式消化复用 OCR、视觉识别、活动段和会话摘要，不再次识别相同图片；
13. 定义并校验带 `bundleId`、`digestBatchId`、`segmentIds`、`sourceEventIds` 和知识资产 ID 的消化回执；
14. 回执通过后自动写入正式摘要、知识状态、指导响应和知识关联；
15. 支持从知识资产、成长模型和学情报告回到活动段及关键截图；
16. 建立按学生隔离的增量全文索引，支持 OCR 文字、活动主题、知识概念和“已形成知识”筛选；
17. 后台任务支持局部提交、幂等、3 次快速指数退避、低频自动恢复、资源让出和等待时间加权，不要求人工恢复；
18. 增加敏感应用排除、窗口名称脱敏和低置信度异常提示；
19. 兼容已经逐张晋升的旧会话，通过稳定 ID 和已有内容哈希聚合，不重复复制或重复消化。

实施顺序：

```text
P1-A 独立处理进程、自动自适应调度器、最小隔离、无人工恢复状态机和性能埋点
→ P1-B 两阶段分段、统一内容哈希、识别缓存、关键帧和会话资料包
→ P1-C 正式消化回执、知识状态与指导响应反向关联
→ P1-D 活动段优先界面、增量搜索索引、异常恢复和双机性能验收
```

预计工作量：约 2～3 周。P1-A 是防卡顿和后续所有重任务共存的前置架构；P1-B 是避免重复识别与重复消化的前置架构。两者不能为了先展示摘要而跳过。

实施状态（2026-09-12）：P1 本地候选已完成独立 Worker 处理、Windows 本地 OCR/缩略图桥、两阶段活动分段、每会话最多 20 张关键帧、单批最多 8 张的视觉复核清单、学生隔离识别缓存、引用计数和容量清理、会话资料包自动晋升、自动触发正式消化、结构化 `timelineResults` 回执、活动段级身份/批次/来源/内容哈希/知识目标校验、知识状态与指导响应回写，以及知识资产、成长模型、学情报告到精确活动段的回链。语义搜索已覆盖 OCR、主题、摘要、视觉补充和知识概念；默认界面以活动段为主体。人工“确认晋升”已从正常界面流程移除；旧手动接口只作为兼容层保留。

三项运行原则已落到实现：单张 OCR、单个活动段或单项知识链接失败只记录对应最小单元，已完成段照常提交；瞬时失败执行 1/5/15 分钟快速退避，持续失败转为 30 分钟低频恢复且 `requiresUserAction=false`；仅归属、授权或安全边界无法确认时才阻断对应资料包。Windows 学生端停止采集后自动写入持久化送达队列，主机完整接收后自动结束远端会话并排入语义处理；普通用户不需要点击确认或恢复。调度器读取真实前台延迟、CPU、内存、磁盘、供电、空闲、采集和其他重任务信号，自动在 0、1、2 并发间切换。敏感窗口在主机端和学生端均自动禁选，持久化窗口名称使用脱敏后的应用级名称。

本地验证结果：P1 专项与发布契约测试 34/34 通过，生产构建通过；5000 条事实事件基准中追加 P95 4.83ms、最大追加 16.96ms、查询 P95 24.78ms、堆增量 7.67MB；100 帧 P1 Worker 基准中主线程最大定时漂移 1.98ms、关键帧 20 张、重复运行缓存命中 20/20、语义查询 P95 0.36ms。使用一张既有中文界面截图调用 Windows `zh-Hans-CN` OCR 成功并生成缩略图；该单图结果只能证明本机 OCR 链路可用，不能代替真实学习场景质量验收。全量 Node 回归仅有 2 项既有 Android 旧版本号断言失败，与 Windows P1 无关。已生成隔离的 `p1-semantic-closure-20260912` 主机端和学生端候选包；两包当前均未配置 Authenticode 签名。以上是本机代码/合成负载结果，不能替代低配置真机长时采集、真实 OCR/视觉内容质量、真实 Agent 消化回执和双机回链验收。

P1 验收标准：

- 默认时间线呈现活动段和学习记忆，不再把缩略图序列作为主体；
- 相邻截图能按实际时间顺序压缩为少量活动段，跨会话和跨午夜不发生错序；
- 每个 AI 判断、知识状态和指导响应都可以打开对应活动段及关键截图；
- 未晋升内容明确显示“候选观察”，不能进入正式知识、成长模型或学情报告；
- 每个采集会话最多形成一个有效资料包和一个进行中的正式消化批次，批次内部按活动段局部提交；
- 同一图片哈希重复处理时命中识别缓存，不再次执行 OCR/视觉识别；
- 初分段阶段不执行全量 OCR，只有入选关键帧可以进入识别队列；
- 正式消化复用会话资料包，不把每张截图作为独立资料重复消化；
- 消化回执按活动段和知识关联分别通过学生、批次、来源 ID 和哈希自动校验，单项失败不阻断已通过项目；
- 消化失败时仍能查看事实层和候选活动段，并显示准确失败状态；
- 重复运行不会产生重复活动段、资料包、消化任务或知识链接；
- 普通后台失败无需用户操作即可从 `retry_scheduled` 或 `recovery_scheduled` 自动恢复；
- 单张截图、单个活动段和单项知识关联失败均不阻断同会话其他内容；
- 学情报告引用能够定位到对应活动段；
- 采集期间 OCR/视觉/AI 并发为 0，全部重任务服从同一个调度器；
- 普通使用时重任务并发为 1，仅插电空闲且资源充足时允许自动提升到 2，资源恶化后能自动回落；
- OCR、图像处理、视觉识别和大结果解析不在 Electron 主进程执行；
- 时间线首屏、启动、CPU、保存间隔和前台响应全部通过第 9.6 节硬门槛；
- 100 张截图最多选择 20 张关键帧，正式消化输入项相比逐张处理减少至少 80%；
- 相同会话重复处理时新增 OCR/视觉调用为 0；
- 敏感窗口排除规则真实生效；
- Windows 主机端与学生端完成至少一次双机真实采集、晋升、消化和回链验收。

### 11.3 P2：可选增强

P0–P1稳定后再评估：

- 日、周、月学习过程对比；
- 跨采集会话的主题连续性；
- 时间线与授权 Agent 会话的关联；
- 从时间线生成复习入口；
- 家长或教师查看的简化摘要；
- 用户选择的局部时间线导出；
- 对已删除原图的长期摘要保留策略。

P2仍不应引入注意力评分或无依据的学习效率排名。

## 12. 测试方案

### 12.1 功能测试

- 固定间隔、内容变化、智能混合三种策略；
- 暂停、继续、重点截取和结束；
- 无项目、有项目、有课程三种归属；
- 候选、已晋升、已删除和源文件缺失；
- Windows 主机采集和 Windows 学生端上传；
- 消化成功、消化失败和部分完成；
- 未晋升时只生成候选活动段，不更新正式知识；
- 晋升时形成一个会话资料包，而不是每张截图一个消化任务；
- 时间线处理和正式消化复用同一 OCR/视觉识别缓存；
- 正式消化回执能把知识状态与指导响应关联回活动段；
- 回执中某个活动段的学生、批次、来源或哈希不匹配时只拒绝该项回链，其余有效项目正常提交；
- 单张关键帧识别失败时，同活动段的其他证据和同会话的其他活动段继续处理；
- 会话摘要失败时，已完成活动段继续可见且不回滚；
- 三次快速重试均失败后自动进入低频恢复队列，整个过程不点击“立即重试”也能恢复；
- 网络、模型服务或资源恢复后，低频恢复任务自动重新执行且不产生重复知识；
- 只有学生归属、授权或安全边界无法确定时才进入需要用户处理的阻断状态；
- 同一天多个会话和跨午夜会话；
- 系统时区变化和设备时间异常；
- 同一截图重复上传；
- 同一会话重复处理、重复晋升和重复读取回执；
- 已经逐张晋升的旧会话聚合迁移；
- 程序异常退出后的恢复。

### 12.2 性能测试

必须在同一台设备、同一采集参数下，以 0.17.8 作为 P0 基线进行前后对比；普通配置和低配置 Windows 真机各至少一台。至少建立三档数据集：

| 数据集 | 用途 |
| --- | --- |
| 100 张 | 日常功能和首屏体验 |
| 1000 张 | 单个重度会话和分页验证 |
| 5000 张 | 长期历史、搜索和启动性能 |

采集以下指标：

- 程序启动时间；
- 时间线首屏时间；
- 分页加载时间；
- 滚动帧率和界面无响应次数；
- Electron 主进程与渲染进程内存；
- 采集时 CPU 和磁盘写入；
- 后台 OCR 时 CPU、内存和交互延迟；
- Electron 主进程长任务数量与最大持续时间；
- 实际保存间隔相对配置间隔的偏差；
- 全局重任务最大并发数及采集开始后的暂停耗时；
- 100 张截图的关键帧数量、模型分块次数和资料消化输入压缩率；
- 同一会话第二次处理产生的 OCR/视觉调用次数；
- 索引文件大小和缩略图空间；
- 删除和重建索引耗时。

性能测试必须覆盖以下组合：

- 连续采集中打开、滚动、搜索和展开时间线；
- 时间线识别、资料消化、报告生成和 Agent 后台任务同时排队，验证并发能根据资源在 0、1、2 之间自动调整；
- 处理过程中开始新采集，验证后台任务及时让出且采集间隔不明显漂移；
- 插电且持续空闲时自动提升到最多两个互不依赖的重任务；
- 电池模式、前台活跃、低磁盘空间和高 CPU 压力下自动降速或暂停，并在冷却窗口后自动恢复；
- 高优先级任务持续进入时，等待时间加权仍能保证低优先级任务最终执行；
- 程序重启后只恢复未完成任务，不扫描 5000 张历史截图；
- 搜索增量更新与索引损坏后的局部重建。

测试结果应输出 P50、P95、最大值和相对基线差异，不能只记录“感觉不卡”。第 9.6 节任一硬门槛未通过即判定 P1 性能验收失败，功能正确不能替代性能验收。

### 12.3 隐私与隔离测试

- 排除应用不产生截图；
- 暂停期间不产生截图；
- 学生 A 无法读取学生 B 的时间线；
- 项目归属变化后主机重新校验；
- 删除某日原图后不存在残留缩略图；
- 跨主机知识同步不会隐式携带原始截图；
- 日志不输出完整敏感窗口标题和本地路径。

## 13. 风险与处置

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 原图全部加载 | 内存激增、界面卡顿 | 缩略图、分页、虚拟列表 |
| 采集时实时OCR | CPU升高、采集丢帧 | 采集结束后低优先级处理 |
| 重计算仍在 Electron 主进程 | 主界面卡顿或无响应 | 独立工作进程，主进程仅编排与轻量 IPC |
| 各模块拥有独立后台队列 | OCR、报告和消化同时抢资源 | 使用全系统统一重任务调度器和优先级 |
| 全量截图先 OCR 后分段 | 调用量、CPU 和等待时间失控 | 两阶段分段，只识别有限关键帧 |
| 为时间线重复读取文件算哈希 | 采集路径磁盘阻塞 | 复用资产 `contentHash`，后台异步升级算法 |
| 时间线和资料消化分别识别 | 重复成本、结论冲突 | 统一识别缓存，按图片哈希复用 |
| 每张截图独立进入消化 | 任务和知识碎片爆炸 | 会话资料包、关键帧和单一批次 |
| 候选摘要被当成正式知识 | 误导成长模型和学情报告 | 候选解释与正式回执字段分离 |
| 消化结果无法回到时间线 | 知识失去过程依据 | 回执强制包含活动段和事件来源 ID |
| 单一大型JSON | 更新和启动越来越慢 | 按会话、学生和日期拆分索引 |
| 搜索时扫描全部识别文件 | 首次搜索和长期历史越来越慢 | 学生隔离的增量全文索引 |
| 单项失败导致整批回滚 | 有效知识延迟或丢失 | 按截图、活动段和知识关联局部提交、最小隔离 |
| 失败任务无限自动重试 | 后台资源持续占用 | 3 次快速退避后转入低频自动恢复队列 |
| 失败后依赖用户点击重试 | 自动化流程长期停滞 | 自动探测依赖恢复，“立即重试”仅作为可选入口 |
| 固定单并发形成长期积压 | 摘要、消化和报告延迟 | 根据采集、供电、空闲和资源状态自动使用 0～2 并发 |
| 前端每次替换完整时间线 | 高频重渲染、滚动掉帧 | IPC 差量、按 ID 合并、懒加载和稳定组件 |
| AI错误分类 | 误导用户 | 显示推断、置信度和来源 |
| 磁盘增长 | 占满学生设备 | 保留期限、容量阈值和自动清理 |
| 隐私内容进入截图 | 敏感信息泄露 | 排除规则、暂停、删除、默认本地 |
| 上传时间代替采集时间 | 时间线错序 | 学生端传输原始 `capturedAt` |
| 原图删除后引用失效 | 无法查看依据 | 显示来源缺失状态，保留摘要但不伪装证据仍存在 |
| 旧数据格式差异 | 历史会话无法浏览 | 按需迁移、迁移版本和回退机制 |

## 14. 发布与回退

### 14.1 发布前置条件

- P0 性能测试通过；
- P1 默认界面已经从缩略图序列改为活动段和学习记忆；
- 独立工作进程、统一重任务调度器、持久化队列和性能埋点已经真实运行；
- 局部提交、最小隔离、低频自动恢复和自动自适应并发通过故障注入测试；
- 会话资料包、识别缓存复用和正式消化回链通过自动测试；
- 知识状态与指导响应只来源于已校验正式消化结果；
- 学生隔离测试通过；
- 旧采集会话迁移不覆盖原数据；
- 候选截图删除与正式资产保留边界验证通过；
- Windows 主机和学生端的时间字段一致；
- 普通配置和低配置真机均通过第 9.6 节性能硬门槛，且保留与 0.17.8 基线的测试记录；
- 文档明确说明采集是用户主动授权的连续截图，不是隐式录像。

### 14.2 灰度策略

- P0 仅作为内部事实层和性能底座，不再以完整学习时间线对外验收；
- P1 语义增强可作为后台可关闭能力，但产品默认视图必须明确区分“待识别”“候选观察”和“已形成知识”；
- OCR 和 AI 分段失败时仅将受影响单元自动降级为事实层，并显示降级状态，其余结果继续提交；
- 后台失败由系统自动恢复，不把“立即重试”或人工审核作为正常流程依赖；
- 不因时间线失败阻断资料上传、消化、知识同步和学情报告。

### 14.3 回退原则

- 时间线索引属于可重建派生数据；
- 回退时只停用新索引和新界面；
- 不删除原始截图、正式资产和既有消化结果；
- 新增字段保持向后兼容；
- 索引损坏时允许按会话重建。

## 15. 最终建议

建议立项，但必须按照以下顺序实施：

```text
保留P0事实索引与性能底座
→ 先建立独立处理进程、统一重任务调度器、最小隔离、自动恢复和性能埋点
→ 建立两阶段活动分段、统一内容哈希、识别缓存和有限关键帧
→ 用会话资料包替代逐张截图消化
→ 接通正式消化回执、知识状态与指导响应
→ 默认展示活动段和学习记忆，缩略图作为分页证据，并接入增量搜索索引
→ 完成双机真实采集、消化、回链和量化性能验收
→ 再发布正式学习时间线
```

本功能的用户价值明确：它让屏幕资料不再只是散落截图或一次性消化输入，而成为能够按时间回看、自动解释知识如何形成、能够支撑学情结论的学习过程档案。P0 缩略图序列不是最终产品，达到上述 P1 验收标准后才构成最低可用的 AI Memory。

但产品价值成立的前提是：时间线服务于学生自己的学习回顾和可信证据链，而不是监控；AI只补充解释，不改写事实；功能增加后不显著增加用户操作，也不影响连续采集、资料消化和知识管理等核心功能的稳定运行。P1 应以“局部失败不阻断整体、后台失败不要求人工恢复、并发自动适应设备状态、重复处理可被证明为零”为运行原则，而不是以功能页面能够显示摘要作为完成标准。
